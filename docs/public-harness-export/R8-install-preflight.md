## 现有候选验证器的准确边界

阅读 `scripts/release/candidate_codex_plugin.py` 的 `prepare()` / `verify()`：

1. prepare 记录 CLI 版本、构包并创建候选状态；不在记录版本时立即比较受审计版本。
   verify 在隔离 registry、launcher 和若干 smoke 后才完成 CLI 契约探测。因此当前
   已知版本不匹配应先报告，不值得再次启动整条链。这里只确认检查顺序，没有测量
   本轮可节省的秒数。
2. verify 包含隔离 registry、真实入口 smoke、PreTool 链及 MCP 检查；这与只做文件
   打包不同，但本轮未运行这些步骤。
3. scheduler 入口使用隔离的替身 launchctl 和 dry-run；`scheduler_host` 明确输出
   `unobserved`，不得报告为真实 launchd 加载通过。
4. `native_permission_ui` 明确输出 `unobserved`，候选 CLI 没有当前会话可附着的
   PermissionRequest 界面。不能将其候选 verified 回执等同于人工审批界面已验收。
5. 当前候选流程不自动证明完整事务安装、升级回滚和 Windows 原生执行。

第 3、4 项是验证覆盖范围，不因未观测本身就判为代码缺陷。R6 bootstrap 组合调用被
