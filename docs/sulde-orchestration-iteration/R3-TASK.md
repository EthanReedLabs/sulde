## 4. 五项返修

### R3-01：覆盖证明不得退化为调用方布尔声明（P1）

**反例**：B 持有 `0.1.0:<完整摘要>` 的活跃租约；只把 A 传给 plan 并设置 `certify_scope_coverage=True`，得到 `coverage=complete`、`reclaimable=1`；apply 删除目标时 B 租约仍活跃。

**位置**：`generation_guard.py:337` 起；行号基于 reviewed HEAD。

**不变量与最小修复**：

1. “列出的目录都读成功”不是“全部引用已覆盖”。调用方声明必须能与已有权威注册/运行来源独立核对，绑定目标、scope 集、来源身份及新鲜度；一个 flag、任意路径列表或自签摘要都不能生成该证明。
2. 复用已有事实和协调入口，不为此重建全局控制面。若现有架构不能证明完整覆盖，则关闭共享目标实际回收，保留 dry-run/诊断；不得保留任意参数即可绕开的 apply 入口。
3. 证明检查和回收必须处理计划后新增 scope/引用，不能只证明过去一刻的清单完整。scope 覆盖与单任务并发额度保持分离。
4. 验收：遗漏活跃 B、伪称已认证、过期/损坏证明、新增 scope 均不能实际回收；只有确有完整有效证明且无引用的正例可以回收。若选择安全禁用，负例须证明所有实际入口均关闭；报告区分“安全缺口关闭”与“自动回收能力未交付”，不得自称全功能完成。

### R3-02：apply 必须验证原引用目录，禁止补建空证明（P1）

**反例**：生成可回收计划后，让已声明的租约目录消失；apply 经 `lease_guard()` 重建空目录，并继续成功删除目标。

**位置**：`generation_guard.py:437`、`run_concurrency.py:118`。

**不变量与最小修复**：

1. 分离“新运行允许初始化租约目录”与“回收方只能打开既存引用来源”的语义；不能为修 GC 禁止正常新任务初始化。
2. apply 核对计划绑定的物理目录身份、可读性和 scope 证明；目录消失、被替换、变成链接或无法访问均应拒绝回收且保留 unknown。
3. 不只加锁前 exists 检查；验证与锁持有期间必须避免路径替换及自动 mkdir 抹去丢失事实。锁顺序去重、规范化并有界，避免同一目录不同拼写造成自锁。
4. 验收：计划后消失不重建、不删除目标；同名空目录替换、符号链接替换、不可读来源、重复 scope；正常租约初始化与合法回收正例不回归。
5. 不删除权威 retirement/audit 事实。仅在临时夹具中演练删除，并回读目标、来源目录和审计状态。

### R3-03：检查与切换共享有效准入边界（P1）

**反例**：持有真实 `_deployment_lock()`，两次 `_generation_switch_projection()` 均返回 compatible=true；随后仍能取得旧代际不兼容租约。租约创建不参与 deployment lock，因此第二次检查之后、切换之前的窗口仍存在。

**位置**：`install_codex_plugin.py:4837` 与 `run_concurrency.py` 的租约获取链。

**不变量与最小修复**：

1. 在现有架构中确定真正的线性化点：租约准入与代际提交必须通过同一有效协调协议（短临界区/代际 fencing 或已有等效机制），不能靠第三次检查、sleep 或长时间全局锁。
2. 明确锁顺序、崩溃恢复和超时；不把普通任务、旧代际运行及恢复通道全部锁到安装全程。旧任务可安全保留，新任务按已提交代际路由。
3. block 确认不安全时，在相关生产变更之前拒绝；兼容并存正例仍可推进。observe 只报告观测，不伪装成已实施的阻断保证。
4. 用可控进程间屏障，在**最后一次检查之后、首次活动状态变更之前**尝试获取不兼容租约。断言其无法悄悄穿过；同时证明安全的新任务/兼容切换不会永久阻塞。
5. 通过实际隔离安装调用链验证该交错；只 mock `_install_locked` 未被调用仅覆盖入口拒绝，不覆盖本窗口。验证切换失败/回滚后准入能恢复，不形成自锁。

### R3-04：重试操作身份稳定，失败后重复也幂等（P1）

**反例**：同一 provider 睡眠 3 秒、timeout=1 秒。首次执行启动数=1；`--retry` 再超时后为 2；原样重复 `--retry` 后为 3。现有测试只覆盖第二次成功后的重复。

**位置**：`agent-runtime.py:5308`、`dispatch_registry.py:open_retry()`。

**不变量与最小修复**：

1. 给重试操作独立、稳定的请求身份，绑定准确 predecessor run/attempt 和内容摘要；重复同一操作始终回放或恢复它自身，即使重试失败/超时也不产生下一尝试。
2. 真正第三次尝试必须是明确的新重试操作；迟到重复重试 1 不能错误作用于已经前进到重试 2 的链。
3. 不把 provider stop_reason 或 `--retry` 标志当成清除未知效果、人工门或暂停原因的权限。policy pause 的安全续接与新副作用执行分开处理，不损坏已修复的 correction 续接旅程。
4. 验收：首次超时 + 同一重试再超时 + 重复该重试，启动数仍为 2；新重试身份才允许变为 3；并发相同重试、同身份异内容、错误 predecessor、迟到请求及崩溃窗口均可核验。
5. 同步检查请求投影、账本、CLI 接口及其直接调用方，避免调用方每次随机生成身份而使去重失效。

### R3-05：恢复结论持久化，多次回放不破坏原事实（P2）

**反例**：在现有 `test_crash_window_replays_original_failure_not_success` 中，丢失 closed 行后第二次提交正确返回 failed；再追加第三次相同提交，却变成 awaiting_human / task_conclusion_unresolved。

**根因线索**：恢复 close 没有补齐结论；回放覆盖 status 并将 `run=` 变成 `duplicate_of_run=`，下次对账失去可识别来源。不要仅扩大正则后宣称持久性已解决。

**不变量与最小修复**：

1. 复用既有权威结果模型，恢复时把已独立证明的任务结论及来源持久结算；投影/展示不覆盖或降格原始事实，不另建竞争真值系统。
2. 结果、身份、失败原因、验证状态与 close 可恢复地保持一致；区分 provider rc 与任务终态。真实未知仍保持 unknown，不利用旧成功状态猜测另一 run 的结果。
3. 测试成功、失败、timeout 及待验证任务在 closed 丢失后跨新进程至少 3 次重复回放；再覆盖恢复写入各断点、归档轮次、损坏记录和迟到回执。
4. 断言最终状态/来源/原因一致、启动数不增加、原事实未被覆盖；有据可恢复的终态不得因重复查询变成人工自锁。
