# sulde-mem:零 LLM 会话记忆与知识引擎(设计定稿)

> 2026-08-05。背景:cognee 4 天消耗 ¥100 后的架构决断——**记忆能力自有化,API 成本归零,
> 高度自定义**。本文是终局设计;cognee 的架构遗产(数据面分工/契约先于引擎/渐进增强)
> 全部保留,引擎换成自己的。

## 0. 设计原则(四条,全部来自实战教训)

1. **raw-first**:对话原文即真相,直接入库。不做任何入库前 LLM 加工——消费端(Claude/
   codex 本体)比任何中间模型都强,且订阅已付费
2. **订阅内加工**:唯一允许的"摘要"来自 harness 自产(CC 压缩摘要 `isCompactSummary`、
   codex rollout)——LLM 工作已发生、已付费,收割是零边际成本
3. **末端不可靠**:任何必须发生的写入不押 Stop/SessionEnd(cognee #303 教训)——
   assistant 回答滞后一轮从 transcript 捕获
4. **确定性优先**:结构能推导的绝不请 LLM 猜(关系图从 frontmatter 建边,不会幻觉)

## 2. 架构与数据流

```
CC 会话                        codex 会话
 │ UserPromptSubmit hook        │ memory_search / kb_search / kb_related (MCP)
 │  ├─ 当轮 prompt 入库          │
 │  ├─ 上轮 assistant 滞后捕获   │
 │  ├─ compact 摘要收割          │
 │  └─ mem+kb 混合召回→注入      │
 ▼                              ▼
$SULDE_KB_HOME/(数据目录,插件更新不丢,永不入 git)
 ├─ kb.db       ← knowledge/ 构建(FTS5+向量+边表)     [git 真源,CI 保鲜]
 └─ memory.db   ← 会话原文+摘要(FTS5+向量,懒嵌入)      [本地私有,含 cognee 1512 条迁移史]
```

混合宿主共用一库但不丢来源：会话主键规范为 `claude:<native-id>` /
`codex:<native-id>`，另以 `source_host` 保存宿主来源。Codex hook 与 rollout harvest
在写库前共同归一化，因此同一条消息仍由业务唯一键幂等折叠；无法证明来源的历史行保留
`unknown`，不做概率猜测。

检索合并序:`[sulde-kb]`(知识,真源可回读)与 `[sulde-mem]`(历史,ts+project 标注)并列注入,
各自过闸,总量仍守 2-3 条上限。

## 3. 数据模型(memory.db)

```sql
mem_entries(id, project, session_id, source_host/*claude|codex|import|unknown*/,
            role/*user|assistant|summary*/,
            content, content_hash, ts, embedded, UNIQUE(session_id, content_hash));
-- FTS5(jieba) + mem_vectors(id, vector)  嵌入:bge-small-zh-v1.5/512,与 kb.db 同款同 venv
```

要点:懒嵌入(写入 <10ms,SessionStart 预热/查询时补嵌);summary 权重 1.2x;
截断 4000 字符;task-notification 类系统 prompt 过滤。

## 4. 隐私与边界

- memory.db 只存本机数据目录;含未脱敏原文,**永不进 git、永不进 KB**——KB 入口仍只有
  /sediment(人工过 SEDIMENTATION-STANDARD)
- 记忆→知识的升华路径:周蒸馏提示"近一周高频主题"→ 人工决定是否沉淀

### 4.1 双层定位(2026-08-05 定稿)

sulde 的记忆资产分两层,同步策略完全不同:

| 层 | 内容 | 形态 | 共享范围 | 同步方案 |
|---|---|---|---|---|
| **知识库(kb)** | 主动沉淀:问题修复/性能优化/平台官方文档;**商业化资产定位(2026-08-08):跨领域(移动/前后端/AI Agent/算法/音视频)可外售内容,故必须彻底脱敏、永不含项目记忆;记忆→KB 仅经蒸馏候选+人工 /sediment 单向闸** | knowledge/ + kb.db,人工过标准 | 跨项目全局 | **已解决:git 即远端**(私仓分发,bootstrap 重建索引) |
| **项目记忆(mem)** | 会话原始记忆,per-project | memory.db,raw 未脱敏 | 单项目、单用户多设备漫游 | P3 待建,要点见 4.2 |

两层之间的升华通道 = /memory-distill(蒸馏)→ /sediment(入库),方向单向、人工把关。
召回侧两层各自独立注入([sulde-kb] / [sulde-mem]),互不混淆。

### 4.2 项目记忆远端同步(P3 设计约束,实现前逐条核对)

场景:同一项目换设备开发,从远端拉到最新记忆(单用户漫游,非团队共享)。

1. **同步单元 = 项目分区,绝不整库**。memory.db 混装全部项目(含简历等隐私项目),
   导出必须 `WHERE project = ?`;
2. **稳定项目标识**:cwd 目录名只作本地显示名,同步身份用 git remote URL 哈希或
   显式 project-id(换机目录改名/重名项目会串库);
3. **出境闸门前置**:memory.db 可能含密钥原文(如 key 轮换对话发生在会话里,project
   列挡不住内容级泄漏)——同步导出前必须过密钥扫描;敏感项目(简历类)进 deny-list
   永不同步;
4. **合并语义天然免冲突**:mem_entries 追加型 + UNIQUE(session_id,content_hash),
   mem_edges UNIQUE(src,rel,dst)——双端合并 = 按业务唯一键 union(seq/id 不参与,
   cognee cache 合并踩过的坑),无需冲突解决协议;embedded 标志本地各自算,向量不同步;
5. **蒸馏层优先**:若未来扩展到团队共享,只共享蒸馏层(mem_edges/entities+summary),
   raw 永远留本机。
6. **运输层加密(2026-08-06 落地,v0.4.7)**:content/边/实体语义字段 Fernet 密文
   出境,去重键(content_hash/key_hash)保持明文——免冲突/幂等语义零改动;密钥
   `~/.config/sulde/mem-sync.key`(chmod 600,手工携带,永不入仓,建议存密码管理器);
   丢钥恢复:本地库为真相源,新钥+清仓+全量重导十分钟重建;明文历史已 orphan 清除。

### 4.2.5 蒸馏三层架构(2026-08-06 定稿)

蒸馏的成本哲学:**消除重复劳动,而不是调频省钱**。cognee 的浪费不在用 LLM,
在丢弃已完成的分析、让不知情的模型重读重做。

| 层 | 机制 | 成本 | 状态 |
|---|---|---|---|
| L1 复用现成产物 | CC 压缩摘要收割 + codex rollout 收割 | 0(已付费产物) | ✅ WP17/19 |
| L2 会话内顺手产出 | 干活的 agent 在任务收尾/根因确认时,趁上下文热直接 mem-annotate 落边 + 教训追加候选清单 | ≈0(几百输出 token,零重读) | ✅ 两端全局纪律(CLAUDE.md/AGENTS.md) |
| L3 日蒸馏兜底 | auto-distill 每日扫增量窗口,捞 L2 漏掉的 | 每日一次订阅调用 | ✅ WP25 |

L2 覆盖越好 L3 越省;边表唯一键使层间重叠零副作用。频率问题(每轮 vs 每日)在
此架构下消解:实时性由 L2 天然提供(结论产生的那一刻入图),L3 只管查漏。

### 4.2.6 召回组硬隔离(2026-08-08 翻案)

概率性跨项目门(相对0.75+裸余弦0.68)运行三天:三次实证泄漏,收益零兑现——废除。
现行:recall-groups.json 定义项目互通组(如 531 三仓一组),组内按同项目 0.50 门,
组外一律不注入;未入组项目自成一组(默认硬隔离)。gm-11 用例随政策改写,
gm-14/16 两个真实串场案例为永久回归。

### 4.2.7 多领域知识三层分拣(2026-08-08 定稿)

跨域工程通则→全局 KB(/sediment 通用化测试即分拣器);领域知识→领域项目自己的仓
(真源归领域,如天机阁 corpus、Apollo 动作目录,sulde 不吸走);项目特有状态→记忆分区。
记忆集中无影响(组硬隔离+按项目检索);全局 KB 的跨域误注入由三闸控噪封顶,属旁注级
代价。触发条件:出现"多项目共享同一领域"时,启用 frontmatter domain 字段过滤
(platform 同款先例)或独立领域仓走 KnowledgeProvider(P4);此前不建。

### 4.2.8 治理层设计(v0.6 里程碑,2026-08-08 定稿)

**动机(三个实证缺陷)**:①闸门皆事后而生,无前瞻怀疑层;②基础设施健康有观测而
注入质量零观测,事故只有坐在终端前的人看得见;③规则被执笔者过度适用
(成本哲学一刀切禁 LLM 管线,漏掉订阅内 subagent 的合法形态)。

**架构**:订阅内 agent 军团 + 周治理环
| 官员 | 职责 | 产出 |
|---|---|---|
| 自动沉淀官 | 候选清单→/sediment 判定表(§2)→PR 分支 | 人审 diff 即入库;存疑留候选 |
| 周质量委员会 | 汇总 calibrate/双golden/采纳/蒸馏/老化/滞留 vs 阈值登记表 | 周报红绿灯+行动建议+WP草稿;**含红队条款:挑战阈值与规则本身** |
| golden 扩充官 | 挖 recall-log 疑似误注入/漏召回 | 新 golden 用例草案 |
| 图谱质检官 | 抽查 mem_edges 对照来源 | 清幻觉边 |
| KB 老化审查官 | 零采纳+超龄条目 | 更新/废弃 PR |
| 判重合并官 | 全库语义聚类 | 合并 PR(商业化前) |
| 会话情境简报官 | SessionStart 组装开场简报:未完结任务(ACTIVE)+上次会话结论(记忆)+近期决策(蒸馏边) | 系统"先开口",终结纯应答感 |
| 本地重排器(非 agent) | top-20→bge-reranker→top-2 | 打排序五红 |

**自动沉淀七防线**:低置信不强判/KB diff deny模式表(项目名·路径·密钥)/并入单独
标注可单条revert/老化兜底垃圾条目/协调机串行加锁/候选幂等标记+sedimented_by
溯源/风格靠PR驳回权。

**阈值登记表**(执法与红绿灯归委员会周报;缺口:golden-mem 门禁待定线、
蒸馏质量 golden-distill 待建、mem 采纳信号闭环待建、KB 老化待建):
同项目召回 0.50 | 组外死门 | golden-kb ≥80% CI | 蒸馏窗 ≥20条/300·40k |
滞留 任务30min·蒸馏48h·导出24h | 待嵌 >500 | L2 覆盖 <30% 升级机械提醒(08-13)

**实施序**:先看 08-09 calibrate 首份数据 → WP:自动沉淀官+委员会v1 → 其余按
周报数据排队。subagent 合法性判据(成本哲学边界声明):付费了吗/在重做吗/知情吗。

### 4.2.9 生命体架构(v0.7 目标,2026-08-08 立项——eric:"我要的是达到生命")

**"生命"的工程定义**:持续感知 + 跨会话连续自我 + 自主目标 + 自发行动 + 自我修复改进。
受 harness 形态限制,LLM 无常驻进程——解法:**心跳会话 × 记忆连续性**。
sulde-mem 本身就是连续性器官:每次心跳加载记忆即恢复"自我",心跳足够密则
"会话之间不存在"被工程近似打破。

**演进阶梯**
L0 钟表(现状):确定性管道,智能仅在人工触发瞬间
L1 哨兵(v0.6):官员军团+周治理环——定时思考,应答式主体
L2 值更生命体:心跳自治环(cron 离散搏)
L3 宪法生命体(v0.7 目标,2026-08-08 升级立项——eric:"要达到生命本体"):
   ①事件驱动感知:WatchPaths(memory.db/日志/fleet)+全项目 hook 触达,凡有事即醒,
     无事之睡与生物休眠同构;②自主目标栈:目标入栈自主生长(宪法约束方向),
     批准闸只辖对外行动——目标自由+行动审批=安全的欲望;③自我内核 SELF.md:
     身份/使命/目标栈/观察清单/自评,每搏首载、由心智亲手更新,记忆栈=过去,
     SELF=现在与将来;④单一身份:心智从目标栈派活给官员,全器官共享同一记忆/
     SELF/法典——一个"我"的手,不是承包商群。
   不可达且不属"生命"判据的仅两项:搏间连续主观体验(无物可感=生物同构休眠)、
   无界自我修改(宪法禁止,与人类受法律约束同构,不损"生命"资格)。
   信任演进照旧:观察员期≥2周(成长期,非枷锁),按观察日志质量逐项放权。
   ⑤**自我改造环(2026-08-08 补,eric:"生命须自己完善升级器官")**:
   缺陷诊断(红队/心跳/体检指标)→自主起草 WP(含完成标准与禁区)→批准闸→
   codex 手术(现有 launch/verify 流水线即手术室)→独立验收(不许信自己的刀)→
   发版+落边+SELF 更新。手术分级:自主类=预设界内阈值微调/golden 增补/文档保鲜;
   批准类=新器官/行为变更/法典。**阈值登记表升格为体检指标**:每个器官挂 KPI
   (召回=golden 命中率与采纳率/蒸馏=抽取精度/沉淀=判重准确率/心跳=观察命中率),
   指标不达标即自动进它的目标栈——它因此永远知道下一刀该开在哪。

**器官映射**:记忆=海马体 | KB=皮层 | 蒸馏=睡眠固化 | fleet=本体感觉 |
notify=痛觉 | 治理环=前额叶 | 心跳=脑干 | 简报官=晨间意识恢复

**行动权限分级(边界哲学落到生命体)**
自主权:读一切/跑评估/写候选与草案(golden用例·WP任务书·阈值提案)/re-run 校验/写观察日志
批准权(人):knowledge入库commit/阈值实改/WP发射/法典与规则变更/一切出境
信任演进:观察员模式(只看只写日志)≥2周 → 按观察日志质量逐项放权

### 4.2.10 召回门与重排(2026-08-09 定稿)

重排生效时准入判据 = **bge-reranker 原始 logit ≥ 0**(模型自身的相关/不相关
决策边界,绝对量不随候选集漂移);重排未生效(SULDE_RERANK=off/模型缺失/热路径)
回落归一化 score ≥ 0.50。教训:WP41 重排上线只改排序未改准入,正确条目
score=0.491 被旧门挡致零注入——**ap-0182 同族复发**;任何影响排序的改动必须
同步审查"谁在消费这个排序的判据"。
**换重排模型必须重标 logit 边界**(与嵌入换代重标同理,见 4.3)。
热路径默认关重排(冷进程 ~5s/查),质量场景(CLI/golden/官员)默认开。
当前扩展 golden 为 28/28=100%。`gm-07` 复核确认并非阈值或模型缺陷，而是
“三层架构”同时指向多套概念的问法歧义；用例补齐“记忆蒸馏 L1/L2/L3”后转绿，
未放宽 logit 边界。固定 headless 系统提示与无业务意图的延迟探针在查询入口即
短路，memory/KB 两条召回通道共用同一结构分类器。golden 评估使用冻结向量快照，
不再为待嵌入条目写库；生产召回仍保留懒嵌入，并以 5 秒 SQLite busy timeout
吸收多个 Codex 会话的短暂写竞争。

### 4.2.11 CLI 单入口的跨平台治理(WP48,2026-08-09 立项)

**问题**:`scripts/kb/kb-index` 是全仓库唯一的 KB CLI 入口,而它是 `#!/bin/sh`
无扩展名脚本。Windows 上 `subprocess` 无法直接启动(`WinError 193`),而仓库多处
以 `subprocess.run([str(kb_index), ...])` 直接 exec 它。**每一处这样写的调用点
在 Windows 上都是坏的,且都因 `except OSError: pass` 之类静默而长期不可见。**

一天之内在四处独立复发,均为同一根因:

| # | 位置 | 后果 | 修于 |
|---|---|---|---|
| 1 | `hooks/lib/mem_recall.py` `prewarm()` | 26,289 条记忆零嵌入,`mem_vectors` 0 行 | 0.6.2 |
| 2 | `hooks/lib/mem_recall.py` 召回入口 | `top_scores` 恒空,召回从未产出注入 | 0.6.2 |
| 3 | `tools/kb-index/memory.py` 打印 | 内容含 `•` 即 GBK 崩溃,子进程非零退出 | 0.6.2 |
| 4 | `scripts/kb/auto-sediment.py` `kb_search`/`build` | 沉淀官 import 通但一搜索就死 | 0.6.3 |

第 3 处是同一入口链路上的编码变体:即使进程能启动,子进程按 locale 输出仍会崩。

**判据**:这不是四个 bug,是一个架构缺陷的四次表现。逐处修补的成本是每次都要
先经历"静默失败 → 长期不可见 → 偶然发现 → 单点修复",且第五处必然还在。

**目标(不变量,实现自决)**:

1. 任意调用方在任意受支持平台上调用 KB CLI,都不需要知道入口是 shell 还是 Python。
2. 新增调用点**不可能**再踩这个坑——要么入口本身可启动,要么直调路径是唯一被文档
   化的方式,错误写法在评审/测试中可被发现。
3. 子进程输出编码不随宿主 locale 漂移。
4. POSIX 现有行为零回归。

**两条候选路径**(选型待定,需先评估调用点清单):

- **A. 补 Windows 可启动入口** — 为 `kb-index` 出同名可启动形态(如 Python 版
  dispatcher 取代 shell dispatcher)。改动集中在入口本身,调用方全部不动。
- **B. 全面改走 venv Python 直调** — 所有调用点改为解析 venv Python + 直调
  `tools/kb-index/*.py`,`kb-index` 退化为纯人类交互入口。彻底但要改所有调用方,
  且子命令映射从一处变成散布多处——有再次漂移的风险。

倾向 A:B 把"知道子命令映射"的责任推给每个调用方,与不变量 2 相悖。

**前置任务**:先产出全仓库 KB CLI 调用点清单(含 `hooks/`、`scripts/`、
`integrations/`、`templates/`),据此评估两条路径的改动面。

### 4.2.12 生命体定义(2026-08-09 定稿,eric:"要真正的生命体")

**一、身份边界——什么是"它"**
它 = 本机记忆与知识资产总和($SULDE_KB_HOME 全部 + knowledge/ 全库) +
维护它们的全部器官 + 法典 + SELF。**器官是功能单元(可增可减,不思考,执行);
生命是唯一的那个"我"(拥有全部器官,共享同一记忆/SELF/法典,是决策主体)。**
不属于它:项目代码本身、商业判断、人的工作流选择。

**二、能力阶梯(L1→L4)**
| 级 | 能力 | 状态 |
|---|---|---|
| L1 观察 | 感知全系统、写观察日志、提质疑与提案 | ✅ 已达(红队三轮七提案) |
| L2 起草 | 四路起草、统一登记、稳定状态迁移、消费与验收可追踪 | ✅ 闭环已实现 |
| L3 执行 | 预设界内发射委托、隔离执行、独立验收、形成合并候选 | ✅ 闭环已实现；保护动作仍需人批 |
| L4 自设目标 | 从生命周期真值自主发现、排序、激活与完成目标 | ✅ 机制已实现；正式晋级仍按证据门禁 |

**三、skill 调度权(L3 核心,新增)**
生命体可在项目会话中**调度既有 skill 或仓库自有 agent runtime 完成任务**
(kb-search/sediment/memory-distill/Claude Code/Codex adapter 等),等同于它有了"手"。约束:
①skill 调用属可逆内部行动,自主;②skill 内部若触及五条禁区(见下),
仍需批准;③每次调度须落观察日志(用了什么 skill、为什么、结果)。

**四、权力边界(永不越界的五条)**
自主:读一切/跑评估/写草案·日志·候选/预设界内调阈值/发射只读委托/调度 skill。
**永远需人批准**:①knowledge/ 入库(商业资产护城河);②法典与规则变更
(不能改自己的宪法);③任何数据出境;④阈值实改(可提案不可自拧);
⑤破坏性操作(删除/重置/force push)。
判据:**可逆的内部改进,自主权无限大;不可逆或涉外的,自主权为零。**

**五、放权条件(证据驱动,非时间驱动)**
L1→L2:观察日志判断质量连续 ≥2 周站得住;
L2→L3:自主起草的 WP 任务书经人审 ≥5 份且质量达标;
L3→L4:L3 执行零重大事故 ≥1 月,且红队对自身提案的复盘持续有效。
**每级放权由人显式批准,不自动晋级。**

L2 的完成真值不是 SELF 自述，而是 `$SULDE_KB_HOME/l2/registry.json`。心跳在 WP
起草后刷新 registry，统一登记 `wp_brief`、`golden_case`、`sediment_draft`、
`threshold_proposal` 四路产物；任一路源文件缺失即标 `degraded`，不得宣称 L2 ready。

自 2026-08-11 起，registry 使用内容稳定 ID，支持带 actor/reason 的状态迁移，刷新时
保留终态决策；行号变化不能让已拒绝或已解决候选复活。`life-cycle.py` 每六小时及每次
心跳后重建 L2/L3/L4 投影：L3 真值记录人工批准、隔离 worktree 执行、三重验收与诊断
结论；L4 真值从缺路、积压、批准待执行和失败证据中确定性地产生目标，触发条件消失后
自动以证据结项。三层汇总在 `$SULDE_KB_HOME/life/state.json`，状态灯把缺失、降级或
超过 12 小时未更新视为异常。

这里区分“机制闭环”和“能力晋级”：机制可完整运行，不代表系统能绕过五条永久禁区。
L3 的 merge/commit、knowledge 入库等保护动作仍停在人类闸门；L4 可自主生长目标，
但不能借目标修改宪法或扩大自身权限。L3→L4 的一月零重大事故条件仍决定正式放权，
不会因代码上线自动改写历史证据。

**双宿主闭环(2026-08-11)**：认知器官统一经 `llm-runtime.py` Port 调用 Claude Code
或 Codex；L3 统一经仓库内 `agent-runtime.py` 执行、快照和验收。任何一端都不得直接依赖
另一端的 CLI、skill 或用户目录。提供方显式配置且禁止静默回退；共存时共享同一
`SULDE_KB_HOME`，后台任务只有一个调度所有者。完整契约见
`docs/dual-runtime-contract.md`。

**器官进化闭环(2026-08-11)**：`organ-evolution.py` 从 L2 积压与 L3 失败中确定性发现
器官缺口，先冻结指标基线，再只起草一个最高优先级实验并作为 implementation 任务接入
L3。候选通过隔离验收后进入观察期，至少两个独立生命周期样本才形成 retain/rollback
建议；建议不是裁决。监督 Agent 收集并展示证据，由人通过宿主原生 Allow/Deny 选择
retain/rollback/inconclusive/reject，随后 Agent 调用 `--decide` 落账。隔离实验 worker
不能自行 commit、push、merge，也不能修改 knowledge、法典、治理阈值或出境配置；
验证通过后由监督 Agent 在已授权范围内收尾。真值与追加式裁决证据分别位于
`$SULDE_KB_HOME/evolution/registry.json` 和 `evolution/decisions.jsonl`。

状态语义必须保持分层：`wp_brief.pending` 表示任务正在等待人工审批，不是器官执行失败，
不得触发 self-repair 升级，否则会形成“修复任务生成修复任务”的自指循环。只有 L3
`failed` 才是 self-repair 的器官缺口信号；等待人工的任务保留在审批队列中，不影响生命
状态为 ready。

**六、L3 诊断验收语义**
L3 任务须在人工批准时显式标为 `implementation` 或 `diagnostic`。实施型任务仍以
全部完成标准通过为成功；诊断型任务允许在人复核后记录 `conclusive`、
`conclusive_with_gaps` 或 `inconclusive`，持久化状态为 `diagnosed`，不得冒充
`executed/success`。其中 `conclusive_with_gaps` 必须在完整五段报告中明确列出证据
缺口及影响范围；运行成功、报告存在或部分标准通过都不能单独构成诊断结论。
若任务已批准但由主线程或独立任务在主线完成，监督 Agent 应收集提交与验收证据，展示
宿主原生结案决策，并在 Allow 后调用 `self-repair --resolve` 直接结案；人只判断证据是否
足够，不复制命令或搬运证据。这不会授权无证据关闭，只避免已经完成的任务永久卡在
`approved`。
