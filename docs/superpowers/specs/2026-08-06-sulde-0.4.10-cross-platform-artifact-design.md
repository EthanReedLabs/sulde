# Sulde 0.4.10 跨平台产物与知识清单设计

状态：待用户审阅
日期：2026-08-06
范围：Claude Code 插件、Codex 适配器、KB 构建链路、P1/P2 测试与 CI
发布约束：本轮只允许本地提交，不推送远端

## 1. 背景

0.4.9 已修复安装包目录没有 `.git` 时 KB 无法发现文档的问题，并补齐 Windows 原生 venv 的 `Scripts/python.exe` 解析。当前验证仍暴露出三类系统性差异：

1. 源码仓、插件缓存和最终安装产物不是同一种运行环境，依赖 Git 自动发现会造成发布包与源码行为不一致。
2. Windows 的默认文本编码可能是 GBK；即使 JSON 使用 `ensure_ascii=False`，父子进程的文本流仍可能在非 ASCII 内容上失败。
3. Windows/NTFS 不表达 POSIX 可执行位，直接用 `stat().st_mode` 验证脚本权限会产生假失败。

此外，Codex 适配器当前包含 Mac 绝对路径，说明它仍是“指向开发机源码的薄适配器”，而不是可独立安装、可验证的发布产物。

本设计把这些问题统一为一个发布工程问题：**以真实安装产物为测试对象，用确定性机器清单描述知识语料，把平台差异放在明确的边界适配层中。**

## 2. 目标与非目标

### 2.1 目标

- Claude Code 和 Codex 的安装产物都不依赖 `.git`、开发机绝对路径或特定用户目录。
- KB 语料拥有唯一、确定、可校验的机器清单。
- 源码、发布包、SQLite 索引、索引保鲜和状态检查使用同一个语料摘要语义。
- Hook JSON 边界显式使用 UTF-8，不依赖 Windows 当前代码页。
- 可执行权限分别按 Git、POSIX 产物、Windows 启动语义验证。
- CI 同时保留 Linux 完整质量闸门，并增加轻量 Windows 原生 smoke job。
- 0.4.10 可从 0.4.9 平滑迁移，保留一轮旧安装包兼容路径。

### 2.2 非目标

- 不更换 SQLite、FastEmbed 或现有混合检索实现。
- 不修改记忆同步仓、密钥格式和加密协议。
- 不要求 Windows/NTFS 模拟 POSIX mode bits。
- 不在本轮引入容器化发布系统或重写所有 shell 脚本。
- 不在本轮推送、创建远端 release 或发布 marketplace 版本。

## 3. 备选方案

### 方案 A：只修 P1/P2 测试

在 Windows 上设置 UTF-8 环境变量，并跳过执行位断言。改动最小，但仍然测试源码仓而非安装产物，也无法解决 Codex 绝对路径和 KB 发布内容漂移。

### 方案 B：只增加 KB 清单

增加知识语料 manifest，并让无 `.git` 构建读取它。能解决 KB 发现问题，但打包拓扑、Codex 自包含性、脚本权限和真实产物 smoke 仍然是分散问题。

### 方案 C：产物优先、清单驱动、原生平台矩阵（选定）

生成确定性 KB 清单，构建 Claude/Codex 两种 staged artifact，再让测试从 artifact 入口运行。Linux 验证完整语义质量，Windows 验证编码、路径、venv 布局和脚本启动语义。

该方案复用当前索引核心，只增加发布层和平台契约，长期维护成本最低。

## 4. 总体架构

```text
Git 跟踪的 knowledge/*.md
        │
        ▼
确定性语料发现与清单生成
        │
        ├── knowledge/MANIFEST.json
        └── knowledge/INDEX.md（人类可读目录）
        │
        ▼
Claude artifact / Codex artifact staging
        │
        ▼
bootstrap.sh / kb-index build
        │
        ▼
SQLite manifest(path, sha256) + meta.corpus_fingerprint
        │
        ├── SessionStart freshness
        └── sulde-status
```

其中有两个不同含义的 manifest：

- `knowledge/MANIFEST.json` 是**发布语料合同**，回答“官方产物应包含哪些知识文档”。
- SQLite `manifest` 表是**本地索引状态**，回答“当前数据库已经索引了哪些内容”。

两者不能合并，但必须使用相同的路径和 SHA-256 规则。

## 5. 知识语料清单

### 5.1 文件格式

新增 `knowledge/MANIFEST.json`，建议结构：

```json
{
  "schema_version": 1,
  "documents": [
    {
      "path": "knowledge/anti-patterns/example.md",
      "sha256": "<64 lowercase hex>"
    }
  ],
  "document_count": 291,
  "corpus_sha256": "<64 lowercase hex>"
}
```

约束：

- 文档按 POSIX 风格相对路径排序。
- 路径统一为 Unicode NFC，并拒绝经过 Unicode 归一化或不区分大小写后发生碰撞的两个条目，避免 macOS/Windows checkout 指向不同文件。
- 不写入生成时间、机器名或绝对路径，保证重复生成字节稳定。
- 文档摘要基于规范化内容：UTF-8 解码后把 CRLF/CR 统一为 LF，再编码为 UTF-8。不能直接散列 checkout 原始字节，否则 Windows `core.autocrlf` 会让同一个 Git 文档得到不同摘要。
- `corpus_sha256` 对规范化的 `path + NUL + sha256 + LF` 序列计算，而不是对 JSON 排版计算。
- 清单自身不是 Markdown，不进入 KB 语料。

### 5.2 唯一发现规则

源码模式继续以 Git 跟踪文件为真源，并复用 `tools/kb-index/common.py` 中现有容器白名单、排除文件和 Markdown 过滤规则。清单生成器不得维护第二份过滤列表。

运行模式按以下优先级发现文档：

1. 清单存在：读取清单路径，并验证文件存在、路径未越界、SHA-256 匹配。
2. 清单不存在且存在 `.git`：使用现有 Git 发现，支持开发分支和旧 checkout。
3. 清单与 `.git` 均不存在：0.4.10 暂时保留 0.4.9 文件系统 fallback，并输出一次兼容性提示；官方 staged artifact 测试必须拒绝缺少清单的产物。

计划在后续主版本移除第 3 条静默兼容路径。

### 5.3 INDEX 与 fingerprint

`knowledge/INDEX.md` 保持人类可读目录职责，并继续支持 `--check`。机器完整性不再依赖 INDEX 内容。

`tools/kb-index/build.py` 把清单的 `corpus_sha256` 写入 SQLite `meta.corpus_fingerprint`。`kb_freshness.py` 和 `sulde-status.py` 比较同一个值，而不是分别对 `INDEX.md` 再做 SHA-256。

清单读取和校验实现放在 KB 公共层。SessionStart 为避免加载嵌入依赖，可以保留一个仅使用标准库的轻量读取入口，但必须通过单元测试证明它与公共层返回相同 fingerprint。

## 6. 安装产物拓扑

### 6.1 Claude Code

Claude artifact 继续以仓库插件根为布局基础，但测试和安装使用 staging 目录而不是工作树。staging 明确排除 `.git`、本地 worktree、缓存、数据库和密钥，只复制发布所需文件。

测试必须从 staged root 运行：

- manifest 完整性检查；
- `bootstrap.sh`；
- `kb-index build/search` smoke；
- hooks P1；
- 模板与权限 P2。

### 6.2 Codex

Codex artifact 必须自包含，不能继续使用 `/Users/...` 等开发机绝对路径。构建阶段把共享运行载荷放入 Codex staged plugin，至少包含：

- `CANON.md`；
- `hooks/` 所需入口与库；
- `knowledge/` 和机器清单；
- `scripts/kb/`；
- `tools/kb-index/`；
- 所需依赖声明。

Codex 的 `session-start.py` 与 `user-prompt-submit.py` 从 `${PLUGIN_ROOT}` 相对定位共享载荷。允许提供显式测试/开发覆盖变量，但正式产物不依赖外部 Claude 插件缓存，也不搜索用户磁盘猜测路径。

Codex hook 不能假设所有平台都有同名的 `python3` 命令。staging 显式生成 POSIX 与 Windows 启动变体：共享 Python 载荷完全相同，POSIX launcher 解析 `python3`/`python`，Windows launcher 解析 `python.exe`/`py -3`，对应的 `hooks.json` 只调用本平台 launcher。平台选择由构建目标决定，不在会话启动时猜测。

Claude 和 Codex artifact 来源相同，但 staging 目标不同；不能通过手工复制两份知识目录维护。

## 7. UTF-8 进程协议

所有通过 stdin/stdout 交换 hook JSON 的入口遵守统一协议：

- 输入输出编码固定为 UTF-8。
- JSON 使用 `ensure_ascii=False`，保留中文语义。
- Python 入口在支持时对 `sys.stdin`、`sys.stdout`、`sys.stderr` 执行 UTF-8 `reconfigure`。
- 所有 `subprocess.run(..., text=True)` 调用显式传入 `encoding="utf-8"` 和确定的错误策略。
- 启动器和 CI 设置 `PYTHONUTF8=1`、`PYTHONIOENCODING=utf-8` 作为防御层，但业务正确性不能只依赖调用者设置环境变量。
- 机器可解析 JSON 只写 stdout；诊断写 stderr，避免污染协议帧。

`p1_hook_dryrun.py` 使用包含中文和 emoji 的 payload 覆盖父子进程边界，并在 Windows 原生 Python 下运行。另加一个非 UTF-8 默认环境回归用例，证明入口会主动收敛到 UTF-8。

## 8. 权限和脚本可执行性

“脚本可执行”拆为三种事实：

1. **Git 真源**：对要求可执行的脚本，用 `git ls-files --stage` 验证 mode 为 `100755`。
2. **POSIX artifact**：在 Linux/macOS staged artifact 上验证 user executable bit，并直接执行入口 smoke。
3. **Windows runtime**：不检查 `st_mode`；用 Git Bash 执行 `bash -n` 和入口 smoke，证明脚本可被明确解释器启动。

staging 工具读取 Git mode，并在 POSIX 目标上恢复执行位。在 Windows 上保留逻辑 executable 元数据，但不尝试让 NTFS 表达 POSIX 权限。

`p2_template_dryrun.py` 仍验证模板内容与清单，但平台相关权限断言按上述规则分流，不使用无条件 `Path.stat().st_mode`。

## 9. CI 设计

### 9.1 Linux 完整质量闸门

保留现有 `kb-quality.yml` 的 Ubuntu job，并增加：

- 检查 `knowledge/MANIFEST.json` 和 `knowledge/INDEX.md` 均为最新；
- 构建 Claude/Codex staged artifact；
- 在移除 `.git` 的 staged artifact 中运行 manifest 验证；
- 验证 Git mode 和 POSIX artifact mode；
- 运行现有单元测试、完整 bootstrap 和 golden evaluation。

### 9.2 Windows 轻量 smoke

新增 `windows-latest` job，目标控制在约 3 分钟，不下载真实嵌入模型：

- 使用 Windows 原生 Python；
- 使用 runner 自带 Git Bash；
- 构建两个 staged artifact；
- 运行 P1 UTF-8 hook dry-run；
- 运行 P2 Windows 分支；
- 运行 manifest/no-`.git` 单元测试；
- 迁入旧 worktree 的 Windows bootstrap 回归，用预置 marker/fake modules 验证 `Scripts/python.exe`；
- 对 shell 入口执行 `bash -n` 和最小启动 smoke。

模型下载和完整向量质量继续只在 Linux job 执行，避免 Windows job 变慢或受外部下载波动影响。

## 10. 错误处理与安全边界

- manifest JSON 无效、路径绝对化、包含 `..`、文件缺失或 SHA 不匹配时，官方 artifact 验证立即失败，并指出第一个错误路径。
- manifest 拒绝 Unicode/大小写可移植性碰撞、Windows 保留文件名以及以空格或句点结尾的路径组件。
- staging 只接受仓库内的规范化相对路径；拒绝符号链接逃逸目标根目录。
- 不打包 `SULDE_KB_HOME` 数据、`memory.db`、`mem-sync.key`、同步仓或日志。
- bootstrap 继续把可重建索引写到用户数据目录，不写插件缓存。
- 索引仍通过临时数据库和 `os.replace` 原子替换，失败不破坏最后一个可用数据库。
- freshness 后台构建继续使用锁和 stale-while-revalidate；清单错误时记录诊断，不进入重复重建循环。

## 11. 测试层次

### T0：纯函数与清单

- 路径排序和规范化；
- CRLF/LF 内容摘要一致性；
- Unicode NFC 与大小写碰撞拒绝；
- corpus fingerprint 稳定性；
- manifest schema、缺文件、hash mismatch、路径逃逸；
- 有/无 `.git` 的发现优先级；
- freshness/status fingerprint 一致性。

### T1：源码与适配器

- P1 hooks JSON 协议；
- P2 模板和 Git mode；
- Claude/Codex 相对路径定位；
- Codex adapter 不包含开发机绝对路径。

### T1.5：真实 staged artifact

- 两个产物均不含 `.git`；
- manifest 文件数和 SHA 全部匹配；
- bootstrap/build/status 从 staged root 工作；
- Windows Git Bash 和 POSIX direct execution 分别通过。

### T2：语义质量

- 现有 `kb-golden-eval.py --min-rate 0.8`；
- 文档数、chunks 和边数保持在预期范围；
- 只在需要模型的 Linux 完整 job 执行。

## 13. 验收标准

- 在没有 `.git` 的 Claude staged artifact 中，bootstrap 最终输出 `build complete`，文档数与清单一致。
- Codex staged artifact 在 Windows 和 macOS/Linux 上都不依赖源码绝对路径。
- `p1_hook_dryrun.py` 在 Windows 默认环境中 13/13 通过，并覆盖中文/emoji JSON。
- `p2_template_dryrun.py` 在 Windows 不再因 NTFS mode bits 产生假失败；Linux 仍严格验证 `100755` 与 artifact executable bit。
- Windows bootstrap 回归确认使用 `venv/Scripts/python.exe`。
- `kb_freshness.py`、`sulde-status.py` 与 SQLite meta 对同一语料给出相同 fingerprint。
- Linux 完整质量闸门与 Windows 轻量 smoke 均通过。
- staged artifact 不包含密钥、用户数据、绝对开发机路径或 `.git`。
- 所有改动仅本地提交，未推送远端。
