## 交付边界

- POSIX 六个 Hook 使用固定的缓存外入口；最小不可变包和入口摘要绑定，正常
  调用继续进入原 Guardian，不新增决策权。完成帧只证明入口执行完成，不是 Allow。
- 安装器在 registry 修改前准备入口；发布置于最终安装准入检查之后，入口
  纳入原事务快照与恢复。候选失败不删除可能仍在使用的旧不可变包。
- legacy / 覆盖未知的缓存命令不得冒充已迁移；首次迁移在生产变更前拒绝。
  fresh 安装与具有可核验 stable lineage 的后续升级是本轮可验证路径。
- 缓存外入口保留现有故障恢复路由：仅验证现役 runtime / adapter 身份后复用
  原恢复授权链；不能把坏 launcher 的健康状态设成修复它自身的前置条件。
- Windows 和真实宿主的旧会话迁移尚未验收；隔离测试不等于生产安装或宿主
  trust 验收。当前生产版本、dev、main 均不在本轮修改范围。

## 旧缺陷与候选缺陷分开登记

旧缺陷：缓存绝对路径被宿主移除后，尚未启动的 Hook 已无入口；预持有 FD
只能保护已启动进程，不能覆盖此情形。新固定入口解决其后续 stable 注册路径，
不能反向改写旧会话内存中已经冻结的命令。

候选集成中发现的问题（不是 dev 历史缺陷）：

1. 空入口退出零被当成完成——新增完成帧并验证六事件注册精确形状。
2. 假设 registry 存在 installedPath——改读实际 CLI 的结构化 source/version，
   unknown 与空 registry 分离，残留部署证据不能当 fresh。
3. 入口发布早于最终切换准入——后移发布，拒绝路径保持原入口。
4. 新 loader 重渲染旧 bootstrap 会拒绝跨源码升级——按旧密封身份验证。
5. 稳定包脱离原 cache 目录后丢失已有恢复路由——复用经过身份验证的原路由。
6. 解析 Python 别名改变了恢复预览的精确 argv——保留经校验的原调用路径和
   真实目标摘要；不放宽原审批对精确命令的绑定。

第 4、5 项及 Python 隔离修正已有下节实测证据，不仅依赖代码解释。
解释器别名造成的探针失败单独作为夹具问题，不作产品反例。
需要区分两件事：探针没有选择与旧链一致的 Python 是夹具错误；在同解释器
旧链成立后，新入口改写原调用路径使密封命令不匹配则是候选兼容性缺陷。
