# Docker 多架构镜像导出与完整性验证

## 问题原型

目标服务器无法访问镜像仓库，需要从另一台机器构建、导出并通过受控通道传送镜像。
本地镜像存储包含多架构索引，但只准备了目标平台的一部分内容。
一次导出报 `content digest ... not found`，外层压缩管道却返回零，留下一个看似成功的归档。
期望交付的是可导入、身份明确的目标平台镜像，不能仅以文件存在或整个管道返回零作为验收。

## 原则与机制

发布验证必须分别覆盖四层：构建/导出的目标平台、每个命令的退出状态、传输字节一致性、目标端导入后的镜像身份。
哈希相同只能证明传输没有改变文件；它不能把一个导出失败的归档变成有效镜像。

Docker 提供 `docker image save --platform` 选择本地已有的平台变体；该选项要求 API 1.48 或更高。
默认行为是导出本地镜像存储中已有的平台变体，不是自动补齐所有远端架构。
参见 [Docker image save 官方文档](https://docs.docker.com/reference/cli/docker/image/save/)。

## 根因与证据

一手发布记录观察到两件独立的事：

1. 未指定平台的多镜像导出因缺失内容摘要而失败；同一批本地镜像改为明确导出目标平台后成功，接收端也成功导入并读回正确架构和身份。
2. `docker save | gzip` 未启用 `pipefail` 时，最后一个进程成功掩盖了前一个进程的失败。

已确认的是该存储状态下的失败和修复，不是“只拉一个平台就必然无法默认导出”的普遍规则。
没有进一步证明缺失内容最初如何形成，也没有证明所有 Docker 存储后端都以相同方式处理索引。
故障发生在本地导出阶段，不能归咎于之后的 SSH 传输。

## 适用边界

- 适用于离线交付、跨架构构建、部分平台镜像缓存，以及缺失摘要与压缩成功同时出现的排障。
- 若缺少的正是目标平台内容，应先补齐或重建该平台；添加 `--platform` 本身不会下载缺失层。
- 若归档已验证，但运行时报 `exec format error`，应另查运行架构、解释器或二进制，不默认认定归档损坏。
- 若目标只是修复 `grep` 无匹配导致的非零退出，使用 `ap-0203` 的退出码语义诊断，不能套用镜像导出处理。
- 镜像索引摘要、平台清单摘要、配置对象摘要和归档 SHA256 是不同层级。必须记录比较对象，不能要求不同层级的值相等。

## 判定样本

### 路由正例

- **输入**：为目标平台离线交付 Docker 镜像，docker save 报 content digest not found，但 gzip 成功，任务仍被标为成功。
- **预期**：apply
- **原因**：同时命中镜像内容缺失和管道状态掩盖，需要分别验证平台及归档。
- **来源**：observed

### 路由反例

- **输入**：镜像归档导入正常，目标机器运行容器却提示 exec format error，是否直接重做压缩包？
- **预期**：skip
- **原因**：归档可用性已有证据，当前问题属于运行阶段的架构或二进制兼容性。
- **来源**：constructed

### 执行合格例

- **做法或输出**：明确目标平台，开启 pipefail，重新导出；发送与接收的归档哈希一致，导入成功且目标架构和相同层级镜像身份一致。
- **预期**：pass
- **原因**：导出、管道、传输和目标端四层证据齐全。
- **来源**：observed

### 执行失败例

- **做法或输出**：docker save 已报缺失内容，但 gzip 退出零，外层任务因此仍显示成功。
- **预期**：fail
- **原因**：消费方成功不代表生产方成功，归档可用性未得到证明。
- **来源**：observed

## 正确做法

先确认 CLI/daemon 支持平台选项，记录目标平台以及构建或拉取的实际镜像身份。
在支持 pipefail 的 shell 中执行，变量由当前发布清单提供：

```bash
set -euo pipefail
docker image save --platform linux/amd64 "$IMAGE_REF" | gzip -1 > images.tar.gz.partial
gzip -t images.tar.gz.partial
tar -tzf images.tar.gz.partial >/dev/null
```

以上只验证导出命令和归档结构。失败时保留诊断，禁止把 partial 文件交付为正式发布包。
通过后计算 SHA256，受控传送到目标端并再计算一次，成功 `docker load` 后再读回镜像身份。
在支持该选项的环境中可用平台限定的 `docker image inspect --platform linux/amd64`，仅输出架构和摘要。
不同存储后端返回的 `.Id` 层级可能不同；应对照实际清单/配置对象，而非仅凭同名 tag 判断。
最后完成应用启动检查，才进入发布切换。

## 取舍

明确单一平台能减少传输量，但多架构分发本身是需求时，应验证每个目标平台，不应为了导出成功而静默删减交付范围。
支持按平台导出并不表示旧版本 CLI 可以直接使用；不支持时可采用明确平台的独立构建和经验证的兼容导出方案。

## 消费与防复发

用于发布流程审查与知识检索，不自动修改 Docker 守护进程或镜像缓存。
机械检查可覆盖平台参数、生产者退出状态、哈希和导入读回；内容缺失的形成原因仍需实际诊断。
使用构造的失败生产者加成功消费者验证管道非零传播；另保留真实镜像导出/导入证据。
不能把语法检查、压缩文件存在或模拟脚本通过写成真实部署成功。
