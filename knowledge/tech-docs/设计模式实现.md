# 设计模式实现(GoF + 现代模式 × iOS Swift / Android Kotlin)

> 宏观层:如何组织对象间关系,让代码可扩展、解耦、可测试。
> 微观语法层见 `编码原则集.md`(Kotlin / Swift 习语优先级)。
> 跨平台共享编码基线。

---

## 何时用模式 / 何时不用(决策原则)

**用模式的前提**:
- 已经有 ≥ 2 处类似代码 → 抽象有意义
- 未来扩展概率高(新增策略 / 状态 / 数据源) → 用模式预留扩展点
- 代码可测试性提升(替换实现 / mock)

**不用模式的反例**:
- 一次性代码:用模式 = 过度工程
- 团队不熟模式:加深理解成本 > 抽象收益
- 为了"未来扩展"留 fallback / 占位 → Dev 走 fallback,等于没抽(参见反模式:禁 fallback)

**判定线**:抽象代码量 < 业务代码量 = 抽象合理;抽象代码量 ≥ 业务代码量 = 过度工程。

## GoF 23 — 高频使用 10 种 × 双平台实现

| # | 模式 | 用途 | iOS Swift 最佳实现 | Android Kotlin 最佳实现 | 反例 |
|---|---|---|---|---|---|
| 1 | **Strategy** | 算法 / 行为 runtime 切换 | `closure: (Input) -> Output` 或 `enum + assoc` | 高阶函数 `(Input) -> Output` 或 `sealed class` | if-else / when 字符串判断 |
| 2 | **Observer** | 状态变化通知 | Combine `@Published` / `@Observable`(iOS 17+) | `StateFlow` / `SharedFlow` + `collect` | NotificationCenter / LiveData 字符串 key 散落 |
| 3 | **Factory Method** | 创建对象时延迟决定具体类 | `static func make(...) -> Self`(struct factory) 或 `enum + static func` | `companion object` `fun create(...)` 或 sealed class + when | `if (type == "A") A() else B()` 散落各处 |
| 4 | **Adapter** | 接口转换(老 API 适配新接口) | protocol + struct 适配器 / protocol extension | `interface` + adapter class / extension fn | 直接修改第三方代码或包了 N 层 |
| 5 | **Decorator** | 动态增强对象功能 | protocol + struct + composition | `interface` + delegation `by` 关键字 | 多层继承导致钻石问题 |
| 6 | **Singleton**(慎用) | 全局唯一实例 | TCA `@Dependency`(可 mock)| DI 容器 `single { }` module | `class { static let shared = Singleton() }` 不可 mock |
| 7 | **Template Method** | 步骤固定,子类填具体实现 | protocol with default impl + extension | `abstract class` + `open fun` | 复制粘贴步骤代码到多个子类 |
| 8 | **State** | 对象行为随状态变 | `enum + associated values` 全部状态枚举 | `sealed class` 状态机 | if-else 散落判断当前状态 |
| 9 | **Builder** | 复杂对象逐步构造 | Result builder(SwiftUI ViewBuilder / RegexBuilder)/ static func chain | Kotlin DSL(`@DslMarker` + lambda receiver,例 `buildList { } / NavGraphBuilder` / Compose `@Composable`)/ 顶层 `fun xxxBuilder(block: ...)` | 构造器 10+ 参数(参数地狱);误把 `apply { } / with { }` 当 DSL(那是 scope functions) |
| 10 | **Command** | 操作封装为对象,可撤销 / 队列 | `struct Command` + `execute()` / Action(TCA) | `sealed class Action` + `interface Handler` | UI 直调业务逻辑,无法记录 / 重放 |

## 现代模式(架构常用)

| # | 模式 | 用途 | iOS Swift | Android Kotlin |
|---|---|---|---|---|
| 11 | **Repository** | 数据访问统一抽象(网络 / 本地 / 缓存) | `protocol XxxRepository` + struct impl + URLSession + Codable | `interface XxxRepository` + class impl + Retrofit + serialization |
| 12 | **MVI**(架构) | 单向数据流 — Intent → Reducer → State | (用 TCA 替代) | `MviStore<State, UserIntent, ResultIntent>` + `reduceUser` + `reduceResult`(自定义)|
| 13 | **TCA**(架构,iOS) | Reducer + Effect 函数式状态管理 | `Reducer` + `Effect` + `@Dependency` + `Store` | (用 MVI 替代) |
| 14 | **Coordinator**(导航) | 解耦 View 和 navigation 决策 | `Coordinator` 协议 / `AppRouter` | `AppRouter` interface + impl |
| 15 | **DSL**(配置) | 声明式 API | Result builder(SwiftUI / RegexBuilder) | Kotlin DSL(`@DslMarker` + lambda receiver) |
| 16 | **Higher-Order Function** | 行为参数化 | `func filter(_ predicate: (T) -> Bool)` | `fun filter(predicate: (T) -> Boolean)` |
| 17 | **DI**(依赖注入) | 解耦实现切换(prod / test / mock) | TCA `@Dependency` + `DependencyValues` | DI 容器 `module { single { ... } }` |
| 18 | **Pub-Sub**(发布订阅) | 多对多解耦通信 | Combine `PassthroughSubject` / `@Published` | `SharedFlow` + `collect` |
| 19 | **Pipeline**(数据流处理) | 多步数据变换 | Combine operator chain / `AsyncSequence.map.filter` | `Flow.map.filter.distinctUntilChanged` |
| 20 | **Lens / Optic**(嵌套数据更新) | 深层嵌套 state 更新不破坏 immutability | `WritableKeyPath` / `inout` | `data class.copy(field = ...)` chained |

## 模式选择决策树

```
我要做什么?
│
├── 数据访问(网络 / 本地 / 缓存)
│   └─→ Repository(#11)
│
├── 算法/行为切换(支付方式 / 排序方式 / 渲染方式)
│   └─→ Strategy(#1) — 用 closure / sealed class
│
├── 状态变化通知(UI 跟数据走)
│   └─→ Observer(#2)— Combine / StateFlow
│
├── 复杂状态机(订单状态 / 上传状态)
│   └─→ State(#8)— enum / sealed class 全枚举
│
├── 创建对象时多种类型
│   └─→ Factory Method(#3)— static func / companion fun
│
├── 复杂对象构造(配置 / DSL)
│   └─→ Builder(#9)— Result builder / Kotlin DSL
│
├── 解耦实现(测试 mock)
│   └─→ DI(#17)— TCA @Dependency / DI 容器
│
├── UI 状态管理
│   ├─ iOS:TCA(#13)Reducer + Effect
│   └─ Android:MVI(#12)Store + reduceUser/Result
│
├── 跨页面 navigation
│   └─→ Coordinator(#14)— AppRouter
│
└── 多步数据变换(用户操作 → 网络请求 → 解析 → UI)
    └─→ Pipeline(#19)— Combine / Flow operator
```

## 跨平台思维:模式相同,实现不同

**同一个模式在两端的最佳实现往往用不同语法 / 习语**(对应 `编码原则集.md`):

例 1:**Strategy 模式 × 函数式实现**

```swift
// iOS Swift — 用 closure(最少代码)
struct PaymentService {
    let process: (Amount) async throws -> Receipt
    static let stripe = PaymentService(process: { /* ... */ })
    static let paypal = PaymentService(process: { /* ... */ })
}
```

```kotlin
// Android Kotlin — 用 sealed class(类型安全)
sealed class PaymentMethod {
    abstract suspend fun process(amount: Amount): Receipt
    data object Stripe : PaymentMethod() { override suspend fun process(amount: Amount) = /* ... */ }
    data object Paypal : PaymentMethod() { override suspend fun process(amount: Amount) = /* ... */ }
}
```

例 2:**Observer 模式 × 数据流实现**

```swift
// iOS — Combine @Observable(iOS 17+)
@Observable
class CartModel {
    var items: [Item] = []
    var total: Double { items.reduce(0) { $0 + $1.price } }
}
```

```kotlin
// Android — StateFlow(协程)
class CartViewModel : ViewModel() {
    private val _items = MutableStateFlow<List<Item>>(emptyList())
    val items: StateFlow<List<Item>> = _items.asStateFlow()
    val total: StateFlow<Double> = items.map { it.sumOf { i -> i.price } }
        .stateIn(viewModelScope, SharingStarted.Eagerly, 0.0)
}
```

## 实际应用举例(通用占位)

| 场景 | 用模式 | 落地位置(示意) |
|---|---|---|
| 某服务 Mock / 真实切换(双值依赖) | Strategy + DI | iOS:`Spec` 层定义协议 + Adapter 实现 + TCA `@Dependency` `liveValue` / `testValue` 切换<br>Android:`core-spec` 定义 interface + Adapter 实现(DI module 切换) |
| 某向导流多 stage 流转 | State + TCA Reducer | `<某 Feature>.State` + `<某 View>.stageContent` |
| 某列表加载(网络 / 缓存 / 失败) | Repository + Pipeline | `<某 Store>` + `<某 Command>.Fetch` |
| 跳转新页面 | Coordinator | `AppRouter.swift` / `AppRouter.kt` |
| 某输入区跨创作流复用 | Adapter + ViewBuilder | `<某 View>.swift`(iOS)+ `<某 Binder>.kt`(Android) |
| 某模板卡片状态(默认 / 选中 / 锁定) | State | 选中 overlay 显隐 + selector 切换 |

## 反模式(GoF 误用)

| 反模式 | 现象 | 正解 |
|---|---|---|
| **God Object** | 一个 class 1000+ 行,什么都管 | 按职责拆 + 各自 Repository / UseCase / Reducer |
| **Anemic Domain Model** | data class 只有字段没行为 | iOS:加 method 到 struct;Kotlin:加 extension fn |
| **Singleton 滥用** | 处处 `Object.shared.x` 不可 mock | TCA `@Dependency` / DI 容器 module |
| **Premature Abstraction** | 一次性代码就抽 protocol / interface | 等出现 ≥ 2 处再抽 |
| **过深继承** | A → B → C → D class 链 | composition over inheritance(组合优于继承) |
| **Service Locator 反模式** | 全局 `ServiceRegistry.get<X>()` 隐式依赖 | 显式构造注入 |

> **本表 vs 反模式集合**:本表是 **GoF 通用误用集**(代码结构层抽象问题,跨项目通用)。反模式集合是 **项目实际踩坑**(具体实例)。
> 两者互补:**写代码前看本表(主动避坑),改代码踩坑后看反模式集合(被动沉淀)**。
