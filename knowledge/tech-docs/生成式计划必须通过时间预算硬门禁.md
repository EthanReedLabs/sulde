# 生成式计划必须通过时间预算硬门禁

## 问题

仅在 prompt 中要求模型遵守频次和时长，并不能保证输出可执行。模型仍可能生成训练日过多、单日动作过多或休息时间导致总时长超限的计划。如果直接持久化，用户资料与实际处方会形成冲突。

## 协作约束

生成式计划应使用同一份结构化预算贯穿两层：

1. Prompt 层明确告诉模型每周训练日数量和单次可用分钟数。
2. 保存层使用确定性代码重新计算并校验，失败输出不得入库，应进入重试或明确降级流程。

## 校验模型

- 周频次按非休息日数量精确校验，而不是模糊的建议区间。
- 单日时长估算至少包含准备时间、动作切换、每组执行时间和处方休息。
- 预算对象本身应限定合理范围，避免无效资料进入生成链路。
- 用户已有明确预算时，不再拼接可能冲突的通用建议。
- 手动修改计划需要独立的超预算确认语义，不能默认套用生成阶段的静默拒绝。

## 验收

- 频次超限和不足都必须被拒绝。
- 任一训练日估算超时必须被拒绝。
- 合规输出仍能正常解析和持久化。
- Android、iOS 编译和共享测试同时通过。

## 结论

Prompt 约束负责提高首次生成命中率，确定性 validator 才是数据正确性的最终边界。涉及时间、剂量、金额、权限等可执行约束时都应采用同样结构。
