# 性能专项技术决策(全屏视频类 App 通用方法论)

> 适用于"全屏视频消费 + 多任务生成 + 大文件上传"类移动 App。
> 记录若干性能专项的技术决策与依据,作为同类决策的参考骨架。
> 每个决策的价值不在于具体数值,而在于**用什么标准权衡体验提升 vs 资源成本**。

---

## 一、全屏视频播放器池管理

### 决策:固定 3 个 Player,全设备统一,不做分档

### 依据

5 个 Player 相比 3 个的体验提升是切换延迟从偶尔 300ms 变成 200ms,用户几乎感知不到。但内存从约 300MB 涨到 500MB,低端设备(3GB RAM)直接 OOM。

维护两套策略(高端 5 / 低端 3)增加的代码分支和测试矩阵不值得这点体验差异。主流竖滑视频 App 在所有设备上也是类似的 3 Player 池策略。

### 具体规则

- 同时维持 3 个 Player 实例:当前 + 上 1 条 + 下 1 条
- 用户滑到新视频时,回收最远的 Player,通过切换数据源复用给新位置
- 不销毁再创建 Player,而是复用实例切换 MediaSource / AVPlayerItem
- 当前视频自动播放,上下两条只 prepare()(下载 + 解码前几帧),不播放

### 性能目标

- 切换到画面可见:≤300ms
- 连续快速滑动 50 条不崩溃
- 内存峰值 ≤400MB(3 Player + 图片缓存)
- 帧率 ≥55fps

## 二、视频预加载与网络策略

### 决策 1:首版不做视频磁盘缓存

### 依据

快速消费型短视频(单个十几 MB 到几十 MB),竖滑场景用户快速滑过的视频大概率不会回看,磁盘缓存命中率低。

做磁盘 LRU 缓存需要管理缓存大小上限、淘汰策略、存储空间检测、缓存清理 UI,工程量不小,首版收益不够。v2 根据用户行为数据(回看率、二次浏览率)再决定是否加。

### 决策 2:预加载 = prepare(),同时下载 + 解码前几帧

### 依据

ExoPlayer 的 `prepare()` 和 AVPlayer 的 `replaceCurrentItem(with:)` 本身就是下载 + 解码前几帧的行为,这是框架的默认行为,不需要额外处理。

如果只下载不解码,用户滑过来的那一刻还要解码,会有 100-200ms 的黑屏。白费了预加载的意义,用户体感和没有预加载差不多。

### 决策 3:Tab 切换时释放旧 Tab 的 Player,只保留浏览位置索引

### 依据

如果产品规则是"切换 Tab 后当前条内容从 0s 开始自动播放",就不需要保留旧 Tab 的播放进度。

如果保留 3 个 Tab 各 3 个 Player = 9 个 Player 同时存在,没有任何手机扛得住。切回来时根据保存的位置索引重新加载,延迟 ≤300ms,用户可接受。

### 按网络分级的预加载范围

- WiFi / 5G:上下各 1 条,预加载前 5 秒
- 4G:仅下 1 条,预加载前 2 秒
- 3G / 弱网:不预加载,仅加载封面图
- 断网:仅展示本地缓存的封面图

### 封面图兜底

- 视频未加载完成时,先展示封面图 + 呼吸效果
- 封面图通过 Coil / Kingfisher 独立加载,不依赖 Player
- 视频首帧渲染完成后,封面图淡出,视频淡入
- 封面图走正常的图片三级缓存(内存 + 磁盘 + 网络)

## 三、多任务并发轮询控制

### 决策 1:并发轮询上限 3 个

### 依据

大部分用户不会同时有超过 3 个任务在跑。单个长耗时任务要几分钟,用户不太可能连续提交 5 个。超过 3 个的任务等 Push 通知即可,不需要客户端主动轮询。

3 个任务 × 每个最多 5 秒间隔 = 每分钟最多 36 个请求。5 个任务 = 每分钟最多 60 个请求,对电量和带宽的消耗明显增加,但体验提升(第 4、5 个任务的进度实时性)对用户价值很低。

### 决策 2:非活跃任务 15 秒轮询

### 依据

30 秒太长。用户打开统一任务中心,看到进度条 30 秒不动,会以为系统卡了。15 秒是合理的平衡——每分钟只比 30 秒多 2 个请求(payload 几百字节,可以忽略),但用户体感进度在"活着"。

### 决策 3:不显示"最后更新于"

### 依据

显示更新时间会让用户盯着它看,反而放大了"更新慢"的感觉。不显示,用户只关注进度百分比在涨就够了。

### 分层轮询策略

**前台活跃任务**(用户正在查看生成页的任务)
- 按进度动态间隔:0~50% 每 5s,50~90% 每 8s,90%+ 每 3s
- 同时只有 1 个任务是"活跃"

**前台非活跃任务**(在任务中心列表中,但用户没有打开详情的)
- 固定 15s 轮询一次
- 只更新状态和进度百分比
- 最多 2 个

**后台任务**(App 在后台)
- 停止所有轮询,零请求
- 完全依赖 Push 通知告知任务完成/失败
- App 回前台时立即查询一次所有进行中任务的最新状态

## 四、列表/瀑布流视频预览

### 决策 1:所有卡片都支持预览,但只自动播放 1 个

### 依据

视频预览让用户快速判断内容质量。但限制"同时只有 1 个在播放",其余显示封面图——只需要 1 个共享 Player 实例切换数据源,内存和 CPU 开销与播放单个视频一样,性能完全可控。

### 决策 2:自动播放距离中心最近的 1 个,静音

### 依据

手动点击播放的交互太重。用户在瀑布流里是快速扫视模式,不会逐个点播放按钮。自动播放最近的 1 个是主流图片/视频流 App 的常见做法,体验好且性能可控。

需要加一个兜底:Settings 页提供"自动播放预览"开关(默认开启)。流量敏感的用户可以关掉,关掉后全部显示封面图。这个开关同时控制竖滑首页的预加载行为——关闭后只预加载封面图不预加载视频,进一步省流量。

### 决策 3:预览时长 ≤10 秒循环

### 依据

预览的目的是展示效果,10 秒足够看清楚。超过 10 秒用户早就滑走了。预览视频的时长由服务端控制(上传时裁剪或生成时截取前 10 秒),客户端只管循环播放拿到的视频文件。

### 具体规则

- 瀑布流中同时最多 1 个卡片播放视频预览
- 播放的是"距离屏幕中心最近的可见卡片"
- 其余卡片显示封面图
- 滚动过程中暂停所有预览,滚动停止 500ms 后自动播放最近的卡片
- 视频预览静音、循环播放、不显示进度条
- 卡片滑出可视区域时立即暂停,Player 不释放只暂停

### 性能目标

- 瀑布流滚动帧率 ≥55fps
- 视频预览播放时帧率 ≥50fps
- 快速滚动时不播放任何视频,停止后再触发

## 五、分享视频文件准备

### 问题

用户点"分享视频"时,系统分享面板需要本地视频文件。但首页不做视频磁盘缓存(决策 2.1),用户看完的视频滑走就释放了。点分享的那一刻需要重新下载完整视频文件,弱网下等待时间长。

### 决策:先下载到临时目录,下载完成后再调起分享面板

### 具体规则

- 用户点分享 → 选择"分享视频" → 按钮变 loading → 开始下载完整视频到 App 临时目录
- 下载完成后自动调起系统分享面板
- 下载过程中用户可取消,取消后清理临时文件
- 临时文件在分享完成或 App 退出时清理
- "分享链接"不需要下载文件,点击后直接调起分享面板,无等待

### 优化:已下载文件复用

- 如果用户之前已经通过"下载"保存过该视频(本地已有文件),分享时优先检查本地是否已有,有则直接使用,不重复下载
- 检查路径:Android MediaStore / iOS Photos Library

## 六、音频预览(列表试听)

### 问题

某选音乐中间页支持列表试听。用户快速连续点击多首歌预览时:
- 如果不停止上一首就播下一首,两首歌同时播放
- 从选择器返回时,主页面视频的声音可能不恢复
- 音频预览和视频播放的音频焦点冲突

### 决策:单实例音频 Player + 与视频 Player 互斥

### 具体规则

- 全局维护 1 个音频预览 Player 实例(与视频 Player 分开)
- 点击试听时:停止上一首 → 切换数据源 → 播放新的
- 进入选择器时:暂停主页面/列表页的视频播放
- 离开选择器时:释放音频 Player → 恢复之前的视频播放状态

### 音频焦点管理

**Android:**
- 音频预览请求 `AudioFocus` 时使用 `AUDIOFOCUS_GAIN_TRANSIENT`(短暂获取,结束后自动交还)
- 视频 Player 监听焦点丢失,自动暂停
- 音频预览停止后,视频 Player 收到焦点恢复回调,自动继续播放

**iOS:**
- 音频预览使用 `AVAudioSession.Category.playback`
- 进入选择器时设置 session active
- 离开时 deactivate session 并通知视频 Player 恢复
- 使用 `AVAudioSession.interruptionNotification` 监听中断和恢复

## 七、大文件分片上传内存控制

### 问题

上传视频/媒体文件可达数百 MB。如果一次性把文件读入内存再切片,低端设备(3GB RAM)直接 OOM。

### 决策:流式读取分片,单片内存占用 ≤ chunkSize

### 具体规则

- 使用 `RandomAccessFile`(Android)/ `FileHandle`(iOS)按偏移量读取,不把整个文件载入内存
- 每次只读取 1 个 chunk(WiFi 5MB / 蜂窝 2MB)到内存
- 上传完当前 chunk 后释放内存,再读取下一个
- 任何时刻内存中只有 1 个 chunk 的数据

### 实现

```kotlin
// Android — 流式分片读取
fun readChunk(file: File, chunkIndex: Int, chunkSize: Int): ByteArray {
    val offset = chunkIndex.toLong() * chunkSize
    val length = minOf(chunkSize.toLong(), file.length() - offset).toInt()
    RandomAccessFile(file, "r").use { raf ->
        raf.seek(offset)
        val buffer = ByteArray(length)
        raf.readFully(buffer)
        return buffer
    }
    // buffer 出 scope 后即可被 GC
}
```

```swift
// iOS — 流式分片读取
func readChunk(fileURL: URL, chunkIndex: Int, chunkSize: Int) throws -> Data {
    let handle = try FileHandle(forReadingFrom: fileURL)
    defer { handle.closeFile() }
    let offset = UInt64(chunkIndex) * UInt64(chunkSize)
    handle.seek(toFileOffset: offset)
    let data = handle.readData(ofLength: chunkSize)
    return data
}
```

### 内存目标

- 上传过程中内存增量 ≤ chunkSize(最大 5MB)
- 500MB 视频上传全程不额外占用超过 10MB 内存(chunk + 请求开销)

## 八、冷启动链路优化

### 问题

典型启动链路:Splash 动效 → 合规检查 → 远程配置拉取 → DI / 状态容器初始化 → 三方 SDK 初始化 → 首页数据预加载。

环节多,串行执行会拖慢进入首页的时间。特别是远程配置拉取是网络请求,弱网下可能要好几秒。

### 决策:分为阻塞链和非阻塞链并行执行

### 启动链路拆分

**阻塞链(必须完成才能进首页):**

```
App 启动
  → Splash 动效开始播放(同时执行以下并行任务)
    ├── DI / 状态容器初始化(纯本地,≤200ms)
    ├── 远程配置拉取(网络,超时 3s 用本地缓存)
    └── 合规同意状态检查(本地读取,≤50ms)
  → Splash 动效播放完成 AND 阻塞链全部完成
  → 如果合规未同意 → 弹隐私同意弹窗
  → 进入首页
```

**非阻塞链(首页可见后再执行):**

```
首页可见后
  ├── Analytics / Crashlytics 初始化(按合规同意状态)
  ├── 推送 Token 注册
  ├── 通知未读数查询(更新 badge)
  └── iOS ATT 弹窗(首次)
```

### 关键优化点

- Splash 动效播放期间**并行执行**初始化和远程配置拉取,不串行等待
- 远程配置 **3 秒超时**,超时后使用本地缓存或包内默认值,不阻塞启动
- 三方 SDK 初始化**延迟到首页可见后**,不阻塞 Splash → 首页的链路
- 首页首条数据在 Splash 期间**并行预请求**,Splash 结束后直接展示

### 性能目标

- 冷启动到首页可见:≤2 秒
- 首条视频自动播放:≤3 秒(含视频加载)
- 远程配置超时不阻塞:弱网下也能 2 秒进入首页

## 九、字幕/叠加文本实时渲染

### 问题

结果页支持字幕预览开关(CC 按钮)。如果字幕是客户端实时叠加渲染(而非服务端预烧录),需要在视频播放的同时按时间轴同步渲染文字。

### 决策:视情况选择方案

**方案 A:服务端预烧录(推荐首版)**

- 服务端在视频合成时同时生成 With Lyrics / Without Lyrics 两个版本
- 客户端切换 CC 开关 = 切换视频源 URL
- 客户端零渲染开销,最简单

**方案 B:客户端实时叠加**

- 服务端下发 LRC/SRT 格式的时间轴字幕文件
- 客户端在视频播放层上方叠加 `TextView` / `UILabel`
- 按当前播放时间匹配字幕行,更新文字内容
- 不涉及 GPU 合成,只是普通 View 叠加,性能开销很低

**首版建议用方案 A。** 原因:
- 如果产品本来就需要服务端生成两个版本,客户端只是切换 URL,不需要额外开发字幕渲染器
- 字幕样式由服务端控制,双端一致性好

**方案 B 作为 v2 预留。** 当用户可以自定义字幕样式(字体/颜色/位置)时,才需要客户端实时渲染。此时用简单的 View 叠加即可,不需要 GPU 合成。

## 十、设备档位与降级策略(方法论)

> 性能敏感功能要按设备档位预估表现,并对低端档位准备降级方案。
> 具体市场份额数据随时间/地区变化,落地前用最新设备统计(StatCounter / TelemetryDeck / apilevels.com 等)重新核算。

### 10.1 设备档位划分(通用框架)

按 RAM 和系统版本划三档:

| 档位 | 代表特征 | 性能预期 |
|---|---|---|
| 高端 | 8-12GB RAM,最新 2-3 代 OS | 流畅,3 Player 无压力,预加载 5 秒 |
| 中端 | 4-6GB RAM,主流存量机型(往往是最大用户群) | 可运行,切换时偶有首帧延迟 |
| 低端 | ≤4GB RAM,旧 OS | 有 OOM 风险,需降级 |

**关键认知**:中端 4-6GB 设备往往是海外市场最大的用户群体,而不是高端旗舰;某些存量第一的机型(如旧旗舰)只有 4GB RAM。性能压测要覆盖这些"存量大但 RAM 小"的机型,不能只在最新旗舰上测。

### 10.2 各性能敏感功能的档位表现预估

| 功能 | 高端 | 中端 | 低端 |
|---|---|---|---|
| 全屏视频 3 Player 池 | 流畅 | 可运行,偶有首帧延迟 | 有风险,3 Player ~300MB 紧张,需专项压测 |
| 瀑布流视频预览 | 流畅 ≥55fps | 滚动时暂停预览(已在方案中) | 关闭自动预览,全显封面图 |
| 大文件流式上传 | 无压力 | 无压力 | **无压力——流式方案核心价值:不管设备多差,上传只占 5MB** |
| 冷启动 | ≤1.5 秒 | ≤2 秒 | 2-3 秒,远程配置 3s 超时兜底后仍可进入 |
| 多任务并发轮询 | 一致 | 一致 | 一致(轮询是轻量请求,不受设备性能影响,主要影响电量) |

### 10.3 低端设备降级策略

**低端设备判定标准(示例,按项目最低支持版本调整)**
- Android:RAM ≤ 4GB 或 API ≤ 29
- iOS:某代及以下芯片

**降级项**
- 图片缓存从 256MB 降至 128MB
- 瀑布流关闭自动视频预览,全部显示封面图
- 首页视频预加载从上下各 1 条降为仅预加载下 1 条
- 禁用所有过渡动画
- Player 预加载量从 5 秒降为 2 秒

**不降级的(降了会破坏核心体验)**
- 首页 3 Player 池大小不降(降为 2 会导致上滑必黑屏)
- 首页视频自动播放不关(这是核心体验)
- 分片上传策略不变(流式方案本身不受影响)

## 十一、决策总览

| 专项 | 决策 | 核心理由 |
|------|------|---------|
| Player 池大小 | **3 个,不分档** | 5 个体验提升微小,内存翻倍,低端设备 OOM |
| 磁盘视频缓存 | **首版不做** | 竖滑场景回看率低,缓存命中率不够,v2 再看数据 |
| 预加载方式 | **prepare() 下载+解码** | 框架默认行为,只下载不解码会有黑屏 |
| Tab 切换缓存 | **释放 Player,保留位置** | 0s 重播需求下不需保留进度,9 Player 内存扛不住 |
| 并发轮询上限 | **3 个** | 超 3 个的等 Push,省电省带宽 |
| 非活跃轮询间隔 | **15 秒** | 30 秒用户觉得卡,15 秒体感合理 |
| 显示更新时间 | **不显示** | 显示反而放大"慢"的感觉 |
| 瀑布流预览范围 | **全部支持,只播 1 个** | 1 个共享 Player,性能可控 |
| 预览触发方式 | **自动播放 + 设置开关** | 手动点击太重,开关兜底省流量 |
| 预览时长 | **≤10 秒循环** | 超 10 秒用户早滑走了 |
| 分享视频文件准备 | **下载到临时目录,完成后调起分享** | 不缓存则必须下载,复用已有下载文件 |
| 音频预览管理 | **单实例 + 与视频互斥** | 音频焦点清晰,不冲突 |
| 大文件上传 | **流式读取,单片 ≤5MB** | 不整体载入内存,500MB 文件不 OOM |
| 冷启动优化 | **Splash 期间并行初始化,三方 SDK 延迟** | 串行太慢,远程配置 3s 超时兜底 |
| 字幕渲染 | **首版服务端预烧录** | 客户端零开销,v2 再做实时渲染 |
| 低端设备降级 | **自动检测 + 5 项降级** | 4GB 设备占比不低,不降级会 OOM 或卡顿 |

> 通用方法论提炼:每个性能决策都问三件事——
> 1. 体验提升有多大?(用户能否感知)
> 2. 资源成本涨多少?(内存 / 电量 / 带宽 / 代码分支)
> 3. 最差设备扛不扛得住?(低端档位是否 OOM / 卡顿)
> 体验提升微小但资源成本/复杂度大幅上升 → 不做。
