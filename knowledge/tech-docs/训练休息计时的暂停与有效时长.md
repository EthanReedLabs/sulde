# 训练休息计时的暂停与有效时长

## 问题

健身、康复和间歇训练应用通常用绝对截止时间恢复后台倒计时，但“临时离开”与正常休息语义不同。如果暂停只存在内存，进程重启后会丢失；如果暂停仍消耗倒计时，疲劳分析得到的实际休息会被污染。

## 数据模型

一个可恢复的休息区间至少包含：

- 计划休息秒数。
- 开始与结束绝对时间。
- 累计暂停秒数。
- 当前暂停开始时间，可空。
- 结束原因以及 pause/resume 事件。

派生指标应明确区分：

```text
墙钟时长 = 结束时间 - 开始时间
有效休息 = 墙钟时长 - 累计暂停时长
```

训练负荷和疲劳分析使用有效休息；会话审计可以保留墙钟时长。

## 状态转换

暂停时原子写入当前时间，重复暂停保持幂等。恢复时把 `恢复时间 - 暂停开始时间` 累加到暂停总量，再清空暂停开始时间。结束休息时若仍处于暂停，必须先把未闭合暂停区间计入总量，避免异常退出污染数据。

剩余时间不能简单使用 `deadline - now`。暂停状态下应冻结在：

```text
计划秒数 - ((暂停开始 - 休息开始) - 已累计暂停秒数)
```

恢复后再根据新的累计暂停秒数重建绝对截止时间。

## 进程恢复与 UI

- 暂停字段必须持久化，不能只存在 ViewModel。
- 重启后读取开放休息：若有暂停开始时间，显示暂停态和冻结的剩余时间。
- 暂停期间禁用跳过和休息时长调整，提供单一“继续训练”操作。
- 计时结束只提示可以开始下一组，不自动开始拍摄或计数。
- 计时结束后继续按绝对截止时间派生超时，不把 UI 永久停在无语义的 `00:00`；重启后也应恢复“已多休息多久”。
- 训练总结应逐组展示有效休息；当它明显偏离处方时，直接展示多休息或少休息时长，不暴露内部状态字段。
- 每次暂停和恢复写审计事件，便于解释异常时长。

## 验证

使用新仓储实例模拟进程重启，确认暂停状态仍存在。构造包含活动、暂停、再活动的时间线，同时断言墙钟时长、暂停时长、有效休息和事件顺序。总结层测试还应确认展示和处方差值都使用有效休息。数据库迁移必须验证历史 schema 与新建 schema 的列顺序和定义一致。
