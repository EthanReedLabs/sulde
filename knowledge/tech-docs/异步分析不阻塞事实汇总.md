# 异步分析不阻塞事实汇总

## 问题原型

事实记录已经写入，但摘要、模型分析或媒体理解仍在排队；界面把增强结果当成事实汇总的前置条件，
导致用户看到整页加载、空白或“记录丢失”，并在分析失败时连已确认事实也无法使用。

## 根因与证据

根因是把确定事实和概率增强放进同一完成状态。已观察到的稳定边界是：事实先以数据库真值展示，
异步任务只更新自身状态和结果字段；失败、证据不足或重启后恢复均不回滚事实记录。仓储订阅与
状态迁移测试可以证明分析结果只替换对应区域，而不会阻塞或覆盖事实汇总。

## 适用边界

- 适用于训练、健康、业务记录等已确认事实，后续再由模型、媒体或远端服务增强的流程。
- 若增强结果本身就是用户请求的唯一产物，可等待结果，但仍需显式状态、超时和失败语义。
- 增强结果不能反向修改基础事实，除非存在独立、可审计且由用户确认的纠错流程。

## 路由正例

- **输入**：记录已落库，但模型分析超时后总览仍一直空白，用户误以为记录丢失。
- **预期**：apply
- **原因**：确定事实被异步增强的完成状态错误阻塞。
- **来源**：observed

## 路由反例

- **输入**：用户明确请求只生成一段分析文本，任务没有独立的已确认事实可先展示。
- **预期**：skip
- **原因**：分析就是唯一目标产物，不存在事实汇总与增强区域的分层。
- **来源**：constructed

## 执行合格例

- **做法或输出**：记录提交后立即显示事实，分析区域持久化 QUEUED/FAILED/DONE，完成时局部更新。
- **预期**：pass
- **原因**：事实可用性不依赖异步结果，状态又能跨重启解释并恢复。
- **来源**：observed

## 执行失败例

- **做法或输出**：分析 Worker 未返回时整个详情页保持 loading，失败后隐藏已保存的事实。
- **预期**：fail
- **原因**：概率增强接管了事实真值和页面可用性，单点失败被放大。
- **来源**：constructed

## ✅ 正确

训练、健康和业务记录属于确定事实，模型分析属于异步增强。界面应立即展示事实，分析只能更新自己的区域；分析失败不能让用户误以为事实丢失。

## 持久化状态

异步任务至少区分：排队、处理中、完成、证据不足和失败。状态应与被增强的记录一起持久化，不能只放在 Worker、ViewModel 或内存事件中，否则进程重启和页面重进后无法解释空结果。

推荐转换：

```text
未启用 -> null
已提交 -> QUEUED
任务启动 -> ANALYZING
结果原子落库 -> DONE
输入证据不足 -> NO_EVIDENCE
超时或异常 -> FAILED
```

## UI 语义

- 总览先展示已经确认的次数、重量、时长等事实。
- 处理中只在对应记录显示简短状态。
- 完成后通过数据库响应式查询替换该区域，不重载整个页面。
- 证据不足和失败使用用户可理解的文案，并明确已确认记录不受影响。
- 不向用户显示内部枚举、异常类名或模型协议字段。

## 验证

仓储测试应订阅同一条记录并断言完整状态转换及最终内容，UI 测试覆盖各状态的人类可读映射。数据库迁移测试保证历史安装升级后也能恢复任务状态。

## 消费与防复发

- 数据库 schema、仓储、Worker、ViewModel 和 UI 共同消费同一异步状态机。
- 回归覆盖冷启恢复、重复回调、证据不足、超时和事实更新与分析完成竞争。
- 总纲验收分别报告事实可用性与增强完成率，禁止用其中一个布尔状态代表两者。
