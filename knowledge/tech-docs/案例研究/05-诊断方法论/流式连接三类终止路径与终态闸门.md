# 流式连接三类终止路径与终态闸门

> **技术域**：诊断方法论  
> **难度**：⭐⭐⭐⭐⭐  
> **关键词**：SSE / EOF / Flow / 业务终态 / 传输终态 / 重连 / 状态机 / onCompletion  
> **可迁移场景**：聊天生成、AI 推理、长任务进度、实时日志、增量同步等长连接消费链路

---

## 一、场景与系统架构

某生成式交互通过 SSE 持续接收文本片段、结构化快照和任务状态。发送入口用 `requestLocked` 阻止重复提交；网络适配层最多尝试 3 轮连接；状态层收到完成事件后清理加载态并允许下一次发送。

```text
用户发送 ── 设置发送锁 ── 状态层收集 Flow ── 更新界面状态
                              ▲
                              │ 领域事件
HTTP 字节流 ── SSE 适配层 ────┤
   │                          ├─ 完成事件：业务逻辑终态
   ├─ 抛异常：异常断开        ├─ 错误事件：业务错误终态
   └─ readLine == null：干净 EOF └─ collect 返回：收集终态
```

这里有两个不同层次的“结束”：协议事件说明业务任务是否完成；字节流结束只说明这次传输不能再提供事件。二者通常相邻，却不是同一事实。可靠实现必须让适配层正确解释传输，状态层则保证任何收集终止都释放本地资源。

## 二、问题现象

同一套逻辑曾面临两个相反故障：

- 收到业务完成事件后，服务器随后关闭连接并抛出 I/O 错误。若把这个错误继续解释为断线，外层会再次连接；现场注释记录曾出现 **8 次以上冗余重连**。
- 连接未收到完成标记，却以干净 EOF 结束。底层逐行读取在 `readLine == null` 时正常 `break`，Flow 正常完成，不进入 `catch`；发送锁仍为 `true`，之后每次发送都被入口守卫拒绝，界面表现为“发送永久无响应”。
- 适配层的重试上限为 **3 次**，退避间隔依次为 **1 秒、2 秒、4 秒**。这能处理暂时性异常，却无法修复终止语义分类错误。

可复核的控制流 trace 如下：

```text
路径 A：收到完成事件 → socket close 抛异常 → catch
旧判断：异常 == 断线 → 发断线事件 → 外层重连 → 重连风暴

路径 B：没有完成事件 → readLine 返回 null → flow 正常 return
旧判断：catch 才解锁 → catch 未执行 → collect 返回 → 发送锁遗留
```

这不是简单的“多加一个异常捕获”。仅在异常路径收尾，会漏掉干净 EOF；把所有断开都重连，又会把成功后的关闭误判为故障。

## 三、根因分析

### 3.1 终止空间是三类，而不是成功/异常二类

| 终止路径 | 可观测证据 | 业务是否完成 | 正确动作 |
|---|---|---|---|
| 业务逻辑终态 | 收到完成或业务错误事件 | 已确定 | 停止重试，按成功或业务错误收尾 |
| 异常断开 | 读取、解析外层或网络调用抛异常 | 未必 | 未见逻辑终态时才重试或上报断线 |
| 干净 EOF | 上游正常返回，未抛异常 | 未必 | 不制造传输异常，但必须释放本地发送锁和加载态 |

干净 EOF 在语言控制流上属于“正常返回”，在业务协议上却可能是不完整结束。把异常等同失败、正常返回等同成功，会丢失这层差异。

### 3.2 Flow 的异常操作符不覆盖正常完成

Kotlin Flow 的 `catch` 只处理上游抛出的异常；上游正常返回时，收集直接结束。逐行读取 API 在 EOF 时返回 `null` 是约定行为，并不会自动抛出 I/O 异常。因此“在 `catch` 中解锁”从控制流上就不完备。

`onCompletion` 观察的是 Flow 收集的统一终点：正常完成、异常完成以及取消都会经过它。它类似异步资源管理中的 `finally`，适合做必须执行的本地释放；但它不能单独决定是否重连，因为取消、成功完成和缺标记 EOF 的业务语义仍不同。

### 3.3 完成事件后的传输异常不能覆盖既有真值

一旦完成事件已被解析，业务终态就是比后续 socket 状态更强的证据。服务器主动关连接、代理回收连接或客户端读取尾部时抛错，都不能把“任务已完成”改写成“任务断线”。若异常分支无条件发送断线事件，状态层会启动新的连接，形成成功后的重连风暴。

这本质上是状态优先级：`logicalFinished = true` 是吸收态，后续 transport error 只能结束本次读取，不能把状态退回运行中。

### 3.4 单层修复无法同时守住协议与 UI 生命周期

只修适配层，让完成后的异常不再触发重连，仍无法保证所有调用者在干净 EOF 后释放自己的发送锁；只修状态层，在收集结束时统一解锁，又无法阻止适配层把成功后的关闭广播成断线。两个层次承担不同不变量：

- 适配层：完成事件一旦出现，本轮不再重试，也不再发断线事件。
- 状态层：不论上游怎样结束，发送锁最终都必须释放；只有缺少逻辑终态时才清除悬挂占位。

## 四、解决方案

### 4.1 旧代码：把收尾押在事件和异常上

```kotlin
var logicalFinished = false

streamEvents(request)
    .catch { error ->
        requestLocked = false            // ❌ 只覆盖异常，不覆盖干净 EOF
        showDisconnected(error)
    }
    .collect { event ->
        when (event) {
            StreamEvent.Completed -> {
                logicalFinished = true
                requestLocked = false
            }
            StreamEvent.Disconnected -> reconnect() // ❌ 成功后的 close 也可能走到这里
            else -> render(event)
        }
    }
```

问题不在某个布尔变量，而在释放动作没有绑定到收集生命周期的最终出口。

### 4.2 新代码一：适配层建立业务终态闸门

```kotlin
fun openEventStream(payload: ByteArray): Flow<StreamEvent> = flow {
    var logicalFinished = false

    for (attempt in 1..3) {
        try {
            rawLines(payload).collect { line ->
                when (decodeType(line)) {
                    EventType.COMPLETE -> {
                        logicalFinished = true       // ✅ 先固化业务终态
                        emit(StreamEvent.Completed)
                    }
                    EventType.FAILURE -> {
                        logicalFinished = true       // ✅ 业务错误同样是逻辑终态
                        emit(StreamEvent.Failed)
                    }
                    else -> emit(decodeEvent(line))
                }
            }
            return@flow                              // ✅ 干净 EOF：正常结束本轮
        } catch (cancelled: CancellationException) {
            throw cancelled                          // ✅ 保留结构化并发的取消语义
        } catch (error: Throwable) {
            if (logicalFinished) return@flow         // ✅ 终态闸门：成功后的 close 不重连
            if (attempt == 3) emit(StreamEvent.Disconnected(error.message))
            else delay(backoffFor(attempt))
        }
    }
}
```

关键不是吞掉所有异常，而是仅在已经有更强业务证据时把后续关闭视为正常尾声。取消必须继续抛出，不能伪装成普通断线或成功。

### 4.3 新代码二：状态层建立收集终态闸门

```kotlin
var logicalFinished = false
var stoppedByUser = false

openEventStream(payload)
    .catch { error ->
        showStreamError(error)                       // 异常可展示，但不独占释放职责
    }
    .onCompletion {
        requestLocked = false                        // ✅ 所有终止路径最终解锁
        showRecoveringPlaceholder = false

        if (!logicalFinished && !stoppedByUser) {
            removeLoadingIndicator()                 // ✅ 缺终态 EOF：清悬挂 UI
            removePendingPlaceholder()
        }
    }
    .collect { event ->
        when (event) {
            StreamEvent.Completed -> {
                logicalFinished = true
                cancelReconnect()
                removeLoadingIndicator()
                markPendingItemsDone()
            }
            StreamEvent.Failed -> {
                logicalFinished = true
                cancelReconnect()
                showBusinessError()
            }
            is StreamEvent.Disconnected -> {
                if (!logicalFinished && !stoppedByUser) reconnect() // ✅ 二次保险
            }
            else -> render(event)
        }
    }
```

双层闸门形成明确分工：适配层阻断错误重连，状态层保证本地锁和临时 UI 必然释放。`onCompletion` 中只做幂等清理，不重复提交、导航或弹窗，避免取消路径触发新的副作用。

### 4.4 测试矩阵与观测

| 输入序列 | 预期重连 | 发送锁 | UI 结果 |
|---|---:|---|---|
| 数据 → 完成事件 → 正常 EOF | 0 | 释放 | 完成态 |
| 数据 → 完成事件 → I/O 异常 | 0 | 释放 | 完成态不回退 |
| 数据 → 业务错误事件 → close | 0 | 释放 | 明确业务错误 |
| 数据 → I/O 异常，未见终态 | 按上限重试 | 最终释放 | 断线或错误态 |
| 数据 → 干净 EOF，未见终态 | 0 或由上层策略决定 | 释放 | 清除悬挂占位，可再次发送 |
| 用户取消收集 | 0 | 释放 | 不误报网络错误 |

建议记录 `termination_kind`（逻辑完成、业务错误、异常断开、无标记 EOF、取消）、尝试次数和是否释放发送锁。这样能直接观察状态机出口，而不是只看网络错误率。

## 五、可迁移原则

1. **为每种异步原语枚举全部终止路径**：适用于 Flow、AsyncSequence、WebSocket、文件读取和进程管道；正常返回不一定等于业务成功。
2. **业务终态优先于后续传输噪声**：一旦收到不可逆的完成或失败事件，socket 随后的关闭不得触发状态回退或重试。
3. **释放职责绑定生命周期终点**：锁、加载态、订阅计数等必须放在覆盖正常、异常和取消的统一完成钩子中，而非只放在 `catch`。
4. **重试权与清理权分离**：适配层依据协议证据决定是否重试，状态层无条件恢复本地可操作性；不要让一个布尔值同时承担两种职责。
5. **终态清理必须幂等**：完成事件处理和统一完成钩子可能先后执行，重复清理应安全，重复业务副作用则应禁止。
6. **测试必须包含无异常的不完整结束**：仅注入 timeout 和 socket error 覆盖不到 clean EOF，这是长连接最容易遗漏的分支。

## 技术深问

**Q1：为什么不在 EOF 时统一抛一个异常，让现有 `catch` 接管？**

因为 EOF 是传输层合法结果，且可能发生在已经收到业务终态之后。统一抛错会把成功尾声污染成失败。更合理的是保留 EOF 事实，由状态机结合“是否见过逻辑终态”决定展示和恢复动作。

**Q2：`onCompletion` 能否直接启动重连？**

不宜。它也会在正常完成和取消时执行，单凭完成回调无法区分重连资格。重连应依赖显式终止分类；完成回调只承担无条件、幂等的本地释放。

**Q3：为什么业务错误事件也要设置逻辑终态？**

因为它已给出本轮任务的确定结论。若仍把随后关闭当成可恢复断线，客户端会重放已经失败的业务请求，可能产生重复计费、重复任务或错误覆盖。

**Q4：连接协议有 `[DONE]` 是否就不需要完成事件？**

二者表达层次不同。`[DONE]` 通常表示本次消息流结束，业务完成事件可携带任务状态。协议可设计为同一标记，但客户端仍应明确它代表传输结束、业务结束，还是两者兼有，并为缺失标记保留清理兜底。
