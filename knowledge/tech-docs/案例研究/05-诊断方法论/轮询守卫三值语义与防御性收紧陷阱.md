# 轮询守卫三值语义与防御性收紧陷阱

> **技术域**：诊断方法论  
> **难度**：⭐⭐⭐⭐⭐  
> **关键词**：poll-first / 三值语义 / Result / 业务错误 / 网络失败 / 防重复扣费 / 静默失效  
> **可迁移场景**：付费合成、创建订单、提交作业、幂等性未知的远端副作用、先查后建流程

---

## 一、场景与系统架构

付费合成属于不可随意重放的副作用。客户端在创建任务前先查询同一引用是否已有任务：已有完成任务就复用结果，已有进行中任务就接管轮询，明确没有任务才创建；查询结果不确定时宁可提示重试，也不能冒险再次扣费。

```text
用户发起付费合成
        │
        ▼
poll-first：getTaskDetail(referenceId)
        │
        ├─ 确认有任务 ── SUCCESS → 复用结果
        │               └─ RENDERING → 接管轮询
        ├─ 确认无任务 ───────────────→ create（允许付费副作用）
        └─ 结果不确定 ── 重试后失败 ─→ 停止并提示（禁止 create）

HTTP/JSON → 网络适配层 → 领域契约 Result<TaskDetail?> → 调用方状态机
```

最初的风险是把查询失败当成“没有任务”，导致重复创建和重复扣费。防御性修复因此收紧为“一切 failure 都禁止 create”。但服务端以 HTTP 200 返回业务码和 `Task not found` 表示“明确无任务”，网络适配层又把非成功业务码统一包装为 failure。结果是安全守卫挡住了所有全新会话的合法创建。

## 二、问题现象

故障没有表现为崩溃或显式报错，而是付费合成链路静默不启动：复用已有任务的会话可能正常，全新会话却无法创建合成任务，最终退化为无声的单片段结果。由于守卫按照设计执行了“失败不创建”，监控若只关注异常和重复扣费，反而看不到问题。

源事件给出的可核验证据包括：

- 服务端对“尚无任务”的真实应答是 `HTTP 200 + code = -1 + "Task not found."`，它证明查询已到达服务端且服务端明确回答不存在，并非超时或连接中断。
- 第一版守卫会对该应答连续重试 3 次，每次间隔 2 秒，随后停止创建；因此一次全新会话会稳定经历约 4 秒重试等待后被拦截，而不是偶发失败。
- 该行为在线上持续近两周；受影响的是没有既有合成任务的全新会话，已有任务路径不能覆盖这条正向创建分支。
- 旧链路把上述业务应答转换为服务器错误，调用方只能看到统一的 `Result.failure`，无法判断是“明确不存在”还是“查询不确定”。

这是一类典型的“防御成功、功能死亡”：重复扣费风险被压住了，但允许首次创建的充分条件也被错误删除，而且没有异常越过现有告警阈值。

## 三、根因分析

### 3.1 poll-first 天生是三值状态机

查询的领域含义不是成功/失败二值，而是：

| 领域状态 | 证据 | create 决策 |
|---|---|---|
| 确认有任务 | 成功解析出任务，状态为完成或进行中 | 禁止；复用或继续轮询 |
| 确认无任务 | 服务端完成查询并明确回答不存在 | 允许 |
| 结果不确定 | 超时、断网、5xx、无法解析等 | 禁止；重试或提示 |

第一版防重复修复只保留了“有任务”和“failure”两个出口。由于适配层把 `Task not found` 也装进 failure，确认无任务被挤入不确定桶。决策逻辑在局部看非常保守，在领域层却是不完备状态机。

### 3.2 HTTP 成功、业务负语义与传输失败是不同层

HTTP 200 只表示请求获得了可解析的 HTTP 应答，不保证业务操作成功；反过来，业务码非零也不等于网络不确定。`Task not found` 是一个负语义的**确定结果**：答案是否定的，但确定性很高。超时或 I/O 异常才是没有答案。

若网络基础层把所有业务码非零都压成同一种异常，领域调用方就失去完成状态机所需的信息。随后无论选择“failure 时 create”还是“failure 时不 create”，都会伤害一边：前者可能重复扣费，后者阻断首次创建。根因不在重试次数，而在契约丢失了确定性维度。

### 3.3 防御性收紧改变了正向路径，却没有对应回归

修复关注的是“已有任务且首次查询失败”这一负向路径，验证也容易复用已有任务的会话。全新会话恰好依赖“确认无任务 → create”，是被收紧逻辑影响最大的正向路径。没有把它列为发布门，安全修复便能在不报错的情况下长期阻断业务。

### 3.4 静默失败来自观测口径与守卫目标一致

守卫的目标就是不执行 create，所以“不创建”本身未必产生异常。若只监控请求错误率和重复任务数，指标甚至可能改善。要发现这类问题，必须观测状态机转移，例如全新会话从查询进入 create 的转化率，以及“明确无任务”应答被归类到哪个出口。

## 四、解决方案

### 4.1 旧代码：所有 failure 都是不确定

```kotlin
suspend fun runGuardedTaskCreate(referenceId: String) {
    var first: TaskDetail? = null
    var firstError: Throwable? = null

    for (attempt in 0 until 3) {
        val result = getTaskDetail(referenceId)
        if (result.isSuccess) {
            first = result.getOrNull()
            firstError = null
            break
        }
        firstError = result.exceptionOrNull() // ❌ 污染点：明确“无任务”也进入这里
        if (attempt < 2) delay(2_000)
    }

    if (firstError != null) {
        emitMergeFailed()
        return                               // ❌ 全新会话永远到不了 create
    }

    routeExistingOrCreate(first, referenceId)
}
```

即使调用方逻辑写得再严谨，只要 `getTaskDetail` 的 `Result` 无法表达“成功查询但不存在”，这里就不可能做出正确决策。

### 4.2 新代码：在契约边界恢复三值语义

```kotlin
// ✅ null 是领域结果：服务端明确确认没有任务
interface TaskQuerySpec {
    suspend fun getTaskDetail(
        referenceId: String
    ): Result<TaskDetail?>
}

suspend fun getTaskDetail(referenceId: String): Result<TaskDetail?> {
    return safeApi { api.getTaskDetail(referenceId) }
        .recoverCatching { error ->
            if (error is AppError.Server && error.message == "Task not found.") {
                null                         // ✅ 确认无任务：允许调用方 create
            } else {
                throw error                  // ✅ 网络/未知失败：保留不确定性
            }
        }
}
```

调用方保留三条决策分支：

```kotlin
getTaskDetail(referenceId).fold(
    onSuccess = { task -> when (task) {
        null -> createTask(referenceId)       // ✅ 仅“确认无”可创建
        else -> when (task.status) {
            SUCCESS -> applyFinalVideo(task)
            RENDERING -> pollExistingTask(task)    // ✅ 进行中也不能重建
            else -> handleKnownTaskState(task)
        }
    } },
    onFailure = { error -> retryOrReport(error) }  // ❌ 不确定时禁止付费副作用
)
```

关键约束是 `success(null)` 与 `failure` 不得再次合并。若服务端未来提供稳定的结构化错误码，应优先匹配错误码，而非长期依赖消息文本。

### 4.3 测试与发布门

契约测试至少覆盖以下矩阵：

| 输入 | 领域输出 | create 次数 |
|---|---|---:|
| HTTP 200 + 有完成任务 | non-null / SUCCESS | 0 |
| HTTP 200 + 有进行中任务 | non-null / RENDERING | 0 |
| HTTP 200 + 明确不存在 | success(null) | 1 |
| 超时或断网，重试仍失败 | failure | 0 |
| 5xx，重试仍失败 | failure | 0 |

每次收紧防重、鉴权、风控或幂等守卫后，都必须用一个从未创建过任务的全新引用跑通完整正向链路。复用旧会话只能证明“有任务”分支，不能证明首次创建仍可达。

观测上应增加状态机指标：`confirmed_existing`、`confirmed_absent`、`indeterminate` 三个出口的计数，以及 `confirmed_absent → create` 的转化。这样守卫静默阻断时，即使没有异常，也会暴露为正向转化骤降。

## 五、可迁移原则

1. **先查后建不是二值判断，而是带确定性的三值协议**：适用于订单、上传作业、支付、生成任务等非幂等副作用。只有“明确不存在”才能授权创建。
2. **负语义不是失败传输**：空结果、资源不存在、资格不满足等均可能是成功查询得到的否定答案；应在契约层枚举或映射为独立通道。
3. **安全收紧必须回归全新实体的正向路径**：防重复测试要覆盖已有实体，功能存活测试要覆盖从未存在的实体，两者缺一不可。
4. **重试不能修复语义分类错误**：确定的业务否定重试多少次仍是否定；不确定的网络失败也不会因 `getOrNull()` 变成确定不存在。先分类，再决定是否重试。
5. **进行中也是“已有”**：完成态复用结果，进行态接管轮询；二者都禁止 create。只判断完成态会在恢复页面时打开第二个重复创建口子。
6. **监控状态转移而不只监控异常**：防御逻辑常以正常返回结束，异常率无法发现静默死亡；应监控三类查询出口和合法创建转化。

## 技术深问

**Q1：为什么不把 `Task not found` 直接当成普通异常，在调用方捕获后 create？**

因为调用方会被迫了解传输适配细节，而且多个调用点容易产生不同解释。把服务端负语义翻译成 `success(null)` 是契约层职责：上层只处理“有、无、不确定”，无需识别具体异常实现。

**Q2：`Result<TaskDetail?>` 会不会仍然含糊？**

它能表达本案例三态：成功非空、成功空、失败。但当“无任务”还需携带原因，或失败需要区分可重试性时，密封类型更清晰，例如 `Found`、`Absent(reason)`、`Indeterminate(cause)`。类型选择应服从领域分支数量，而非追求最短签名。

**Q3：服务端加幂等键后，客户端守卫是否可以删除？**

只有在幂等键覆盖同一业务意图、有效期、重试和跨设备场景，并且服务端明确保证不会重复扣费时，风险才显著下降。客户端仍可用 poll-first 恢复已有任务和改善体验，但不应把未经验证的“看起来幂等”当作财务安全保证。

**Q4：为什么三次重试和两秒间隔没有挽救首次创建？**

因为输入不是暂时性网络故障，而是服务端对不存在状态的确定应答。错误分类保持不变，重试只会重复得到同一业务结果并增加等待，无法把二值契约变成三值契约。

**Q5：如何避免依赖错误消息字符串？**

优先让服务端提供稳定、可枚举的业务错误码，并在网络适配层映射为领域状态；同时用契约测试锁定映射。消息文本适合展示，不适合作为长期控制流协议。
