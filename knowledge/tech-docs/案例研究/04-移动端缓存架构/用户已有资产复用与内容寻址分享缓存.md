# 用户已有资产复用与内容寻址分享缓存

> **技术域**：移动端缓存架构  
> **难度**：⭐⭐⭐⭐⭐  
> **关键词**：系统媒体库 / 内容寻址 / URL 哈希 / 原子提交 / 取消清理 / LRU / 跨存储域  
> **可迁移场景**：大文件分享、导出物复用、离线包分发、音视频转码结果与可重复生成资产

---

## 一、场景与系统架构

用户分享大媒体时，应用通常先想到“沙箱缓存命中，否则下载”。但用户可能早已把同一最终产物保存到相册。这个文件位于系统媒体库，不在应用缓存目录中；若忽略它，应用仍会重复消耗网络、等待时间和缓存容量。

更完整的读取链是三级：先复用用户已拥有的系统资产，再查由远端 URL 定位的沙箱文件，最后才访问网络。

```text
分享请求
   │
   ├─ 有稳定的产物名前缀？
   │      └─ 查询系统媒体库（最新优先）
   │             ├─ 已发布且 size > 0 ───────────────┐
   │             └─ 未命中 / 无权限                 │
   │                                                ▼
   ├─ 远端 URL → hash(URL) → 沙箱缓存路径      可分享 content URI
   │                      ├─ 文件存在且 size > 0 ────┘
   │                      └─ 未命中
   ▼
网络流式下载 → .tmp → 大小校验 → 原子改名 → LRU 回收 → 可分享 URI
                   └─ 失败或取消：删除半成品
```

这不是简单地多加一次查询，而是把两个存储域纳入同一条复用链：系统媒体库代表“用户长期拥有的资产”，应用沙箱代表“应用可回收的派生缓存”。二者的所有权、生命周期和定位方式并不相同。

## 二、问题现象

修复前，媒体分享只按远端 URL 检查应用缓存；即使用户刚刚保存过相同最终产物，缓存被系统或用户清理后仍会再次下载。对大文件而言，问题会表现为重复等待、重复流量，以及因保留多份副本而更快触发容量限制。

源码可核验的边界 trace 如下；这些数字是实现约束，不是推测的线上耗时：

| 证据 | 修复前风险 | 修复后约束 |
|---|---|---|
| 单文件上限 | 响应头不可信时可能持续写入 | 声明长度与实际累计字节都受 **512 MiB** 限制 |
| 缓存总量 | 大文件持续堆积 | 超过 **1 GiB** 后按最近使用时间回收 |
| 网络等待 | 单一粗粒度超时 | 连接 **30 秒**、读取 **60 秒** |
| 写入粒度 | 下载中目标文件可能被误判为命中 | **8 KiB** 流式写临时文件，完成后再改名 |
| 无效资产 | 空文件或尚未发布的媒体项可能被分享 | `size > 0`，新系统额外要求 pending 状态为 false |

一次典型的旧路径是：`沙箱 miss → 下载 → 写目标路径 → 分享`。新的事件序列是：`媒体库查询 → 沙箱查询 → 必要时下载临时文件 → 提交 → 分享`。当第一级命中时，网络请求数直接从 1 降为 0；当第二级命中时同样不访问网络。

## 三、根因分析

### 3.1 “本地”不是一个存储域

应用缓存目录由应用控制，可能因卸载、系统空间回收或用户清理而消失。相册由系统媒体数据库索引，资产通常跨应用会话长期存在，并通过内容 URI 暴露。只检查沙箱，相当于把“缓存是否存在”错误缩窄为“某个私有路径是否存在”。

用户主动保存过的最终产物还具有更强语义：它不是下载过程的偶然副本，而是用户明确保留的可消费资产。对分享这种只读动作而言，这类资产天然应排在临时缓存之前。

### 3.2 系统媒体库查询返回的是候选项，不等于可用文件

媒体库写入可能经历“先登记、再写数据、最后发布”的过程。新系统用 pending 字段隐藏尚未完成的条目；此外，异常中断或历史脏数据仍可能留下零字节记录。因此“文件名匹配且时间最新”不充分：查询必须过滤未发布项，并从新到旧寻找第一个大小大于零的条目。

读取媒体库还跨越系统授权边界。权限不足属于可预期的一级缓存 miss，应降级到下一层，而不是让整个分享链崩溃。

### 3.3 内容寻址与路径寻址有不同失效语义

相册查询使用“稳定名前缀 + 最新时间”，本质是路径/名称语义：名称表达业务身份，最新记录表达当前候选。它可能因重命名、同名前缀碰撞或用户删除而失效，必须辅以有效性检查。

沙箱层使用 `hash(URL)` 命名，是内容标识的近似形式：同一 URL 稳定落到同一文件，不同 URL 自然隔离。其失效语义是“URL 变更即新资源”。这适合不可变 CDN URL；若同一 URL 的响应内容会原地变化，仅哈希 URL 会返回旧文件，需要把版本、ETag 或内容摘要纳入键。

严格说，URL 哈希是“请求身份寻址”，不是对文件字节做摘要。它解决路径安全、长度和重复请求映射，却不能证明字节内容相同。这个边界必须写进缓存契约。

### 3.4 临时文件是提交协议，不只是命名习惯

若直接写最终路径，另一次读取可能在下载未完成时看到“文件存在”，并把半成品当作命中。正确状态机只有三个稳定状态：

```text
Absent ──下载──> Writing(.tmp) ──校验并改名──> Ready(final)
  ▲                    │
  └────失败/取消清理────┘
```

同一目录内改名把“不可见的写入中”切换成“可见的完整文件”。取消必须单独捕获、清理后继续抛出，不能把协程取消吞成普通失败；否则上层结构化并发语义会被破坏。

### 3.5 LRU 依赖命中时更新使用时间

按最后修改时间排序回收，只有在缓存命中时主动 touch 才近似 LRU。否则一个频繁分享但很早下载的文件仍会被当作最旧项删除。回收时还要排除 `.tmp`，因为半成品由下载事务负责清理，不应被当成可用缓存计入同一淘汰集合。

## 四、解决方案

### 4.1 旧代码：只认识沙箱，目标路径过早暴露

```kotlin
suspend fun prepareForShare(remoteUrl: String): Uri? {
    val target = cacheFile(hash(remoteUrl))
    if (target.exists()) return expose(target)       // ❌ 零字节也可能命中

    network.open(remoteUrl).use { input ->
        target.outputStream().use { input.copyTo(it) } // ❌ 写入中已暴露最终路径
    }
    return expose(target)                            // ❌ 没有大小与容量治理
}
```

这段实现既看不到系统媒体库中的已有资产，也没有定义下载中、取消和磁盘压力下的状态。

### 4.2 新代码：由统一入口按价值顺序下探

```kotlin
suspend fun resolveShareAsset(
    context: Context,
    stableNamePrefix: String?,
    remoteUrl: String?
): Uri? {
    val owned = stableNamePrefix
        ?.takeIf(String::isNotBlank)
        ?.let { systemGallery.findNewestUsable(context, it) }
    if (owned != null) return owned                  // ✅ 一级：用户已有资产

    return remoteUrl
        ?.takeIf(String::isNotBlank)
        ?.let { sandboxStore.obtain(context, it) }   // ✅ 二级缓存，末级网络
}
```

统一入口保证顺序不会散落在各分享按钮中。只有确实进入网络阶段时才展示准备提示；媒体库命中不应制造“正在下载”的错误反馈。

### 4.3 系统媒体库：最新优先，但逐条验证

```kotlin
suspend fun findNewestUsable(context: Context, prefix: String): Uri? = io {
    val where = buildString {
        append("display_name LIKE ?")
        if (platformSupportsPending) append(" AND is_pending = 0") // ✅ 排除未发布项
    }

    try {
        mediaIndex.query(
            columns = listOf("id", "size"),
            where = where,
            args = listOf("$prefix%"),
            order = "date_added DESC"
        ).useEach { row ->
            if (row.long("size") > 0L) return@io row.contentUri() // ✅ 跳过空文件
        }
        null
    } catch (_: SecurityException) {
        null                                             // ✅ 权限不足按 miss 降级
    }
}
```

这里没有把第一行直接当结果。按时间倒序扫描与有效性校验组合，才能得到“最新有效成品”。

### 4.4 沙箱层：双重大小闸门与原子提交

```kotlin
suspend fun obtain(context: Context, remoteUrl: String): Uri? = io {
    val final = cacheRoot(context) / "${digest(remoteUrl)}.mp4"
    if (final.exists() && final.length() > 0L) {
        final.touch()                                    // ✅ 命中即刷新 LRU
        return@io expose(final)
    }

    val temporary = sibling(final, final.name + ".tmp")
    try {
        transport.open(remoteUrl).use { response ->
            if (!response.success) return@io null
            if (response.declaredLength > MAX_ITEM) return@io null // ✅ 快速拒绝

            var copied = 0L
            temporary.outputStream().use { output ->
                response.body.useChunks(8 * 1024) { bytes ->
                    copied += bytes.size
                    if (copied > MAX_ITEM) {
                        temporary.delete()
                        return@io null                    // ✅ 防缺失/伪造长度头
                    }
                    output.write(bytes)
                }
            }
        }
        if (!temporary.renameTo(final)) {
            temporary.delete(); return@io null           // ✅ 只有完整文件成为命中项
        }
        trimByLeastRecentUse(cacheRoot(context), MAX_TOTAL)
        expose(final)
    } catch (cancelled: CancellationException) {
        temporary.delete()
        throw cancelled                                  // ✅ 清理且保留取消语义
    } catch (_: IOException) {
        temporary.delete(); null                         // ✅ I/O 失败不留半成品
    }
}
```

响应头的声明长度只能用于提前拒绝，不能替代实际累计字节检查，因为服务端可能省略或错误填写长度。完成提交后再执行容量回收；回收集合只包含最终文件，并按最后使用时间从旧到新删除，直到总量回到阈值内。

### 4.5 验收矩阵

| 场景 | 预期结果 |
|---|---|
| 相册存在最新、已发布、非空资产 | 直接返回系统内容 URI，网络调用 0 次 |
| 最新记录为空、次新记录有效 | 跳过空记录并返回次新资产 |
| 存在 pending 记录 | 新系统不选择该记录 |
| 相册权限不足但沙箱命中 | 降级后返回沙箱 URI |
| 沙箱文件为零字节 | 不命中，进入网络修复 |
| 响应声明超过 512 MiB | 不读取正文，返回失败 |
| 未声明长度且流超过 512 MiB | 中止并删除临时文件 |
| 下载中取消 | 临时文件删除，取消继续向上传播 |
| 提交后总量超过 1 GiB | 排除临时文件，最久未使用项优先回收 |

## 五、可迁移原则

1. **先找用户已拥有的最终资产，再找应用派生缓存**：适用于导出视频、录音、PDF、离线地图包等跨系统库与沙箱的复用。
2. **缓存层级应按复用价值排序，而不只按访问速度排序**：用户长期资产通常比可回收沙箱文件更稳定，也比网络重取更便宜。
3. **名称寻址必须附带有效性校验**：前缀、时间与路径只能缩小候选集，不能替代非空、已发布、可读取等条件。
4. **请求键必须声明失效语义**：URL 哈希适合版本化不可变资源；可变 URL 应加入版本、校验标签或字节摘要。
5. **最终路径只代表完整状态**：所有大文件写入都应采用临时文件、完整性验证、同目录提交和失败清理。
6. **取消是控制流，不是普通错误**：清理局部资源后必须继续传播，适用于下载、解压、转码与数据库批处理。
7. **容量限制要同时覆盖单项和集合**：前者防单请求耗尽磁盘，后者防长期累积；仅做其中一个都不完整。

## 技术深问

**Q1：为什么不直接比较相册文件与远端文件的字节摘要？**

对数百 MiB 文件先完整读取并计算摘要会增加 I/O 和等待，而且远端摘要未必可得。稳定业务前缀适合作为低成本一级候选；若存在同名前缀误配风险，应保存生成时的资源 ID 或内容摘要元数据，而不是分享时临时全量扫描。

**Q2：`rename` 一定是原子的吗？**

原子性依赖文件系统与是否处于同一挂载点。同一缓存目录内的临时文件和最终文件通常可用原子改名提交；跨卷移动不能依赖这一性质，因此临时文件应创建在最终文件的同级目录。

**Q3：URL 中包含短期签名参数时还能直接哈希吗？**

可以隔离不同请求，但会降低复用率，因为同一内容的每次签名都产生新键。可在确认安全与响应等价后，对 URL 做规范化，或优先使用服务端稳定资源 ID；绝不能未经契约就删除影响鉴权或内容选择的参数。

**Q4：为什么媒体库命中仍要检查大小？**

数据库记录存在不代表文件写入成功。零字节条目可能来自中断、异常发布或历史数据；分享端若只看 ID，会把格式正确的内容 URI 指向不可消费的数据。
