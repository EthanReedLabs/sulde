# 图片加载三级缓存与组件抽象案例研究

> **技术域**：移动端网络与图片性能 / Android Coil / iOS Kingfisher
> **难度**：⭐⭐⭐⭐
> **关键词**：Coil / Kingfisher / ImageLoader / MemoryCache / DiskCache / OkHttpClient / URLSession / URLCache / Cache-Control / ETag / 304 / crossfade / RoundedImageView
> **可迁移场景**：音乐封面列表、视频封面列表、模板墙、Feed 图片、头像、图片 CDN 直链、跨端统一图片加载组件

---

## 场景与系统架构

某移动端应用多个列表页都会加载大量远端封面图：音乐列表封面、使用过的音轨封面、模板封面、Feed 封面等。旧实现中，各处直接调用图片库 API，并在局部重复写 crossfade、圆角 transformation、size、scale 等配置。

当页面滚动、切 Tab、杀进程重启后再次进入列表时，如果没有统一图片缓存和加载组件，就容易出现：

1. 相同 URL 重复走网络。
2. 每个列表各自维护加载参数，行为不一致。
3. 圆角、缩放、占位图、淡入动画散落在 Adapter / View 里。
4. 后续调整缓存策略时，需要逐处迁移。

### 图片三级缓存模型

```
远端图片 CDN
        │
        ▼
L3 HTTP cache
├── Android：图片专用 OkHttpClient + HTTP cache
└── iOS：Kingfisher downloader + 独立 URLCache
        │
        ▼
L2 磁盘图片缓存
├── Android：Coil DiskCache，跨进程重启持久
└── iOS：Kingfisher diskStorage，跨进程重启持久
        │
        ▼
L1 内存 bitmap 缓存
├── Android：Coil MemoryCache
└── iOS：Kingfisher memoryStorage
        │
        ▼
ImageView / SwiftUI View
```

三层缓存职责不同：

| 层级 | 作用 | 典型命中场景 |
|---|---|---|
| L1 内存 bitmap | 最快，避免重新解码和网络 | 列表滚动回顶部、短时间切回页面 |
| L2 磁盘图片缓存 | 跨页面、跨进程保存解码/下载结果 | 切 Tab 后回来、杀进程重启后同 URL |
| L3 HTTP cache | 利用 `Cache-Control` / `ETag` / `304` 复用网络响应 | 远端资源未变、服务端支持缓存头 |

---

## 问题现象

问题不是单张图片加载失败，而是图片加载体系缺少统一入口：

1. 列表首次进入时所有封面都走远端网络。
2. 滚动回已看过的位置时，若缓存策略未统一，可能重复发相同图片请求。
3. 杀进程重启后，理论上可以从磁盘命中，但缺少统一验证和配置。
4. 不同列表重复写加载代码，局部 transformation 和 crossfade 配置不一致。

这类问题的直接用户感知是：列表封面闪烁、滚动时图片重新加载、重进页面仍像冷启动一样加载图片。工程侧问题则是：图片加载散点太多，无法一次性调整缓存容量、HTTP cache、淡入动画或圆角策略。

本次已验证的部分是编译、安装和启动正常；缓存命中行为如“滚回顶部 L1 命中”“杀进程重启 L2 持久命中”“HTTP cache 304”属于验证步骤和预期，需要通过网络日志 / 抓包进一步确认，不能写成已实测收益。

## 根因与设计

### 根因一：没有统一 ImageLoader 配置，缓存能力不可控

Android 侧如果没有全局 Coil `ImageLoader`，各处 `load(url)` 依赖默认配置或局部配置，难以统一 memory/disk/network cache。iOS 侧如果各处直接使用 Kingfisher API，也会让缓存配置和加载参数散落。

统一配置的目标是：

```
App startup
└── configure global image pipeline
    ├── L1 memory cache
    ├── L2 disk image cache
    ├── L3 HTTP cache
    ├── default crossfade
    └── shared loader/downloader
```

这样调用方只关心“加载这张图”，而不是每次重新声明缓存策略。

### 根因二：图片 OkHttpClient / URLSession 应与业务 API client 隔离

图片直链与业务 API 的缓存语义不同。

业务 API 通常返回 envelope：

```json
{
  "code": 0,
  "data": { ... }
}
```

即使 HTTP status 是 200，业务是否成功还要看 envelope code。很多业务 API 还带 token、语言、401 拦截、日志、业务 header 等。直接对这类响应启用通用 HTTP cache，很容易缓存了不该缓存的用户态数据。

图片直链则更适合 HTTP cache：

```
GET https://image-cdn/.../cover.jpg
Cache-Control: public, max-age=...
ETag: ...
304 Not Modified
```

因此图片网络栈应与业务 API 网络栈隔离：

| 网络栈 | 典型配置 |
|---|---|
| 业务 API client | token、401、业务 header、body logging、业务 envelope 解析 |
| 图片 client | HTTP cache、图片 CDN 响应头、图片下载超时、图片专用缓存容量 |

隔离后，图片 cache 可以积极使用 HTTP 语义，而不会污染业务 API 的鉴权、日志或缓存策略。

### 根因三：圆角不应每次都用 bitmap transformation

Android 部分封面 View 已经是 `RoundedImageView` 或等价形态容器，圆角可以由 View shape 裁剪完成。如果每次加载都加 `RoundedCornersTransformation`，会额外引入 bitmap transformation 成本，并让调用点重复写 dp 转 px、radius 等局部逻辑。

更合理的分工是：

```
图片加载组件：负责 URL、缓存、crossfade、size/scale
View / Shape：负责圆角、裁剪、视觉外形
```

只有在确实需要把 bitmap 本身处理成圆角输出时，才使用 transformation。列表卡片的静态圆角通常交给 View 层更清晰。

### 根因四：调用点需要组合式 DSL，而不是复制粘贴图片库调用

统一扩展应提供默认行为，同时允许调用方覆盖：

```kotlin
imageView.loadAppImage(url) {
    scale(Scale.FILL)
    size(360, 640)
}
```

iOS SwiftUI 侧可用链式 modifier：

```swift
RemoteImage(url: url)
    .contentMode(.fill)
    .cornerRadius(8)
    .fadeIn(0.2)
```

这类组件抽象的价值是：默认路径统一，特殊场景仍可局部声明差异。

## 解决方案

### Android：全局 Coil ImageLoader

Android 侧配置全局 Coil `ImageLoader`：

```kotlin
private fun configureImageLoader() {
    val httpCache = Cache(
        directory = File(cacheDir, "image_http_cache"),
        maxSize = 256L * 1024 * 1024,
    )

    val imageOkHttpClient = OkHttpClient.Builder()
        .cache(httpCache)
        .build()

    val imageLoader = ImageLoader.Builder(this)
        .memoryCache {
            MemoryCache.Builder(this)
                .maxSizePercent(0.25)
                .strongReferencesEnabled(true)
                .build()
        }
        .diskCache {
            DiskCache.Builder()
                .directory(File(cacheDir, "image_cache"))
                .maxSizeBytes(512L * 1024 * 1024)
                .build()
        }
        .okHttpClient(imageOkHttpClient)
        .memoryCachePolicy(CachePolicy.ENABLED)
        .diskCachePolicy(CachePolicy.ENABLED)
        .networkCachePolicy(CachePolicy.ENABLED)
        .crossfade(200)
        .build()

    Coil.setImageLoader(imageLoader)
}
```

参数含义：

| 层级 | 配置 |
|---|---|
| L1 memory | 最大 25% 内存 |
| L2 disk | 512MB |
| L3 HTTP | 256MB |
| 动画 | crossfade 200ms |

### Android：统一 `loadAppImage` 扩展

封装公共加载入口：

```kotlin
fun ImageView.loadAppImage(
    url: String?,
    builder: ImageRequest.Builder.() -> Unit = {},
) {
    load(url) {
        crossfade(200)
        builder()
    }
}
```

普通封面：

```kotlin
coverView.loadAppImage(item.coverUrl)
```

需要指定裁剪和尺寸的封面：

```kotlin
coverView.loadAppImage(item.coverUrl) {
    scale(Scale.FILL)
    size(360, 640)
}
```

如果 View 本身已经负责圆角，就移除局部 `RoundedCornersTransformation`，避免重复处理 bitmap。

### iOS：Kingfisher 缓存与统一组件

iOS 侧采用 Kingfisher，并配置 L1/L2/L3：

```swift
func configureImageLoading() {
    let cache = ImageCache.default
    cache.memoryStorage.config.totalCostLimit = 256 * 1024 * 1024
    cache.memoryStorage.config.countLimit = .max
    cache.diskStorage.config.sizeLimit = 512 * 1024 * 1024
    cache.diskStorage.config.expiration = .days(7)

    let urlCache = URLCache(
        memoryCapacity: 64 * 1024 * 1024,
        diskCapacity: 256 * 1024 * 1024,
        diskPath: "image_url_cache"
    )

    let sessionConfig = URLSessionConfiguration.default
    sessionConfig.urlCache = urlCache
    sessionConfig.requestCachePolicy = .useProtocolCachePolicy
    KingfisherManager.shared.downloader.sessionConfiguration = sessionConfig
}
```

iOS 参数：

| 层级 | 配置 |
|---|---|
| L1 memory | 256MB |
| L2 disk | 512MB，7 天过期 |
| L3 URLCache | 64MB memory + 256MB disk |
| 动画 | 默认 fade 约 0.2s |

SwiftUI 侧提供组合式远端图片组件：

```swift
RemoteImage(url: url)
    .contentMode(.fill)
    .cornerRadius(8)
    .fadeIn(0.2)
```

UIKit 侧提供 `UIImageView` 扩展：

```swift
imageView.loadRemote(url: url)
```

这样 SwiftUI 和 UIKit 都不再直接散落调用 Kingfisher 原始 API。

### 验证步骤与预期

以下是缓存行为验证步骤，不写成已实测收益：

| 场景 | 验证方法 | 预期 |
|---|---|---|
| 首次进入列表 | 抓网络日志 / 代理 | 每个封面 URL 首次 GET，返回 200 |
| 滚到底再滚回顶部 | 观察同 URL 是否再请求 | L1 memory 命中，不再 GET |
| 切 Tab 后返回 | 观察同 URL | L1 未淘汰则内存命中；否则 L2 disk 命中 |
| 杀进程重启后进入 | 观察同 URL | L2 disk 持久命中，或 L3 304 |
| 服务端带 ETag | 抓 HTTP 响应 | L3 可返回 304 |

L3 HTTP cache 是否命中依赖远端图片响应头。如果图片 CDN 不返回 `Cache-Control` / `ETag`，L1/L2 仍可工作，但 HTTP 304 收益不会出现。

### 为什么这样修，而不是其他方式

**不复用业务 API client**：图片直链适合 HTTP cache，业务 API 有 envelope、鉴权、401、日志和业务 header。复用会互相污染配置。

**不在每个 Adapter 里继续写图片库调用**：散点调用会导致缓存策略、crossfade、scale、placeholder 不一致。统一扩展保留可定制能力，同时收敛默认行为。

**不强制所有图片同一种 transformation**：圆角、裁剪和占位是视觉职责，不能在 loader 层一刀切。统一 loader 只提供基础能力，特殊视图通过 builder / modifier 声明。

**不把 L3 HTTP cache 当作唯一缓存**：HTTP cache 依赖响应头，不稳定；图片库 L1/L2 是客户端可控的主战场。三级缓存应互补，而不是互相替代。

## 可迁移原则

### 1. 图片缓存至少分清 L1、L2、L3

L1 解决滚动回看，L2 解决跨页面和重启，L3 解决远端响应未变。三者命中条件不同，排查时不要把“没有网络请求”笼统归因。

### 2. 图片网络栈应与业务 API 网络栈隔离

图片 CDN 直链可以使用 HTTP cache，业务 API 往往不能直接按 HTTP status 缓存。隔离 client / session 可以避免 token、日志、401、Cache-Control 策略互相污染。

### 3. 统一组件负责默认行为，调用方保留组合能力

一个好的图片组件应提供默认 crossfade、cache、占位入口，同时允许调用方设置 scale、size、cornerRadius、cacheKey。不要为了统一而牺牲特殊场景。

### 4. 圆角优先交给 View shape，bitmap transformation 按需使用

如果 UI 控件本身已经支持圆角裁剪，就不必每次对 bitmap 做 transformation。这样能减少重复计算，也让视觉职责更清晰。

### 5. 缓存收益必须用网络日志验证

build 通过只说明代码可运行，不说明缓存命中。图片缓存应通过网络日志、代理抓包或图片库日志验证：首次 200、滚回无请求、重启后 disk hit 或 304。

### 6. 双端对称是行为对称，不是库名对称

Android 用 Coil，iOS 用 Kingfisher；Android 是 OkHttp cache，iOS 是 URLCache。只要都满足 L1/L2/L3、统一加载入口、图片网络栈隔离，就是对称工程。

## 技术深问 Q&A

### Q1：为什么有 L2 磁盘缓存，还需要 L3 HTTP cache？

L2 是图片库自己的文件缓存，通常按请求和解码结果管理；L3 是 HTTP 协议缓存，可利用 `ETag` / `304` 验证远端资源未变。L2 更可控，L3 更依赖服务端响应头。

### Q2：为什么图片 client 不复用业务 API client？

业务 API 可能有 token、401、body logging、业务 envelope 和不可缓存响应；图片直链适合按 HTTP cache 处理。复用会让两种语义互相牵制。

### Q3：crossfade 200ms 会不会影响性能？

200ms crossfade 主要改善图片从占位到真实图的视觉过渡。它不是缓存优化本身。若列表极端密集或低端机掉帧，应单独压测并允许调用方关闭或调整。

### Q4：为什么 Android 圆角交给 `RoundedImageView`？

如果 View 层已经通过 shape 裁剪实现圆角，再做 `RoundedCornersTransformation` 就是重复工作。列表里大量图片重复 transformation 会放大 CPU 和内存开销。

### Q5：为什么杀进程重启后可能仍然发请求？

如果 L2 disk cache miss，或 cache key 变化，或图片 URL 带时间戳，客户端会重新请求。即使 L3 存在，也需要服务端返回缓存头才可能 304。

### Q6：如何判断缓存配置真的生效？

最小验证链路是：首次加载看到 GET 200；滚回同位置无重复 GET；杀进程重启后同 URL 不重新下载或返回 304；清 cache 后再次进入恢复 GET 200。
