# 请求级单飞与多订阅者广播缓存

> **技术域**：移动端缓存架构  
> **难度**：⭐⭐⭐⭐⭐  
> **关键词**：Swift actor / AsyncStream / single-flight / fan-out / late subscriber / L1 / L2 / 请求合并  
> **可迁移场景**：图片、音视频、配置、元数据、离线包等同资源并发加载与分层缓存

---

## 一、场景与系统架构

多个卡片可能同时请求同一媒体 URL。缓存链路先查内存 L1，再查磁盘 L2，最后访问网络 L3。调用方不仅需要最终资源，还要接收当前加载阶段、成功或可重试失败，因此入口返回 `AsyncStream`。

```text
订阅者 A ─┐                 ┌─ lastEvent 回放给迟到者
订阅者 B ─┼─ fetch(URL) ───>│ actor 内的 inflight[URL]
订阅者 C ─┘                 │  ├─ subscribers[id] → continuation
                            │  └─ 一个底层网络任务
L1 内存 → L2 磁盘 → L3 网络┴────> 写 L2 → 写 L1 → 广播 success → finish
                                 ▲
                     无订阅者时仍继续完成并写缓存
```

single-flight 的目标不是“全局一次只跑一个请求”，而是“同一资源键共享一次底层工作，不同键仍可并行”。多订阅者协议还要定义迟到加入、单个离开、主动失效和无人等待时的行为。

## 二、问题现象

正例实现有一条明确并发回归：**5 个并发消费者请求同一 URL，网络加载计数严格等于 1**。测试用约 **50 ms** 的模拟慢网络制造重叠窗口，确保五个订阅者先注册再完成。这个数字证明的是请求合并，不代表生产网络耗时。

对照实现虽然由 Swift `actor` 隔离，并注明用于防止同文件并发竞争，却没有按 URL 保存进行中任务。两个调用都可能在首次缓存检查时 miss，随后分别进入下载：

```text
任务 A：actor 内查缓存 miss → await download ─────────┐
                                                       │ actor 可重入
任务 B：actor 内查缓存 miss → await download ─────────┤
任务 A 恢复：检查目标、移动临时文件                  │
任务 B 恢复：删除/覆盖同一目标、移动另一临时文件 ────┘
```

结果不只是浪费一次网络流量。两个恢复段还可能围绕同一目标路径重复删除、移动和裁剪缓存；调用方看到的进度也各自独立，无法共享最近状态。

## 三、根因分析

### 3.1 actor 隔离的是可变状态访问，不是整个异步函数的独占执行

Swift actor 保证同一时刻只有一个任务执行其隔离代码，但当任务运行到 `await` 并挂起时，actor executor 可以处理其他任务。原任务恢复前，第二个调用能够完成同样的 cache miss 检查并启动第二次下载。这叫 actor reentrancy，是避免 executor 被慢 I/O 阻塞的必要机制。

因此“函数写在 actor 里”只能避免同步数据竞争，不能自动把 `check → await work → publish` 变成跨挂起点的原子事务。要获得同 key 单飞，必须在第一次 `await` 之前登记进行中状态。

### 3.2 inflight 表保存的是共享协议，而不只是 Task

一个 `[URL: Task]` 可以共享最终值，但本场景还需广播 loading、success、failure，并允许每个订阅者独立终止。每个条目因此至少包含：

```text
SharedFlight
├─ subscribers: [SubscriberID: Continuation]
└─ lastEvent: FetchEvent?
```

`lastEvent` 解决迟到订阅：若网络阶段已经开始，新订阅者加入后立即收到当前状态，不必等到下一次事件才知道请求正在进行。订阅者 ID 则让取消只移除自己，不会结束其他人的流。

### 3.3 订阅生命周期与底层工作生命周期不是一回事

最后一个订阅者离开后，直觉上可以取消下载；缓存系统却可能选择继续，因为已经消耗的带宽和即将得到的缓存价值高于继续成本。正例明确采用“无人订阅仍完成”：取消只删除 continuation，底层请求完成后仍写入 L2、L1，下一次请求可直接命中。

这是策略选择，不是普适答案。大文件蜂窝下载、带签名短链或资源已失效时，取消可能更合理。关键是把策略写清楚，而不是让 `AsyncStream` 的 termination 偶然决定网络任务命运。

### 3.4 主动失效需要结束所有旧订阅

资源 URL 被替换或上层执行 forget 时，旧 inflight 若继续向订阅者发事件，可能把过期资源写回新状态。正确的 invalidate 会移除 L1、删除 L2、从表中摘除对应条目，并对该条目的所有 continuation 调用 `finish()`。

注意：结束订阅流和取消底层任务仍是两个动作。若底层任务不可取消或策略决定继续，完成回调必须使用 entry 身份校验，避免旧任务误删同 URL 后来创建的新条目。

## 四、解决方案

### 4.1 旧代码：actor 内 check-then-await

```swift
actor FileStore {
    func fetchAndCache(_ remote: URL) async throws -> URL {
        let target = localPath(for: remote)
        if fileExists(target) { return target }

        let temporary = try await transport.fetch(remote)
        // ❌ 污染点：await 期间 actor 可重入；另一调用也会看到 miss

        if fileExists(target) { remove(target) }
        try move(temporary, to: target)               // ❌ 多任务争用同一路径
        return target
    }
}
```

串行 executor 并没有把缓存检查和下载提交锁成一个不可分割区间。

### 4.2 新代码：首次挂起前登记按键条目

```swift
actor ResourceCache {
    private var flights: [URL: Flight] = [:]

    func stream(for url: URL) -> AsyncStream<FetchEvent> {
        let subscriberID = UUID()
        let (stream, continuation) = AsyncStream<FetchEvent>.makeStream()

        Task { await enroll(url, subscriberID, continuation) }
        continuation.onTermination = { [weak self] _ in
            Task { await self?.detach(url, subscriberID) }
        }
        return stream
    }

    private func enroll(
        _ url: URL,
        _ id: UUID,
        _ sink: AsyncStream<FetchEvent>.Continuation
    ) async {
        if let asset = memory.get(url) {
            sink.yield(.success(asset)); sink.finish(); return // ✅ L1 快路径
        }
        if let asset = disk?.get(url) {
            memory.set(url, asset)
            sink.yield(.success(asset)); sink.finish(); return // ✅ L2 回填 L1
        }

        if let flight = flights[url] {
            flight.subscribers[id] = sink                       // ✅ 加入同 key 请求
            if let recent = flight.lastEvent { sink.yield(recent) }
            return                                               // ✅ 不启动第二次网络
        }

        let flight = Flight()
        flight.subscribers[id] = sink
        flight.lastEvent = .loading(.network)
        flights[url] = flight                                    // ✅ 在首个网络 await 前登记
        sink.yield(.loading(.network))

        await loadAndPublish(url, flight)
    }
}
```

`Flight` 是 actor 隔离下使用的内部引用对象；所有读写仍在 actor 上完成。不同 URL 拥有不同条目，网络 `await` 挂起后其他键可继续推进。

### 4.3 广播、完成与逐订阅者退出

```swift
private func publish(_ event: FetchEvent, to flight: Flight) {
    flight.lastEvent = event                              // ✅ 供 late subscriber 回放
    for sink in flight.subscribers.values { sink.yield(event) }
}

private func complete(_ url: URL, _ flight: Flight) {
    for sink in flight.subscribers.values { sink.finish() }
    if flights[url] === flight { flights.removeValue(forKey: url) }
    // ✅ 身份校验：旧任务不能删除同 URL 的新条目
}

private func detach(_ url: URL, _ id: UUID) {
    flights[url]?.subscribers.removeValue(forKey: id)
    // ✅ 只结束该订阅关系；按当前策略不取消底层加载
}

func expireResource(_ url: URL) {
    memory.remove(url)
    disk?.remove(url)
    if let flight = flights.removeValue(forKey: url) {
        for sink in flight.subscribers.values { sink.finish() } // ✅ 旧流立即失效
    }
}
```

### 4.4 即使无人订阅，也完成缓存提交

```swift
private func loadAndPublish(_ url: URL, _ flight: Flight) async {
    do {
        let temporary = try await network(url)
        let asset = try disk?.store(url, temporary) ?? Asset(temporary)
        memory.set(url, asset)                            // ✅ 先提交缓存
        publish(.success(asset), to: flight)              // 再广播结果
    } catch {
        publish(.failure(classify(error)), to: flight)
    }
    complete(url, flight)
}
```

缓存写入不依赖 `subscribers` 是否为空。若产品策略要求末订阅者离开即取消，可在条目中保存底层 `Task`，在订阅数归零时取消；但必须同时处理临时文件清理、取消错误分类和新订阅竞争。

### 4.5 并发与生命周期测试

| 测试 | 断言 |
|---|---|
| 同 URL 5 个并发消费者 | 网络调用 1 次，五者都收到成功 |
| 不同 URL 并发 | 各调用 1 次，彼此不阻塞 |
| 网络开始后加入订阅者 | 立即回放最近 loading，随后收到相同终态 |
| 一个订阅者取消 | 其 continuation 被移除，其他订阅者继续 |
| 全部订阅者取消 | 网络仍完成并写缓存，下次请求命中 |
| 请求中主动失效 | 所有旧流 finish，L1/L2 被清除 |
| 失败完成 | 所有仍在线订阅者收到同一失败，条目被移除以允许重试 |

测试应使用计数器和可控挂起点，而非依赖真实网络时序。只有强制多个调用同时跨过 cache miss，才能证明 single-flight 真正建立在第一次 `await` 之前。

## 五、可迁移原则

1. **actor 串行不等于异步事务原子**：任何 `check → await → publish` 都应审查可重入窗口；数据库连接、token 刷新和文件生成同样适用。
2. **single-flight 必须按资源键建模**：同键合并、异键并行；全局互斥会无谓降低吞吐，单纯缓存最终值又挡不住并发 miss。
3. **在第一次挂起前发布进行中状态**：否则第二个调用仍能穿过检查并启动重复工作。
4. **把订阅和底层任务的生命周期分开**：单个订阅取消不应误伤其他消费者；末订阅离开后继续还是取消，应由成本和缓存价值明确决定。
5. **迟到订阅者需要状态回放**：至少保存最近事件，避免订阅者加入后长时间没有 loading 或进度反馈。
6. **失效必须同时治理数据与流**：清 L1/L2 之外还要结束旧订阅，并防止旧任务完成后删除或污染新条目。
7. **以并发计数测试证明单飞**：结果都成功并不能证明没有重复请求；必须断言 N 个同键消费者对应一次底层调用。

## 技术深问

**Q1：为什么不用一个共享 `Task<Asset, Error>`，还要 `AsyncStream`？**

若调用方只关心最终值，共享 Task 更简单。需要广播加载阶段、进度、可重试失败或多次事件时，AsyncStream 才提供合适协议。选择取决于事件模型，不应为使用流而使用流。

**Q2：最后一个订阅者离开后继续下载是否浪费资源？**

取决于文件大小、网络类型、已完成比例和复用概率。小型高复用资源通常值得完成；大文件或昂贵蜂窝流量可取消。可把策略扩展为引用计数加成本阈值，但无论选择哪种，都应有测试锁定。

**Q3：为什么 `lastEvent` 不保存全部历史？**

迟到者通常只需当前阶段和最终结果，完整历史会增加内存并可能重放过时进度。若事件是增量数据而非状态快照，则应改为有界缓冲、持久化日志或为迟到者重建当前状态。

**Q4：主动失效后旧网络任务仍完成，会不会重新写入缓存？**

如果底层任务不取消，确有此风险。生产实现可给条目增加 generation/token，在提交 L1/L2 前确认它仍是当前条目；或在主动失效时取消任务并清理临时文件。仅用 entry 身份保护表删除还不够保护缓存写入。

**Q5：单飞是否等同于 HTTP 缓存或连接池复用？**

不等同。连接池复用 TCP/TLS 资源，HTTP 缓存复用已完成响应，single-flight 合并的是同一时刻尚未完成的业务请求。三者可以叠加，解决的是不同层次的问题。
