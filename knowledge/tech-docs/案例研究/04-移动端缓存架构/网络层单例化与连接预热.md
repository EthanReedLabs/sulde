# 移动端网络层单例化、连接预热与 HTTP 缓存案例研究

> **技术域**：移动端网络架构 / Android / OkHttp / Retrofit / HTTP 缓存
> **难度**：⭐⭐⭐⭐⭐
> **关键词**：OkHttpClient / Retrofit / ConnectionPool / DNS / TLS / HTTP/2 / ALPN / Protocol.HTTP_2 / Cache-Control / ETag / 304 / Koin / 连接预热
> **可迁移场景**：冷启动首个接口慢、多个业务 API 共用同一域名、音乐/模板/列表首屏慢、Android 网络层重构、HTTP 缓存接入、401 拦截器统一治理

---

## 场景与系统架构

某 Android 应用的多个业务模块都访问同一个后端域名，但依赖注入里每个业务 API 都通过 factory 创建自己的 Retrofit 和 OkHttpClient。表面上每个 API 都是 `single`，实际底层却是多个独立网络客户端。

旧结构可以简化为：

```
DI Container
├── ApiA          -> build Retrofit -> build OkHttpClient #1 -> ConnectionPool #1
├── ApiB          -> build Retrofit -> build OkHttpClient #2 -> ConnectionPool #2
├── ApiC          -> build Retrofit -> build OkHttpClient #3 -> ConnectionPool #3
├── ApiD          -> build Retrofit -> build OkHttpClient #4 -> ConnectionPool #4
└── ... 11+ business APIs
```

每个 OkHttpClient 都有自己的：

1. `ConnectionPool`
2. DNS 解析结果缓存
3. TLS session / socket 复用机会
4. interceptor 实例
5. HTTP/2 连接与 multiplexing 状态

因此，即使这些 API 访问同一个远端域名，第一次使用时仍可能各自经历 DNS、TCP、TLS、ALPN 协商和 HTTP/2 建连。对用户来说，某个页面第一次触发某个 API，就会把建连成本暴露在点击后的关键路径里。

目标结构是把同 baseUrl 的业务 API 收敛到共享网络栈：

```
NetworkModule
├── shared OkHttpClient
│   ├── shared ConnectionPool
│   ├── shared DNS / TLS session reuse
│   ├── shared interceptors
│   ├── 64MB HTTP cache
│   └── protocols: HTTP_2, HTTP_1_1
│
└── shared Retrofit
    ├── create(ApiA)
    ├── create(ApiB)
    ├── create(ApiC)
    └── create(ApiD)
```

iOS 侧可作为对照：常见实现会通过 `URLSession.shared` 或显式共享 `URLSession` 复用系统级连接池，天然较少出现“每个业务 API 都独立建连接池”的问题。

## 问题现象

用户侧问题集中在选音乐列表冷启动：从进入列表到首批数据可用耗时较长。已有打点基线显示：

| 指标 | 实测 |
|---|---:|
| 选音乐列表冷启动 `T0 -> T1` | 2148ms |

这个 2148ms 是已实测基线。后续改造后的 `1500-1700ms`、warm restart `<800ms` 属于预期目标，需要复测验证，不能写成已达成收益。

冷启动慢的可疑成本包括：

1. 首个业务接口首次访问域名，需要 DNS + TCP + TLS + ALPN。
2. 多个 API 各自持有 OkHttpClient，连接池无法共享。
3. 用户点击后才触发建连，连接预热没有提前发生。
4. 没有 HTTP cache，即使资源短时间不变也要完整走网络。
5. HTTP/2 未显式声明时，若 ALPN 协商降级，可能失去 multiplexing 收益。

## 根因分析

### 根因一：11+ 独立 OkHttpClient 导致连接池碎片化

OkHttpClient 不是普通轻量 wrapper。每个实例都持有自己的连接池和一组网络状态：

```kotlin
fun createApiA(): ApiA {
    val client = OkHttpClient.Builder()
        .addInterceptor(tokenInterceptor)
        .build()
    return Retrofit.Builder()
        .client(client)
        .baseUrl(baseUrl)
        .build()
        .create(ApiA::class.java)
}

fun createApiB(): ApiB {
    val client = OkHttpClient.Builder()
        .addInterceptor(tokenInterceptor)
        .build()
    return Retrofit.Builder()
        .client(client)
        .baseUrl(baseUrl)
        .build()
        .create(ApiB::class.java)
}
```

这种写法会造成：

```
ApiA 首次请求
└── DNS + TCP + TLS + ALPN + HTTP/2 connection

ApiB 首次请求
└── 另一个 OkHttpClient，无法复用上面的连接
    └── 再来一次 DNS + TCP + TLS + ALPN

其他业务 Api
└── 同理，各自首次建连
```

单次建连常见成本约 `300-500ms`。如果它发生在用户点击后的首屏关键路径上，就会直接拉长感知延迟。

### 根因二：没有连接预热，建连发生在用户路径上

冷启动后，如果直到用户进入选音乐页才发出热门歌曲列表请求，那么建连和业务请求会串在一起：

```
用户点击进入选音乐页
└── 创建/使用 Api
    └── DNS
        └── TCP connect
            └── TLS handshake
                └── ALPN 协商
                    └── 发业务请求
                        └── 等响应
```

如果应用启动后可以在后台提前发起一个低风险请求，就能把 DNS、TLS 和 HTTP/2 连接建立提前完成。等用户真正进入页面时，OkHttp 可以复用同一个 `ConnectionPool` 中的健康连接。

连接预热的重点不是缓存这次返回的数据，而是暖连接：

```
App 启动
└── 后台预热请求
    ├── 建立 DNS / TLS / h2 connection
    └── 数据可丢弃或不进入业务状态

用户进入页面
└── 复用连接池
    └── 少一次建连成本
```

### 根因三：无 HTTP cache，短时间重复 GET 无法 304

对于热门列表、模板列表、用户资料等变化频率不高的 GET 接口，HTTP cache 可以通过 `Cache-Control`、`ETag`、`304 Not Modified` 避免重复下载完整响应。

如果客户端没有配置 OkHttp `Cache`：

```kotlin
OkHttpClient.Builder()
    // no cache
    .build()
```

即使服务端返回缓存头，客户端也无法持久化和复用响应。warm restart 时仍要像 cold start 一样发完整请求。

需要注意：客户端配置 cache 只是前提。若服务端没有返回合适的 `Cache-Control` 或 `ETag`，64MB cache 物理存在也可能命中率为 0。

### 根因四：HTTP/2 与 ALPN 需要保持可见的协议策略

OkHttp 默认会进行协议协商，但在网络栈重构时，显式声明：

```kotlin
.protocols(listOf(Protocol.HTTP_2, Protocol.HTTP_1_1))
```

可以让意图更明确：优先 HTTP/2，失败时回退 HTTP/1.1。HTTP/2 对同域名多请求的价值在于 multiplexing，多个请求可以复用同一个连接并发传输，减少连接数和队头等待。

如果连接池碎片化，即使支持 HTTP/2，也无法最大化 multiplexing；每个 OkHttpClient 都有自己的连接，复用范围被人为切碎。

### 根因五：401 拦截器多实例不是功能错，但增加结构复杂度

旧结构中，每个 OkHttpClient 都注入自己的 401 拦截器实例。只要 callback 行为相同，功能上可以工作；但实例数多、注入点多，排查和保证一致性更困难。

收敛到共享 OkHttpClient 后，401 拦截器也从多个实例变成一个实例。结构上等价于：

```
改前：任一业务 client 收到 401 -> 各自 interceptor -> 同一类 logout callback
改后：任一业务 Api 共用 client 收到 401 -> 单 interceptor -> 同一 logout callback
```

行为目标不变，结构更集中。

## 解决方案

### 方案一：共享 OkHttpClient + Retrofit，使用双重检查 lazy 初始化

将业务 API 工厂改成单例网络入口：

```kotlin
object NetworkClient {
    @Volatile private var sharedClient: OkHttpClient? = null
    @Volatile private var sharedRetrofit: Retrofit? = null

    fun install(config: NetworkConfig) {
        this.config = config
    }

    inline fun <reified T> create(): T {
        val retrofit = sharedRetrofit ?: synchronized(this) {
            sharedRetrofit ?: buildRetrofit().also { sharedRetrofit = it }
        }
        return retrofit.create(T::class.java)
    }

    private fun buildRetrofit(): Retrofit {
        val client = sharedClient ?: synchronized(this) {
            sharedClient ?: buildClient().also { sharedClient = it }
        }

        return Retrofit.Builder()
            .baseUrl(config.baseUrl)
            .client(client)
            .addConverterFactory(jsonConverter)
            .build()
    }
}
```

所有同 baseUrl 的业务 API 改为：

```kotlin
single { NetworkClient.create<ApiA>() }
single { NetworkClient.create<ApiB>() }
single { NetworkClient.create<ApiC>() }
```

这样多个业务接口共享同一个 `ConnectionPool`、DNS/TLS 复用状态、拦截器和 HTTP cache。

### 方案二：启动后台连接预热

应用启动后，在后台发起一个低风险 GET 请求，目的不是把数据塞进业务状态，而是让连接先建立：

```kotlin
applicationScope.launch(Dispatchers.IO) {
    runCatching {
        musicService.listTrendingSongs(limit = 50)
    }
}
```

预热请求的目标：

1. 建立 DNS 解析。
2. 完成 TCP/TLS handshake。
3. 完成 ALPN，建立 HTTP/2 连接。
4. 暖 OkHttp `ConnectionPool`。

预热请求的返回数据可以不进入页面 store，避免启动时污染业务状态。

### 方案三：配置 64MB HTTP cache，并显式声明协议

OkHttpClient 配置：

```kotlin
private fun buildClient(): OkHttpClient {
    return OkHttpClient.Builder()
        .cache(Cache(File(cacheDir, "api_http_cache"), 64L * 1024 * 1024))
        .protocols(listOf(Protocol.HTTP_2, Protocol.HTTP_1_1))
        .addInterceptor(tokenInterceptor)
        .addInterceptor(unauthorizedInterceptor)
        .connectTimeout(15, TimeUnit.SECONDS)
        .readTimeout(30, TimeUnit.SECONDS)
        .writeTimeout(30, TimeUnit.SECONDS)
        .build()
}
```

64MB 是客户端缓存容量配置，不代表一定命中。要命中 304 或本地缓存，还需要服务端为适合缓存的 GET 接口返回：

```http
Cache-Control: public, max-age=60
ETag: "..."
```

或其他符合业务语义的缓存头。

### 方案四：401 拦截器收敛到单实例

共享 client 后，401 处理也收敛到同一个 interceptor：

```kotlin
val unauthorizedInterceptor = Interceptor { chain ->
    val response = chain.proceed(chain.request())
    if (response.code == 401) {
        onUnauthorized()
    }
    response
}
```

这不是改变 401 行为，而是减少重复实例和重复 wiring。任何业务 API 收到 401，仍走同一个清会话和通知链路。

### 为什么这样修，而不是其他方式

**不只给单个慢接口优化**：慢接口只是暴露点。根因是所有同域名业务 API 的连接池碎片化。只修一个 API，其他页面仍会在各自首次请求时付建连成本。

**不创建多个按业务分组的 client**：除非 baseUrl、证书、header 契约或超时策略确实不同，否则同域名业务 API 应共享 client。过度拆分会重新引入连接池碎片。

**不把预热数据直接当页面缓存**：连接预热解决的是 DNS/TLS/连接池，不等于业务缓存。业务页面仍应按自己的状态流处理数据，避免启动预热污染页面逻辑。

**不宣称 HTTP cache 已经带来 warm <800ms**：客户端已配置 64MB cache，但是否命中取决于服务端缓存头。没有复测和响应头确认前，只能写成预期方向。

## 可迁移原则

### 1. 同 baseUrl 业务 API 默认共享 OkHttpClient

OkHttpClient 应被视为网络栈资源，而不是每个 Retrofit API 的临时对象。共享 client 才能共享 ConnectionPool、DNS、TLS session、HTTP/2 multiplexing 和 cache。

### 2. 冷启动慢要区分建连成本和业务耗时

`T0 -> T1 = 2148ms` 这类指标需要继续拆分：DNS/TLS/ALPN、后端处理、响应下载、JSON parse、UI 渲染。单例化和预热主要优化建连成本，不一定优化后端 query time。

### 3. 连接预热只应暖网络，不应污染业务状态

预热请求适合建立连接、TLS session 和 HTTP/2；返回数据是否进入页面状态，应由业务缓存策略决定。否则启动阶段可能引入难以解释的数据副作用。

### 4. HTTP cache 是双端协作契约

客户端配置 cache 只是半边。服务端必须提供 `Cache-Control`、`ETag` 或 `Last-Modified` 等语义，客户端才能 304 或本地命中。没有响应头，缓存容量再大也可能无效。

### 5. 性能收益要区分 measured 与 expected

已实测的是基线 2148ms；建连成本 300-500ms 是常见拆分和预期扣减依据；改后 1500-1700ms、warm <800ms 需要复测确认。没有复测就不能写成上线收益。

### 6. 拦截器单例化要证明行为等价

把 11 个 401 拦截器收成 1 个，不应改变“任一 API 401 都触发清会话”的行为。重构时要检查 callback 捕获、token provider、language provider 等依赖是否仍能取到最新值。

## 技术深问 Q&A

### Q1：为什么多个 Retrofit `single` 仍可能不是网络单例？

因为 `single` 只保证 DI 返回同一个 API 实例，不保证这些 API 底层共享 OkHttpClient。如果每个 API 构造时都 `OkHttpClient.Builder().build()`，连接池仍然是多个。

### Q2：OkHttpClient 为什么建议复用？

OkHttpClient 持有连接池、线程池、缓存和拦截器。复用它可以复用 socket、TLS session、HTTP/2 连接和缓存；频繁新建会浪费建连成本和内存。

### Q3：连接预热和 HTTP cache 有什么区别？

连接预热是提前建立网络通道，减少后续 DNS/TLS/ALPN 成本；HTTP cache 是复用响应内容或验证响应未变。前者即使响应不缓存也有价值，后者依赖服务端缓存头。

### Q4：显式配置 `Protocol.HTTP_2, HTTP_1_1` 有什么意义？

它明确告诉 OkHttp 优先尝试 HTTP/2，并允许回退 HTTP/1.1。HTTP/2 可以在同一连接上 multiplex 多个请求，但前提是连接池共享且 ALPN 协商成功。

### Q5：为什么 warm restart <800ms 只能写预期？

因为它依赖两件事：连接是否在启动预热后仍可复用，以及服务端是否返回可缓存响应头并命中 304。素材里没有改后复测数据，所以只能作为目标或预期。

### Q6：哪些 API 不应该强行共用同一个 client？

不同 baseUrl、不同证书 pinning、不同代理/超时策略、不同认证协议、SSE/WebSocket 长连接、图片加载等可能需要独立 client。单例化针对的是同 baseUrl、同协议契约的普通业务 REST API。
