# iOS 积分 L1 缓存链路断裂排查案例研究

> **技术域**：iOS 架构 / Swift / TCA / swift-dependencies / 移动端缓存
> **难度**：⭐⭐⭐⭐
> **关键词**：L1 缓存 / UserDefaults / AsyncStream / try? / 多级缓存 / 单一事实源 / 冷启动 / TCA / 缓存一致性
> **可迁移场景**：用户资料缓存、积分/会员状态、钱包余额、权限状态、登录会话、移动端冷启动首屏数据

---

## 场景与系统架构

某 iOS 应用将用户会话、积分和会员状态收敛到一个会话存储中，再通过 TCA Feature 和 SwiftUI 页面展示。为了让冷启动首帧尽量不显示默认占位，系统设计了多级缓存链路：

1. L1：本地轻量持久化，使用 `UserDefaults` 保存最近一次积分、会员状态和用户信息。
2. L2：进程内会话快照，应用运行期间作为同步读取的单一事实源。
3. L3：远端接口，通过网络刷新积分和会员详情。

理想行为是：杀进程冷启动后，L1 先提供上次已知值，初始化 L2；页面第一帧从 L2 读取真实缓存；随后 L3 异步刷新，再把新值写回 L2 和 L1，并通过状态流通知页面。

### L1/L2/L3 三级缓存链路图

```
L3 Remote API
├── getCurrentCredits()
└── getMembershipDetail()
        │
        ▼
refreshCreditsAndMembership()
├── credits 成功 -> setCredits(value)
├── membership 成功 -> setMembership(value)
└── 失败 -> 显式记录 / 保留旧缓存 / 可重试
        │
        ▼
L2 Session Store（进程内单一事实源）
├── user: User?
├── credits: Int?
├── isMember: Bool?
└── sessionStream: AsyncStream<SessionSnapshot>
        │
        ├── setter 写入内存 snapshot
        ├── setter 写入 L1 UserDefaults
        └── broadcast() 通知订阅者
        │
        ▼
L1 UserDefaults
├── userKey
├── creditsKey
└── membershipKey
        │
        ▼
冷启动 init
├── 读取 userKey
├── 读取 creditsKey
├── 读取 membershipKey
└── 构造首个 SessionSnapshot
        │
        ▼
TCA / SwiftUI 页面
├── Profile：用户、会员、积分
└── Create：顶部积分
```

这个链路的关键约束是：每个被声明为可持久化的字段，都必须满足三联关系：

```
init read  <->  setter write  <->  clear remove
```

任意一环缺失，L1 就会变成“看似存在、实际不可用”的缓存。

---

## 问题现象

用户侧表现集中在冷启动和跨页面展示：

1. 杀进程冷启动后，登录态下进入个人页，第一帧显示默认占位数据。
2. 个人页显示默认会员状态、`0` 积分和默认用户信息。
3. 创建页顶部积分也是 `0`。
4. 等待短时间后，部分数据可能被接口刷新覆盖，但首帧体验已经暴露出 L1 缓存未命中。

可观测排查结果显示，问题不只是“首帧慢”，而是 L1 持久化链路本身断裂：

| 字段 / 链路 | 观测结果 |
|---|---|
| 积分展示 | 冷启动显示 `0` |
| 会员展示 | 冷启动显示默认免费态 |
| 用户展示 | 冷启动显示默认用户信息 |
| `UserDefaults` 积分 key | 长期为空 |
| `UserDefaults` 会员 key | 长期为空 |
| 初始化读取 | 读不到可用 L1 值，只能构造默认快照 |

缓存问题最容易误判为接口慢。这里的关键判断是：如果 L1 真正可用，冷启动第一帧不应该依赖 L3 网络返回；它应该能展示上次已知值。

## 根因分析

### 根因一：初始化读取链路不完整，字段持久化矩阵缺项

会话存储初始化时，部分字段从 `UserDefaults` 读取，但用户字段没有纳入同一套持久化矩阵。伪代码可以简化为：

```swift
final class SessionStore {
    private var snapshot: SessionSnapshot

    init(defaults: UserDefaults) {
        let cachedCredits = defaults.object(forKey: creditsKey) as? Int
        let cachedIsMember = defaults.object(forKey: membershipKey) as? Bool

        self.snapshot = SessionSnapshot(
            user: nil,                  // ❌ 未从 L1 读取 user
            credits: cachedCredits,
            isMember: cachedIsMember
        )
    }
}
```

这导致用户信息在冷启动时永远回不到 L2。即使历史上登录成功并拿到过 user，只要 init 不读取，首个快照仍然是 `user = nil`，页面就会按默认用户渲染。

平台机制层面，这不是 `UserDefaults` 的性能问题，而是缓存 schema 与读写实现不一致：系统宣称 L1 保存会话字段，但初始化只读取了其中一部分字段。

### 根因二：刷新写入路径被双层 `try?` 静默切断

积分和会员状态长期不写入 L1，根因在刷新函数的错误处理方式。旧逻辑把远端请求包在 `try?` 里：

```swift
func refreshCreditsAndMembership() async {
    let creditsResult = try? await paymentClient.getCurrentCredits()
    let membershipResult = try? await paymentClient.getMembershipDetail()

    if let credits = creditsResult {
        await setCredits(credits)
    }

    if let membership = membershipResult {
        await setMembership(membership)
    }
}
```

`try?` 的语义是：表达式抛错时返回 `nil`，错误对象被丢弃。于是链路会变成：

```
getCurrentCredits() 抛错
└── try? 转成 nil
    └── if let credits 不进入
        └── setCredits 不调用
            └── UserDefaults.set 不执行
                └── 下次冷启动仍读不到 L1
```

同理，会员接口失败会让 `setMembership` 不执行。由于没有日志、没有错误上报、没有 fallback 标记，外部只能看到“缓存一直为空”，很难知道是接口失败、解码失败、鉴权失败，还是 setter 没被调用。

Swift 里的 `try?` 适合“失败可忽略且无副作用要求”的场景，例如尝试解析一个可选本地文件。但它不适合包住缓存写入前置链路，尤其不适合直接决定 `setCredits`、`setMembership` 这类持久化 setter 是否执行。

### 根因三：setter 是 L1/L2 一致性的唯一写入口，未调用就没有缓存

一个正确的 setter 不只是改内存字段，它通常还承担三件事：

```swift
func setCredits(_ credits: Int) async {
    snapshot.credits = credits                  // L2 内存快照
    defaults.set(credits, forKey: creditsKey)   // L1 持久化
    broadcast(snapshot)                         // 通知 UI 订阅者
}
```

因此 `setCredits` 没被调用，影响不是单点的：

1. L2 当前快照没有积分。
2. L1 `UserDefaults` 没有积分。
3. `AsyncStream` 订阅者收不到积分更新。
4. 下次冷启动仍然没有 eager init 数据。

这解释了为什么个人页和创建页会同时显示 `0`：它们不是两个页面各自坏了，而是共同依赖的缓存写入口没有被执行。

### 根因四：init / setter / clearSession 不一致会制造“伪 L1”

多级缓存最危险的状态不是“没有缓存”，而是“代码里有缓存读取，看起来像有缓存”。如果只看某几行 `UserDefaults` 读取，很容易误以为 L1 完整；但真正的完整性需要按字段做矩阵：

| 字段 | init read | setter write | clear remove | 结果 |
|---|---|---|---|---|
| user | 缺失 | 可能写入或由其他链路维护 | 可能清理 | 冷启动丢用户 |
| credits | 有读取 | 被 `try?` 链路阻断 | 有清理 | L1 长期为空 |
| isMember | 有读取 | 被 `try?` 链路阻断 | 有清理 | L1 长期为空 |

只有 read、write、remove 三列都闭合，字段才算真正接入 L1。否则会出现“初始化代码看似支持缓存，但运行时永远读不到有效值”的伪缓存。

## 解决方案

### 修复一：补齐字段持久化矩阵

对会话快照中的每个需要持久化字段，建立明确的读写清理关系：

```swift
struct SessionSnapshot: Codable {
    var user: User?
    var credits: Int?
    var isMember: Bool?
}
```

初始化时读取所有 L1 字段：

```swift
init(defaults: UserDefaults) {
    let cachedUser: User? = defaults.data(forKey: userKey)
        .flatMap { try? JSONDecoder().decode(User.self, from: $0) }

    let cachedCredits = defaults.object(forKey: creditsKey) as? Int
    let cachedIsMember = defaults.object(forKey: membershipKey) as? Bool

    self.snapshot = SessionSnapshot(
        user: cachedUser,             // ✅ user 也纳入 eager init
        credits: cachedCredits,
        isMember: cachedIsMember
    )
}
```

setter 写入 L2 与 L1：

```swift
func setUser(_ user: User?) {
    snapshot.user = user

    if let user {
        let data = try? JSONEncoder().encode(user)
        defaults.set(data, forKey: userKey)
    } else {
        defaults.removeObject(forKey: userKey)
    }

    broadcast(snapshot)
}
```

清理时删除所有对应 key：

```swift
func clearSession() {
    snapshot = SessionSnapshot(user: nil, credits: nil, isMember: nil)
    defaults.removeObject(forKey: userKey)
    defaults.removeObject(forKey: creditsKey)
    defaults.removeObject(forKey: membershipKey)
    broadcast(snapshot)
}
```

为什么这样修：L1 缓存不是“某个字段有读取”就算完成，而是每个字段必须有完整生命周期。用字段矩阵补齐后，冷启动、运行期刷新和登出清理才不会互相矛盾。

### 修复二：把 `try?` 改成显式错误处理，保留链路可观测性

刷新函数不应把所有错误折叠成 `nil`。更合理的写法是分别处理积分和会员接口，成功则写缓存，失败则记录并保留旧值：

```swift
func refreshCreditsAndMembership() async {
    do {
        let credits = try await paymentClient.getCurrentCredits()
        await setCredits(credits)              // ✅ 成功必写 L2/L1/stream
    } catch {
        NSLog("[Credits] refresh failed: \(error)")
        // 保留旧缓存，不把 L1/L2 改成默认 0
    }

    do {
        let membership = try await paymentClient.getMembershipDetail()
        await setMembership(membership)        // ✅ 成功必写 L2/L1/stream
    } catch {
        NSLog("[Membership] refresh failed: \(error)")
        // 保留旧缓存，可按业务决定是否重试
    }
}
```

这样修有三个直接收益：

1. 失败原因可见，能区分网络、解码、鉴权和服务端错误。
2. 单个接口失败不影响另一个字段刷新。
3. 旧缓存不会被静默丢弃，冷启动仍可展示上次已知值。

### 修复三：将“默认值”和“未知值”分开

积分显示 `0` 和积分未知不是一回事。缓存层应尽量用可选值表达未知：

```swift
struct SessionSnapshot {
    var credits: Int?     // nil = 未知；0 = 真实余额为 0
    var isMember: Bool?   // nil = 未知；false = 已确认非会员
}
```

UI 层再决定未知态展示：

```swift
switch snapshot.credits {
case .some(let credits):
    Text("\(credits)")
case .none:
    PlaceholderView()
}
```

为什么这样修：如果缓存 miss 直接落成 `0`，页面、日志和用户都无法区分“真实 0 积分”和“缓存链路断了”。把 unknown 建模出来，才能在冷启动和弱网下做正确兜底。

### 修复四：用 smoke test 验证冷启动首帧

缓存链路修复不能只看接口成功，必须验证 L1 是否真的能独立支撑首帧：

```
1. 登录并触发积分/会员刷新
2. 确认 UserDefaults 中 user / credits / membership 三类 key 非空
3. 杀进程
4. 断网或延迟 L3 接口
5. 冷启动进入相关页面
6. 第一帧显示 L1 上次已知值，而不是默认占位
7. L3 返回后再覆盖为最新值
```

为什么这样修：L1 的价值就是脱离网络支撑冷启动。只有在 L3 不可依赖时仍能显示上次已知值，才说明 L1 链路真正闭合。

### 为什么不采用其他修法

**不把页面默认值从 0 改成 500**：这只是硬编码掩盖问题，不能解决不同用户、不同会员态和真实余额变化。

**不只修 UI 的 loading 状态**：loading 可以改善观感，但无法让 L1 有数据。缓存写入链路断裂时，换 UI 不会让冷启动首帧获得真实值。

**不继续保留 `try?` 再补一个 fallback**：`try?` 已经丢掉错误上下文，fallback 也不知道发生了什么。缓存刷新链路需要可观测错误，才能判断是否重试、保留旧值或提示用户。

**不只补 init read，而不修 setter write**：如果写入路径仍然被吞错切断，下一次冷启动还是读不到值。init 和 setter 必须一起闭合。

## 可迁移原则

### 1. 多级缓存要按字段做 read/write/clear 矩阵

不要只问“有没有缓存”，要问每个字段是否具备 `init read`、`setter write`、`clear remove`。用户、积分、会员、权限、余额都应该逐字段验收。矩阵缺一列，就不是完整 L1。

### 2. `try?` 不适合包住关键写缓存路径

`try?` 会把错误折叠成 `nil`，适合失败无害的尝试性操作，不适合决定 setter 是否执行的主链路。凡是后面接 `setX`、`UserDefaults.set`、数据库写入、状态广播，都应显式 `do/catch`。

### 3. 冷启动首帧是 L1 缓存的验收标准

如果杀进程冷启动第一帧仍依赖网络，L1 就没有发挥作用。缓存验证应包含断网或延迟接口场景，确认页面能显示上次已知值。

### 4. 默认值和未知值必须分开

`0`、`false`、空字符串经常既可能是真值，也可能是 fallback。缓存层应使用 optional 或状态枚举区分 unknown，否则链路断裂会被伪装成合法业务值。

### 5. 单一事实源不等于单一入口

把状态收敛到一个 store 后，所有写入路径都必须经过同一组 setter。接口刷新、登录完成、用户资料更新、登出清理如果绕开 setter，就会造成 L1、L2 和 UI 订阅者不一致。

## 技术深问 Q&A

### Q1：为什么 `UserDefaults` 读到了 nil，不能直接说明用户没有缓存？

读到 nil 只能说明当前 key 没值。原因可能是从未写入、写入失败、key 不一致、clear 时删除了、编码失败，或者 init 根本没读对应字段。排查必须沿写入路径反向追踪。

### Q2：`try?` 到底危险在哪里？

危险不在语法本身，而在它会丢掉错误对象，把失败变成普通 nil。如果后续代码用 `if let` 决定是否写缓存，那么任何接口或解码错误都会静默变成“不写缓存”，外部没有可观测信号。

### Q3：为什么要把积分建模成 `Int?`，而不是默认 0？

因为 `nil` 表示未知，`0` 表示真实余额为 0。冷启动缓存 miss、接口失败、用户确实没有积分，这三种状态对 UI 和排查含义完全不同，不能混成同一个数字。

### Q4：L1 和 L2 谁是单一事实源？

运行期通常以 L2 进程内 store 作为单一事实源，L1 是启动恢复和持久化备份。L3 则是权威远端来源。数据流应是 L1 初始化 L2，L3 刷新 L2，再由 setter 同步回 L1。

### Q5：为什么修缓存要看 clearSession？

只看 read/write 会漏掉登出和切换账号。clearSession 如果少删某个 key，下个用户可能看到上个用户缓存；如果多删或时机错误，也会让冷启动失去上次已知值。清理是缓存生命周期的一部分。

### Q6：如何判断一个 L1 缓存方案真正闭合？

最小验证是：写入后能在 `UserDefaults` 看到 key；杀进程冷启动 init 能读回；断网首帧能展示上次值；远端刷新成功后能覆盖；登出后 key 被清理且 UI 收到清空事件。
