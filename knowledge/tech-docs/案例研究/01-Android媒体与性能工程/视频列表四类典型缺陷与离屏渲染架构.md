# 视频列表（RecyclerView + ExoPlayer）四类典型缺陷与离屏渲染架构

> **技术域**：Android 媒体与性能工程
> **难度**：⭐⭐⭐⭐⭐
> **关键词**：ExoPlayer / RecyclerView / StaggeredGridLayout / MediaCodec / AudioFlinger / Looper 绑定 / playWhenReady / SurfaceTexture / 离屏渲染
> **可迁移场景**：任何「列表内多卡同时播放视频」的需求（信息流、模板墙、短视频预览）

---

## 场景

模板列表页：StaggeredGridLayout 两列，每张卡片循环播放一段视频，可滑动浏览、可选中单卡控制音频。该场景同时承压 RecyclerView 回收复用、多路硬件解码、滑动帧率、音频混合，是移动端媒体工程的典型深水区。

四个缺陷相互独立、同期发现并修复，覆盖卡顿、漏播、串音、状态污染四类典型问题。

### 系统架构一览

```
TemplateAdapter (主线程)
├── RecyclerView + StaggeredGridLayoutManager (2 列)
├── 每个 ViewHolder 持有 TextureView → SurfaceTexture
├── PlayerManager (独立 HandlerThread)
│   ├── active: HashMap<SurfaceTexture, ExoPlayer>
│   ├── pool:   ArrayDeque<ExoPlayer> (max 10)
│   └── 所有 player 操作在 handler 线程执行
└── 状态：isScrolling / isMuted / selectedItemId
```

---

# 缺陷一 — ExoPlayer 主线程阻塞导致 fling 卡顿

## 问题现象

快速 fling RecyclerView，列表掉帧（< 30fps），卡顿集中在手指离开后的滑行期间。Profiler CPU trace 显示主线程有规律性 spike，每次 ViewHolder 进入回收流程时触发，持续 1–20ms。

## 根因：Android 线程模型 + ExoPlayer Looper 绑定

### Android 主线程的本质

主线程（UI 线程）是一个运行着 `Looper.loop()` 死循环的普通线程：

```
MainThread
└── Looper.loop()
      └── 死循环：取 MessageQueue 队头 → 分发 Handler → 执行 runnable
```

`Choreographer` 通过 VSYNC 信号每 16.6ms 往 MessageQueue 插一个"帧绘制"任务。队列中任何任务执行超过 16ms，该帧被跳过 → 用户感知卡顿。

### ExoPlayer 的内部架构

ExoPlayer 分两层：

```
ExoPlayerImpl（外壳，接收调用方命令）
     │ sendMessage(MSG_STOP / MSG_PREPARE / ...)
     ▼
ExoPlayerImplInternal（状态机，运行在 playback thread）
     │ 执行完毕后
     ▼
回调到 ExoPlayerImpl 的 eventHandler（哪个线程？）
```

**关键**：`eventHandler` 用的 Looper 由 `ExoPlayer.Builder.setLooper()` 决定。未调用时，默认取 `Looper.myLooper()`，即**构造 ExoPlayer 的那个线程的 Looper**。

### 主线程构造 ExoPlayer 时的阻塞路径

```kotlin
// 主线程构造（旧代码）：
val player = ExoPlayer.Builder(context).build()
// → setLooper 未调用 → eventHandler 绑定主线程 Looper

// ViewHolder 回收时主线程调用：
player.stop()
// → ExoPlayerImpl.stop()
// → 发 MSG_STOP 给 playback thread
// → playback thread 执行 MediaCodec.flush() + stop()（1–20ms）
// → 执行完毕回调 eventHandler（主线程 Looper）
// → 主线程在等待这个回调，此期间阻塞
```

`player.stop()` 并非纯异步——ExoPlayer 内部为保证状态一致性，会等 playback thread 的 `MSG_STOP` 处理完毕并回调 eventHandler 才返回。主线程等待 MediaCodec 硬件 flush，这是 1–20ms spike 的来源。

**MediaCodec flush 耗时的原因**：codec 可能有待解码的帧在 pipeline 里，flush 需要等 GPU 完成当前 EGL frame → 耗时与视频分辨率、SoC 性能正相关。高通 888 约 1–3ms，联发科低端机约 10–20ms。

快速 fling 时，每次 ViewHolder 离屏触发一次 `stop()`，8 个 ViewHolder 离屏 × 平均 5ms = **40ms spike**，连续 3 帧掉帧。

## 解决方案：离屏渲染架构（PlayerManager）

### 核心设计

```kotlin
class PlayerManager(private val context: Context) {
    // 独立线程，所有 player 操作在此执行
    private val thread = HandlerThread("player-mgr").apply { start() }
    private val handler = Handler(thread.looper)
    private val mainHandler = Handler(Looper.getMainLooper())  // 仅用于回调

    private val pool = ArrayDeque<ExoPlayer>()              // 仅 handler 线程访问
    private val active = HashMap<SurfaceTexture, ExoPlayer>() // 同上
    private val frameListeners = HashMap<ExoPlayer, Player.Listener>()
}
```

### 在 handler 线程构造 ExoPlayer

```kotlin
private fun buildPlayer(): ExoPlayer {
    // 此函数在 handler 线程内调用
    return ExoPlayer.Builder(context)
        .setLooper(thread.looper)   // ← eventHandler 也绑定 handler 线程
        .setLoadControl(lc)
        .build()
}
```

`setLooper(thread.looper)` 让 ExoPlayer 的状态回调也发到 handler 线程，player 的整个生命周期全在 handler 线程内闭环，彻底不经过主线程。

### detach 变成 fire-and-forget

```kotlin
fun detach(st: SurfaceTexture) {
    handler.post {  // ← 主线程执行到此立即返回，~μs
        active.remove(st)?.let { p ->
            frameListeners.remove(p)?.let { p.removeListener(it) }
            p.clearVideoSurface()   // MediaCodec flush，在 handler 线程等
            p.stop()
            p.clearMediaItems()
            returnToPool(p)
        }
        try { st.release() } catch (_: Throwable) {}
    }
}
```

主线程开销：`MessageQueue.enqueue()` = O(1)，约 0.3–2μs。MediaCodec flush 的等待转移到 handler 线程，主线程立即空闲。

### `frameListeners` 的内存泄漏防护

ExoPlayer 池复用时，若不清除旧 listener：
- 旧闭包持有旧 ViewHolder 的引用，ViewHolder 被 RecyclerView 回收但 GC 无法释放 → 内存泄漏
- 新视频的 `onRenderedFirstFrame` 触发时，旧 listener 也被调用 → 错误回调到已回收的 ViewHolder

detach 时 `frameListeners.remove(p)?.let { p.removeListener(it) }` 确保每个 player 回池前清除 listener。

### SurfaceTexture 所有权与 race condition

`TextureView.SurfaceTextureListener.onSurfaceTextureDestroyed` 必须返回 `false`：

```kotlin
override fun onSurfaceTextureDestroyed(surface: SurfaceTexture): Boolean {
    playerManager.detach(surface)
    return false  // 放弃 framework 的自动 release
}
```

返回 `true` 时：framework 在回调返回后立即调用 `st.release()`，同时 handler 线程正在 `clearVideoSurface()` 里访问 SurfaceTexture 的 native layer（EGLImageKHR）→ **use-after-free**，进程崩溃。

返回 `false` + PlayerManager 在 `clearVideoSurface()` + `stop()` 完成后 `st.release()` → 序列化，消除 race。

### N 个并发 ExoPlayer 的硬件资源上限

| SoC 级别 | 同时可用硬件 MediaCodec 实例 | 单 player 内存占用 |
|----------|----------------------------|------------------|
| 旗舰（骁龙 8 Gen2+）| 6–8 个 | ~15–30MB |
| 中端（骁龙 7 系列）| 3–4 个 | ~15–30MB |
| 低端（联发科 Helio G）| 2–3 个 | ~15–30MB |

超出上限后 ExoPlayer fallback 软件解码器（`OMX.google.xxx`），低端机解码 1080p 占 40–60% 单核 CPU，与主线程争抢 → 仍然卡顿。本场景 2 列 StaggeredGrid 最多 ~8 个可视 ViewHolder，低端机必然触发软解。

工程缓解：`DefaultLoadControl.setBufferDurationsMs(1_000, 5_000, 500, 1_000)` 把 maxBufferMs 从默认 50s 降为 5s，将每 player 网络 buffer 从 ~20MB 降到 ~2MB，总体内存降低 ~60%。

# 缺陷二 — SCROLL_STATE_IDLE 后可视 ViewHolder 遍历遗漏

## 问题现象

列表滑动停止后，当前一屏中部分卡片封面更新了（显示正确的模板图），但视频没有开始播放。慢速滑动、快速 fling 后均可复现。把整屏 item 完整露出后再松手则全部正常。

## 根因：RecyclerView 位置系统 + SGLM layout 时序

### RecyclerView 的四类"位置"

理解这个缺陷需要先清楚 RecyclerView 的位置概念：

| 位置类型 | 含义 | 更新时机 |
|----------|------|----------|
| **Adapter position** | Adapter 数据集下标，`notifyXxx` / `DiffUtil` 后立即变化 | 立即 |
| **Layout position** | LayoutManager 上次 layout pass 时记录的位置 | 下一次 layout pass |
| **Child index** | RecyclerView view hierarchy 里的序号（0 to childCount-1）| 实时，view attach/detach 时变化 |

Adapter position 和 Layout position 之间存在一帧到数帧的**延迟窗口**。在这个窗口内：
- `findViewHolderForAdapterPosition(i)` 查找的是 Adapter position
- LayoutManager 记录的是 Layout position
- 两者不一致时，`findViewHolderForAdapterPosition` 直接返回 null

### `findViewHolderForAdapterPosition` 的源码行为

```java
// RecyclerView.java（简化）
public ViewHolder findViewHolderForAdapterPosition(int position) {
    if (mDataSetHasChangedAfterLayout) {
        return null;  // 有 pending update，直接放弃查找
    }
    final int childCount = mChildHelper.getUnfilteredChildCount();
    for (int i = 0; i < childCount; i++) {
        final ViewHolder holder = getChildViewHolderInt(mChildHelper.getUnfilteredChildAt(i));
        if (!holder.isRemoved() && getAdapterPositionInRecyclerView(holder) == position) {
            return holder;
        }
    }
    return null;
}
```

`mDataSetHasChangedAfterLayout` 在任何 `notifyDataSetChanged()` / `DiffUtil.dispatchUpdatesTo()` 后被置为 `true`，直到下一次 layout pass 完成后清除。

如果列表在滑动过程中有任何数据更新（哪怕是后台静默刷新），IDLE 触发时此标志可能为 `true` → **全部返回 null** → 所有 ViewHolder 被 `continue` 跳过。

### SGLM GAP_HANDLING_NONE 的 layout 时序

`SCROLL_STATE_IDLE` 触发的时间轴：

```
t=0  手指松开，fling 动画开始
t=N  fling 速度衰减到 0
t=N  RecyclerView 内部：onScrollStateChanged(SCROLL_STATE_IDLE)
t=N  Adapter.setScrolling(false) 被调用  ← 旧代码在此时遍历
t=N+ SGLM 执行 gap check（GAP_HANDLING_NONE 下检查跨 span 的 gap）
t=N+ SGLM 若需要重排，requestLayout()
t=N+ Choreographer VSYNC → traversal → SGLM.onLayoutChildren() 完成
t=N+ 此后 findFirst/LastVisibleItemPositions 才稳定
```

旧代码在 `t=N`（IDLE 刚触发）调用 `findFirstVisibleItemPositions` / `findLastVisibleItemPositions`：

```kotlin
// 有缺陷的旧代码：
lm.findFirstVisibleItemPositions(first)   // t=N 时 SGLM layout 未完成
lm.findLastVisibleItemPositions(last)     // 返回的是旧的、可能偏小的位置

val firstPos = first.filter { it >= 0 }.minOrNull() ?: return
val lastPos  = last.maxOrNull() ?: return

for (i in firstPos..lastPos) {
    // 两个叠加问题：
    // 1. firstPos/lastPos 不准确，边缘 item 的 position 超出范围 → 根本不会遍历到
    // 2. findViewHolderForAdapterPosition 因 mDataSetHasChangedAfterLayout 返回 null
    val vh = rv.findViewHolderForAdapterPosition(i) as? VH ?: continue
    vh.tryAttachPending()
}
```

**两个问题叠加**：范围不准导致边缘 item 漏遍历，null 返回导致范围内的 item 也被跳过。结果：一屏 8 个 ViewHolder，可能只有 3–4 个被 attach。

### 正确修法：直接 child 遍历 + rv.post

```kotlin
rv.post {
    if (isScrolling) return@post  // guard：post 期间若再次滑动则放弃
    for (i in 0 until rv.childCount) {
        val vh = rv.getChildViewHolder(rv.getChildAt(i)) as? VH ?: continue
        vh.tryAttachPending()
    }
}
```

**`rv.post {}` 的语义**：把 runnable 投入主线程 `MessageQueue` 队尾。SCROLL_STATE_IDLE 的回调是当前 `MessageQueue` 消息，执行完毕后队列取下一条消息（即 `rv.post` 投入的 runnable）。到这时，Choreographer 的 VSYNC traversal（SGLM layout pass）已经在队列里排好，`rv.post` 的 runnable 在 traversal 后执行，SGLM 的重排已完成，child 列表稳定。

**`rv.childCount` / `rv.getChildAt(i)` 的语义**：直接读取 RecyclerView view hierarchy 里 attached 的 View 列表，不经过任何 position 转换，不依赖 SGLM 的 position 计算，不受 `mDataSetHasChangedAfterLayout` 影响。这是**读取 view tree 的当前物理状态**，是此场景下唯一可靠的遍历方式。

**为什么不影响 scrap cache**：RecyclerView 有多级缓存：
- `mCachedViews`（离屏 ViewHolder，`setItemViewCacheSize(8)` 控制）：已从 view hierarchy **detach**，不在 `childCount` 里
- `mRecyclerPool`（完全回收的 ViewHolder）：同上

`rv.childCount` 只包含真正在屏幕上 attached 的 ViewHolder，scrap cache 里的 ViewHolder 不会被误 attach。

**`if (isScrolling) return@post` 的必要性**：`rv.post {}` 投入队列后有约 1–2 帧延迟。如果用户在这段时间内再次开始滑动（`isScrolling` 重新置为 true），此时不应 attach（滑动中不播放），guard 防止这个窗口期的错误 attach。

# 缺陷三 — 全局静音广播导致所有卡片同时出声

## 问题现象

进入页面，所有卡片正常静音播放。选中某张卡片后点击 mute 按钮解除静音，**全部可视卡片同时发出声音**（多路音频叠加），而非只有选中卡出声。

## 设计意图（产品设计稿）

```
card1（选中态）: overlay + mute 按钮 → 控制自身音量
card2/3/4（非选中）: 无任何音频控件，始终静音播放
```

产品设计意图：多卡同时循环播放视频（纯视觉），只有选中卡的音频跟随用户操作。

## 根因：全局静音广播架构

### 旧实现

```kotlin
// PlayerManager（旧）
fun setGlobalMuted(muted: Boolean) {
    handler.post {
        globalMuted = muted
        val v = if (muted) 0f else 1f
        for (p in active.values) p.volume = v  // ← 所有 active player 同时设音量
    }
}
```

`active` 是当前所有已 attach 的 `<SurfaceTexture, ExoPlayer>` map，包含全部可视 ViewHolder 的 player。`p.volume = 1f` 逐个设置 → 每个 ExoPlayer 的 `AudioTrack` 都以满音量播放。

### Android 音频架构：为什么会叠加

```
ExoPlayer 1 → AudioTrack 1 ─┐
ExoPlayer 2 → AudioTrack 2 ─┤
ExoPlayer 3 → AudioTrack 3 ─┼─→ AudioFlinger (AudioMixer) → 硬件扬声器
ExoPlayer 4 → AudioTrack 4 ─┘
```

`AudioFlinger` 是 Android 的音频混合服务，运行在独立进程（`audioserver`）。多个 `AudioTrack` 同时以 `volume=1.0f` 播放时，`AudioMixer` 对 PCM 数据**线性叠加**：

```
output[i] = track1[i] + track2[i] + track3[i] + track4[i]
```

叠加后超过 `MAX_INT16` 的样本会被 clamp（hard clip），产生失真。Android 的 `AUDIO_STREAM_MUSIC` 有 AudioFocus 机制可以做 ducking，但 ducking 是对 stream 整体降音量，不能阻止同 stream 内多个 AudioTrack 的叠加。

实际用户听感：音量异常大 + 多段模板音乐同时播放的混乱感。

### 旧代码的第二个问题：tryAttach 对所有卡传同一 isMuted

```kotlin
// VH.tryAttach（旧）
private fun tryAttach(st: SurfaceTexture) {
    val url = currentUrl ?: return
    val delay = computeStaggerDelay()
    playerManager.attach(st, url, isMuted, delay) { ... }  // ← 所有卡用全局 isMuted
}
```

当 `isMuted = false`（用户已解除静音）时，新进入视口的非选中卡以 `muted=false` attach → attach 瞬间就有声音。即使后来再调 `setVolume(st, true)` 补救，attach 到补救之间有一个窗口期（`handler.post` 的排队延迟）→ 瞬间出声。

**attach 时就必须决定正确的初始音量**，不能先以错误音量 attach 再修正。

## 解决方案：职责分层 + 单卡精控

### 层次划分

```
PlayerManager 层：只暴露单卡 setVolume API，不做音量广播
Adapter 层：持有选中状态，决定哪张卡改音量
```

### PlayerManager：去掉广播，只更新状态 + 单卡 API

```kotlin
// 只更新内部状态，供 attach 新 player 时初始化音量
fun setGlobalMuted(muted: Boolean) {
    handler.post { globalMuted = muted }
}

// 单卡精控
fun setVolume(st: SurfaceTexture, muted: Boolean) {
    handler.post {
        active[st]?.volume = if (muted) 0f else 1f
    }
}
```

### VH：持有选中状态，attach 时按状态决定初始音量

```kotlin
internal var currentIsSelected: Boolean = false
internal val activeSurface: SurfaceTexture? get() = pendingSurface  // 只读暴露

private fun tryAttach(st: SurfaceTexture) {
    val url = currentUrl ?: return
    val delay = computeStaggerDelay()
    // 非选中卡始终以静音 attach，消除窗口期出声
    val attachMuted = if (currentIsSelected) isMuted else true
    playerManager.attach(st, url, attachMuted, delay) { ... }
}
```

### VH：选中状态切换时同步更新当前 player 音量

```kotlin
fun bindSelectionOnly(item: TemplateItem, isSelected: Boolean) {
    currentIsSelected = isSelected
    binding.selectedOverlay.visibility = if (isSelected) View.VISIBLE else View.GONE
    if (isSelected) {
        binding.btnMute.setOnClickListener { onMuteToggle(item.id) }
        binding.ctaCreate.setOnClickListener { onCreateCtaTapped(item.id) }
        // 切换为选中：按当前全局 mute 状态恢复音量
        pendingSurface?.let { playerManager.setVolume(it, isMuted) }
    } else {
        // 取消选中：立即静音
        pendingSurface?.let { playerManager.setVolume(it, true) }
    }
}
```

### Adapter.setGlobalMuted：只改选中卡

```kotlin
fun setGlobalMuted(muted: Boolean) {
    isMuted = muted
    playerManager.setGlobalMuted(muted)   // 仅更新 PlayerManager 内部状态
    val rv = boundRecyclerView ?: return
    for (i in 0 until rv.childCount) {
        val vh = rv.getChildViewHolder(rv.getChildAt(i)) as? VH ?: continue
        if (!vh.currentIsSelected) continue
        vh.activeSurface?.let { playerManager.setVolume(it, muted) }
        break  // 最多一张选中卡
    }
}
```

注意：遍历 `rv.childCount` 而非 Adapter 全部 item，原因同缺陷二——只操作当前真正可见的 ViewHolder，且规避 position 同步问题。

### 设计决策：为什么 `activeSurface` 用 getter 而非直接暴露 `pendingSurface`

```kotlin
internal val activeSurface: SurfaceTexture? get() = pendingSurface  // ✅ 只读
// internal var pendingSurface: SurfaceTexture?  // ❌ 直接暴露 setter
```

`pendingSurface` 是 ViewHolder 的生命周期状态，写入权只属于 `onSurfaceTextureAvailable` / `onSurfaceTextureDestroyed` 回调。Adapter 层只需要读取当前 surface 做音量控制，不需要写入权。`getter` 形式暴露保持封装性，Adapter 不能意外写入导致 surface 状态错乱。

# 缺陷四 — ExoPlayer 池复用时 playWhenReady 状态污染

## 问题现象

fling 后列表停止，当前一屏所有卡片中**部分卡片持续显示静态封面**，不显示视频画面。反复 fling 后不播放的卡片数量随机，与缺陷二（IDLE 遍历遗漏）症状相似，但缺陷二修复后仍可复现。

## 根因：ExoPlayer `pause()` 和 `stop()` 对 `playWhenReady` 的不同语义

### ExoPlayer 播放状态机

```
IDLE → (prepare) → BUFFERING → READY → ENDED
                                  ↑
                           playWhenReady = true → 自动播放
                           playWhenReady = false → 暂停，等待 play() 调用
```

`playWhenReady` 是一个独立的"意图"字段，与 player 的实际状态（BUFFERING / READY）正交：
- `player.play()` → `playWhenReady = true`
- `player.pause()` → `playWhenReady = false`
- `player.stop()` → 回到 IDLE 状态，**但不改变 playWhenReady**

这个设计意图是：stop 后再次 prepare，player 能"记住"上次是否在播放。但在 pool 复用场景下，这个"记忆"变成了缺陷。

### Pool 复用的状态污染链

```
生命周期                   playWhenReady 的变化
──────────────────────────────────────────────────
buildPlayer()              → true（buildPlayer 显式设置）
player.prepare()           → 不变，仍 true
player 开始播放            → true（正常播放中）
pauseAll() → player.pause()→ false  ← 污染点
onSurfaceTextureDestroyed  ↓
detach() →
  player.clearVideoSurface() → 不变，仍 false
  player.stop()              → 不变，仍 false（stop 不重置！）
  player.clearMediaItems()   → 不变，仍 false
  returnToPool(player)       ← pool 里的 player 带着 false 状态

新 VH 出现在视口
attach() → borrow()        → 得到 playWhenReady=false 的 player
player.volume = ...        → 不改 playWhenReady
player.setVideoSurface()   → 不改 playWhenReady
player.setMediaItem()      → 不改 playWhenReady
player.prepare()           → 不改 playWhenReady
player 进入 READY 状态     → 但 playWhenReady=false → 不播放！
onRenderedFirstFrame 永不触发 → TextureView.alpha 停在 0
```

### 为什么缺陷二修复后仍出现

缺陷二（IDLE 遍历遗漏）修复后，`rv.post { tryAttachPending() }` 确保了所有可见 ViewHolder 都调到 `tryAttach()`，`playerManager.attach()` 也被调到。但 `attach()` 借出的 pool player 可能带着 `playWhenReady = false`，`prepare()` 后进入 READY 仍不播放。两个缺陷表现相同，是叠加关系：缺陷二修了"谁没被 attach"，缺陷四是"attach 了也不播"。

## 解决方案：在 `attach()` 借出后立即重置

```kotlin
fun attach(
    st: SurfaceTexture,
    url: String,
    muted: Boolean,
    delayMs: Long,
    onFirstFrame: () -> Unit,
) {
    handler.postDelayed({
        if (active.containsKey(st)) return@postDelayed
        val player = borrow()
        player.playWhenReady = true  // ← 唯一修改：消除 pool 状态污染
        player.volume = if (muted) 0f else 1f
        player.setVideoSurface(Surface(st))
        // ...
        player.setMediaItem(MediaItem.fromUri(url))
        player.prepare()
        active[st] = player
    }, delayMs.coerceAtLeast(0L))
}
```

**为什么不放在 `borrow()` 里**：`borrow()` 是纯 pool 取出操作，不含播放语义。`attach()` 才是"意图播放"的语义边界，在此重置语义最清晰。

**为什么不放在 `returnToPool()` 里（提前重置）**：pool 里 player 处于 IDLE 状态，`playWhenReady` 在 IDLE 下无意义。借出时重置是"最晚但恰好合适"的时机，不会有多余的状态转换。

**`resumeAll()` 无法解决此问题**：`resumeAll()` 调 `active[st].play()`，但新借出的 player 在 attach 的 postDelayed 执行前还没进入 `active`，`resumeAll()` 根本遍历不到它。

## 可迁移原则

抽离自四个缺陷的通用工程规律，适用于任何「列表内多媒体播放」场景：

1. **媒体对象的生命周期操作不要跨线程触发隐式阻塞**：ExoPlayer / MediaPlayer 等带 playback thread 的对象，构造时用 `setLooper` 绑定到专用线程，让所有命令与回调在该线程闭环，主线程只投递 fire-and-forget 消息。判断点：任何在主线程调用、内部会等硬件（codec flush / surface 释放）的 API，都是潜在 spike 源。

2. **RecyclerView 取"当前可见项"只信 view hierarchy 物理状态**：滑动停止后遍历用 `rv.childCount` + `getChildAt(i)`，不要用 `findViewHolderForAdapterPosition`（受 `mDataSetHasChangedAfterLayout` 与 layout 时序影响会返回 null）。需要等 layout 稳定时用 `rv.post {}` 把操作排到下一个消息循环，且加 `isScrolling` guard 防窗口期。

3. **多路音频默认全静音，只对"焦点对象"开声**：系统音频混合器对多个满音量 AudioTrack 做线性叠加 + hard clip，不会自动只播一路。控制权必须在应用层——非焦点卡 `volume=0f`，且**在 attach 那一刻就传入正确初始音量**，不能先错后补（异步补救存在窗口期）。

4. **对象池复用前，显式重置所有"有记忆"的状态字段**：`stop()` 不重置 `playWhenReady` 这类正交意图字段。凡是池化复用的对象，借出时（而非归还时）显式重置到已知初值，避免上一次使用的状态污染下一次。

5. **同症多因要分别验证，不能一个修复掩盖另一个**：缺陷二与缺陷四症状完全相同（部分卡不播），但根因不同、叠加存在。修完一个仍复现时，第一反应应是"还有第二个根因"，而非"上一个没修好"。

6. **诊断从 Profiler 实测出发，不凭症状猜根因**：卡顿先抓 CPU trace 看主线程 spike 的函数名与调用栈，拿到 `MediaCodec.flush()` 在主线程的证据，才能定位到 Looper 绑定而非误入 layout 方向。

## 技术深问

**Q: 这几个缺陷的发现顺序和排查策略？**

> 缺陷一（卡顿）最先感知到，但排查顺序上**不能凭症状猜**。第一步必须跑 Profiler 抓 CPU trace，看主线程 spike 的函数名。拿到 `MediaCodec.flush()` 在主线程的调用栈，才能确认根因是 ExoPlayer Looper 绑定而非 layout 问题。缺陷二在修完缺陷一后真机验证时发现（某些卡停止后不播放）。缺陷三在真机测试 mute 功能时发现（所有卡同时出声）。没有 Profiler 就没有缺陷一的正确方向，这是媒体 + RecyclerView 场景的通用排查原则。

**Q: `rv.post {}` 真的能保证在 SGLM layout 完成之后执行吗？**

> 有概率保证，不是绝对保证。`rv.post {}` 投入 MessageQueue 队尾，Choreographer 的 VSYNC traversal（layout pass）是以 `postFrameCallback` 形式注册的，优先级高于普通 `post`。实际执行顺序：当前消息（IDLE 回调）→ Choreographer traversal（layout）→ `rv.post` 的 runnable。在绝大多数设备上这个顺序成立。极端情况（系统负载极高，VSYNC 延迟）下顺序可能不一致，但即使 layout 未完成，`rv.childCount` 基于 view hierarchy 物理状态仍然可靠——最坏情况是少遍历了刚进入视口的 1–2 个 ViewHolder，下次滑动后会自动补 attach。

**Q: setItemViewCacheSize(8) 的 8 个离屏 ViewHolder 不会被误 attach，怎么确认？**

> RecyclerView 的 `mCachedViews`（即 scrap cache）里的 ViewHolder，在进入 cache 时会调用 `detachRecycledViewFromParent(holder)` 从 view hierarchy detach。detach 后不在 `rv.getChildAt(i)` 的遍历范围内。可以通过打 breakpoint 或 `rv.childCount` vs `recycledViewPool.getRecycledViewCount(viewType)` 的值差异来验证。`childCount` 只计 attached child，pool 不计入。

**Q: 为什么 attach 时必须决定正确音量，不能先 attach 再 setVolume？**

> `playerManager.attach(st, url, muted, delay)` 和后续的 `playerManager.setVolume(st, muted)` 都是 `handler.post {}` 异步执行。handler 线程是单线程 Looper，两个 post 会按顺序执行，看起来没问题。但 `attach` 内部有 `postDelayed(delayMs)`（stagger delay），而 `setVolume` 是普通 `post`。若 delayMs > 0，`setVolume` 会比 `attach` 先执行（setVolume post 在队列，delayed attach 还没到时间），`active[st]` 还不存在 → `setVolume` 什么都不做 → attach 后仍以错误音量播放。attach 时传正确的初始音量是唯一可靠的方式。

**Q: AudioFlinger 的 hard clip 和 ducking 有什么区别？**

> Hard clip：PCM 样本叠加超过 MAX_INT16 后截断，产生波形失真（听感：爆音）。Ducking：AudioFocus 机制，当某个 AudioTrack 获得 focus 后，其他同 stream 的 AudioTrack 降低 volume（通常到 0.2f）。Ducking 针对的是不同 AudioTrack 之间的优先级，而非叠加量。多路同时以 volume=1.0f 播放的 AudioTrack 没有 focus 竞争关系，AudioFocus ducking 不会介入，结果是多路线性叠加 + hard clip。正确做法是在应用层控制：非选中卡 volume=0f，只有选中卡给非零音量。

**Q: ExoPlayer 的 `stop()` 和 `pause()` 对 `playWhenReady` 的影响有什么区别？为什么这在 pool 复用场景里是缺陷？**

> `pause()` 显式设 `playWhenReady = false`；`stop()` 把 player 回到 IDLE 状态但**不改变** `playWhenReady`——这是 ExoPlayer 的设计：stop 后再 prepare，player"记住"上次是在播还是在暂停，可以无缝恢复。但这个"记忆"在 pool 复用里变成了状态污染：先 `pause()` 再 `stop()` 回池的 player，`playWhenReady` 是 `false`，新 ViewHolder 借出后 `prepare()` 进入 READY 但不播放，`onRenderedFirstFrame` 永不触发，TextureView alpha 停在 0。修法：在 `attach()` 借出 player 后立即 `player.playWhenReady = true`，消除 pool 里的状态污染。这个缺陷和缺陷二（IDLE 遍历遗漏）症状完全一样（部分卡不播放），但根因不同，表现为缺陷二修完后仍可复现——这类"同症多因"的缺陷是排查里最容易误判的。
