# 观察系统条件读取与依赖追踪失稳

> **技术域**：iOS TCA 架构实践  
> **难度**：⭐⭐⭐⭐⭐  
> **关键词**：SwiftUI / TCA / Perception / Observation / 动态依赖追踪 / early return / 首次交互失效  
> **可迁移场景**：细粒度状态观察、派生视图、响应式渲染闭包、Vue/MobX/Compose Snapshot 中的条件读取

---

## 一、场景与系统架构

某 iOS 页面由 TCA Store 提供列表、页签和播放状态。UIKit 适配层通过 `withPerceptionTracking` 执行一次状态应用；闭包读取到的可感知字段发生变化时，`onChange` 再次建立观察。页面刷新、切换页签时会走重置分支并提前返回，普通交互则继续同步暂停状态。

```text
TCA Store（feedItems / isPaused / longPressTargetId ...）
        │ 状态读取
        ▼
withPerceptionTracking { applyState(state) }
        │ 本次实际访问的 key path
        ▼
Observation Registrar（当前依赖集合）
        │ 被追踪字段变化
        ▼
onChange → observeStoreChanges() → 下一轮 applyState
        │
        └─ 页签切换或刷新完成 → reset → early return
```

同一技术栈里还有两类相近但不同的问题：整个 SwiftUI `body` 没进入追踪作用域，或者被 SwiftUI 保存后延迟执行的闭包逃出了原作用域。本案例的特殊之处是：追踪作用域已经存在，状态也确实在闭包中读取，但控制流使每一轮读取集合不一致。

## 二、问题现象

真机上的稳定复现序列是：先触发一次会进入重置分支的状态变化，再点一次静音或暂停，界面第一次没有响应；随后操作另一个仍被观察的控件，前一次状态突然一起生效。也就是说，业务状态已经改变，缺失的是以该字段变化为触发器的视图应用。

可核验的时间与行为证据如下：

- 首轮排查曾把问题视为偶发，只增加运行探针，没有识别动态依赖集合；约两周后，用户给出精确操作顺序才稳定定位。
- 故障轮次中，`applyState` 会执行到列表读取和重置分支，然后提前返回；暂停字段位于返回语句之后，没有发生 getter 访问。
- 单独改变暂停字段时 `onChange` 不执行；再改变列表等仍在集合内的字段后，闭包重新运行并读取当前暂停值，于是表现为“碰一下别的控件就恢复”。

这组证据排除了点击事件丢失、Reducer 未更新和随机线程竞争：如果 action 没有生效，后续无关重绘不应自动呈现正确的暂停状态；如果只是渲染延迟，也不应严格依赖另一个被追踪字段变化。

## 三、根因分析

### 3.1 追踪的是本轮访问，不是历史字段并集

Observation/Perception 的细粒度观察依赖 getter 访问。追踪闭包运行时，系统记录实际读取过的 key path，并为这些访问建立下一轮失效条件。它不是“扫描函数源码后找出所有可能字段”，也不会把历次运行的读取结果永久求并集。

可把第 `n` 轮依赖集合写成：

```text
D(n) = AccessedKeyPaths(run(n))

正常路径：D(1) = { feedItems, isPaused, longPressTargetId, ... }
重置路径：D(2) = { feedItems, ... }  ← return 后字段没有 getter 访问
```

当 `D(2)` 成为当前追踪依据后，`isPaused` 的变化不再命中依赖集合，因此不会触发下一轮闭包。只有 `feedItems` 等尚在 `D(2)` 中的字段变化，才会再次执行闭包。若那次执行走完整路径，`isPaused` 才重新加入集合。

这也解释了为什么探针容易误导：日志能证明闭包某些时候读过暂停状态，却不能证明**最近一次建立观察时**读过。仅统计函数调用次数或 action 次数，看不到依赖集合随控制流被替换的关键事实。

### 3.2 有包裹不等于稳定观察

顶层追踪容器解决的是“访问是否发生在追踪上下文中”；延迟闭包单独包裹解决的是“访问发生时追踪上下文是否仍有效”；本案例还要求“每一种控制流都读取所有应触发重跑的字段”。三者分别对应作用域存在、作用域时机和依赖集合稳定性，不能互相替代。

### 3.3 early return 同时造成触发丢失与本地镜像滞后

旧实现不仅把字段踢出追踪集合，还可能跳过本地 `isPaused` 镜像的同步。后续即使因其他字段而重跑，也会比较一个过期镜像。修复必须同时保证：关键字段在返回前被读取，以及重置路径需要的本地缓存也在返回前更新。

## 四、解决方案

### 4.1 旧代码：关键读取受控制流支配

```swift
withPerceptionTracking {
    self.applyState(store.state)
} onChange: {
    self.observeStoreChanges()
}

func applyState(_ state: State) {
    let items = Array(state.feedItems)       // ✅ 本轮始终读取，持续被追踪

    if tabChanged || refreshCompleted {
        reset(with: items)
        return                              // ❌ 截断点：下方字段退出本轮依赖集合
    }

    if isPaused != state.isPaused {         // ❌ 仅完整路径读取
        isPaused = state.isPaused
        updatePlayback(paused: isPaused)
    }
}
```

问题不在 `if` 本身，而在“是否需要触发整轮状态应用”与“某分支当前是否消费字段”被写成了同一个条件。

### 4.2 新代码：先建立稳定依赖快照，再执行分支

```swift
func applyState(_ state: State) {
    // ✅ 无条件读取：这些字段的变化都必须触发下一轮 applyState
    let paused = state.isPaused
    let longPressID = state.longPressTargetId
    let items = Array(state.feedItems)

    if tabChanged || refreshCompleted {
        isPaused = paused                   // ✅ return 前同步必要的本地镜像
        reset(with: items)
        return
    }

    if isPaused != paused {                 // ✅ 消费稳定快照，不再新增条件依赖
        isPaused = paused
        updatePlayback(paused: paused)
    }

    updateLongPressTarget(longPressID)
}
```

这里的局部常量不是性能优化，而是依赖声明：在函数入口无条件触发 getter，保证所有返回路径得到一致的关键依赖集合。只应提前读“变化后确实需要重跑”的字段，避免把整个 State 粗暴读取成大依赖，丢失细粒度观察的收益。

### 4.3 验证矩阵

修复验证不能只覆盖完整路径，应按“上一轮控制流 × 下一次变化字段”组合测试：

| 上一轮路径 | 下一次变化 | 预期 |
|---|---|---|
| 普通路径 | `isPaused` | 立即再次应用状态 |
| 重置并提前返回 | `isPaused` | 仍立即再次应用状态 |
| 重置并提前返回 | `longPressTargetId` | 仍立即再次应用状态 |
| 任意路径 | 未声明为渲染依赖的字段 | 不产生无关重跑 |

诊断时可在追踪闭包入口、每个返回点和字段 getter 附近记录同一轮次标识。关键问题不是“字段是否曾经读过”，而是“最后一次闭包结束前，哪些字段实际读过”。

## 五、可迁移原则

1. **把动态依赖集合当作每轮重建的订阅表**：适用于 Observation、Perception、MobX autorun、Vue effect 和读取驱动的响应式系统。审查重点是最近一次执行路径，而不是源码中出现过哪些字段。
2. **所有提前退出点都要做依赖完整性审查**：对 `return`、`guard`、条件 ViewBuilder、异常分支逐一询问：“这个字段变化是否仍应触发重算？”若答案为是，就必须在退出点前读取。
3. **区分追踪作用域缺失、延迟闭包逃逸和条件读取失稳**：三者症状都可能是 UI 不刷新，但修复位置分别在外层容器、延迟闭包内部和控制流入口。
4. **探针要记录因果链，而非只有结果日志**：至少关联闭包轮次、所走分支、关键字段读取和回调触发；否则“函数运行过”无法证明订阅仍存在。
5. **局部快照只覆盖必要字段**：无条件读取是显式声明失效条件，不应演变成读取整个对象。该原则同样适用于 Compose 中在组合阶段读取 Snapshot 状态、Vue/MobX 中 effect 的条件访问；具体 API 不同，但动态访问决定依赖的风险相同。

## 技术深问

**Q1：为什么字段变化后，追踪系统不能自动发现源码里稍后会读取它？**

因为细粒度观察依赖运行时 getter 访问，而非静态控制流分析。字段若不在当前访问集合中，系统没有订阅它，也就没有启动下一轮执行的信号；“下一轮本来会读到”无法自举出下一轮。

**Q2：把 `State` 先整体复制到局部变量，能否一次性解决？**

不一定。复制容器是否触发各字段 getter 取决于状态表示与宏生成方式，而且粗粒度读取可能让任意变化都触发重跑。更可靠的做法是逐个读取真正决定渲染或副作用同步的字段，让依赖边界可审查。

**Q3：为什么增加日志后仍可能长期无法定位？**

普通日志通常记录 action、最终值或闭包是否执行，却不记录本轮访问集合。该缺陷的关键证据是“最近一轮在何处返回、返回前读了哪些字段”。没有轮次和分支关联，成功路径的读取日志会掩盖失败路径的缺失读取。

**Q4：能否依靠静态检查禁止观察闭包中的 early return？**

一刀切会产生大量误报，因为有些返回后的字段变化本就不需要重跑。更实际的方式是把关键依赖集中到入口快照，并用路径组合测试验证；静态规则可提示存在提前退出，但最终仍需语义审查。
