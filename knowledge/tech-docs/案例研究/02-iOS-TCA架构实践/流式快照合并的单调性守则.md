# 流式快照合并的单调性守则

> **技术域**：iOS TCA 架构实践  
> **难度**：⭐⭐⭐⭐⭐  
> **关键词**：SSE / TCA / Reducer / 累计快照 / 单调状态 / non-empty-wins / 重连 / 字段级合并  
> **可迁移场景**：生成任务进度、协同编辑、断线恢复、分页聚合、离线同步、服务端状态投影

---

## 一、场景与系统架构

某多阶段生成流程通过 SSE 反复发送状态快照。客户端的 TCA Reducer 将快照投影为十个阶段的预览状态：已解锁阶段数、输入参数、场景列表、镜头列表、图片字典和视频片段字典等。重连时会重放累计快照，而完成态或恢复接口可能只返回精简字段。

```text
初次连接 ─┐
重连重放 ─┼─> 解码成功的 Snapshot ─> Reducer 字段级 merge ─> State ─> SwiftUI
恢复接口 ─┘                              │
                                       ├─ 进度：max
                                       ├─ 集合：non-empty-wins
                                       └─ 标量：有值且有效才覆盖
```

关键约束是：快照“较晚到达”不代表“信息更完整”。传输顺序、业务版本和字段完备度是三个不同维度，因此不能把整个状态对象交给 last-write-wins。

## 二、问题现象

风险集中在三类可见回退：

- 已经解锁到后续阶段，重连重放了一份较早快照，页面重新被锁回前一阶段。
- 已累积的场景、镜头或媒体字典被完成态精简快照中的空数组、空字典冲掉，预览区突然消失。
- 已拿到的最终合成所需输入被缺字段或空字段覆盖，后续合成无法构造完整输入。

源码可核验的结构证据是：流程包含 **10 个阶段**；阶段解锁采用 `max`；场景列表、镜头列表以及两个媒体字典均只在非空时覆盖；关键媒体输入只在存在且核心 URL 非空时写入。这里没有可诚实引用的线上耗时或故障量，因此验收应采用状态 trace，而非杜撰性能数字：

```text
t0  stage=7, sceneDrafts=[A,B], clips={0:C0}, mediaInput=valid
t1  重连旧快照：stage=5, sceneDrafts=[], clips={}, mediaInput=nil

整对象覆盖：stage=5, sceneDrafts=[], clips={}, mediaInput=nil       ❌ 真值回退
字段级合并：stage=7, sceneDrafts=[A,B], clips={0:C0}, input=valid ✅ 保持单调
```

## 三、根因分析

### 3.1 SSE 保证到达，不保证每份快照都比本地状态新且完整

同一连接内事件通常有序，但断线重连可能从检查点重放；不同接口生成的“运行中累计快照”和“完成态摘要”也可能使用不同字段集合。即使每份 JSON 都成功解码，仍不能推出后到者在所有字段上都更权威。

因此问题发生在 decode 之后：语法正确只证明载荷可读，不证明它适合整体替换当前领域状态。

### 3.2 Reducer 的赋值语句隐含了冲突解决策略

在 TCA 中，Reducer 串行处理 action 能消除同时写内存的数据竞争，却不会自动解决事件的语义乱序。每一句 `state.field = incoming.field` 都是在声明“后到值拥有最高优先级”。若服务端的空集合代表“本快照省略”而不是“权威清空”，这个声明就是错误的。

这与线程安全无关：即便所有 action 严格串行，错误的 last-write-wins 仍会稳定地产生状态回退。

### 3.3 不同字段属于不同的合并代数

| 字段类别 | 领域含义 | 合并规则 | 身份元 |
|---|---|---|---|
| 阶段进度 | 已经达到的里程碑 | `max(old, new)` | 0 |
| 累积集合 | 已获得的场景、镜头、媒体映射 | incoming 非空才替换 | 空集合表示无新增信息 |
| 可选标量 | 输入、语言、提示词等 | non-nil / 非空才覆盖 | `nil` 或空串表示未知 |
| 成对约束字段 | 只有组合完整才可消费 | 全部有效时原子覆盖 | 任一缺失均不提交 |

阶段进度天然是偏序：7 包含“已达到 1…6”的信息，旧快照中的 5 不能推翻它。集合字段则更微妙：当前协议把空集合用作省略或尚未生成，因此采用 non-empty-wins；如果业务确实需要清空，必须增加显式清空语义，不能继续重载空集合。

### 3.4 单调合并不是“所有值只增不减”

真正目标是知识不回退，而不是数值永远增大。用户可编辑的提示词可能合法变为空，服务器也可能撤销某个资源。此类字段不能机械套用 non-empty-wins，应携带版本号、操作类型或权威来源，再按领域规则解决冲突。

换言之，单调性针对的是“已确认事实”：已完成阶段、已生成资产、已验证输入。可撤销意图必须另建协议通道。

## 四、解决方案

### 4.1 旧代码：整包后写覆盖

```swift
func applySnapshot(_ incoming: Snapshot, to state: inout ViewState) {
    state.reachedStage = incoming.reachedStage       // ❌ 乱序快照令阶段回退
    state.sceneDrafts = incoming.sceneDrafts ?? []   // ❌ 缺字段被翻译成清空
    state.shotDrafts = incoming.shotDrafts ?? []
    state.clipMap = incoming.clipMap ?? [:]          // ❌ 精简完成态冲掉累计资产
    state.mediaInput = incoming.mediaInput           // ❌ nil 覆盖已确认输入
}
```

这里把 `nil`、空值、显式清空和值缺失混成一种含义，也让所有字段被迫共享同一冲突策略。

### 4.2 新代码：按字段语义合并

```swift
func mergeSnapshot(_ incoming: Snapshot, into state: inout ViewState) {
    if let candidate = incoming.reachedStage {
        state.reachedStage = max(state.reachedStage, candidate)
        // ✅ 里程碑只前进，不因重放旧快照回退
    }

    if let scenes = incoming.sceneDrafts, !scenes.isEmpty {
        state.sceneDrafts = scenes
        // ✅ 当前协议中 [] 表示“本快照没有完整数据”
    }
    if let shots = incoming.shotDrafts, !shots.isEmpty {
        state.shotDrafts = shots                      // ✅ non-empty-wins
    }

    if let clips = incoming.clipMap, !clips.isEmpty {
        state.clipMap = clips                         // ✅ 保住累计媒体真值
    }

    if let input = incoming.mediaInput,
       let source = input.sourceURL, !source.isEmpty {
        state.mediaInput = input                      // ✅ 有值且核心字段有效才覆盖
    }
}
```

### 4.3 组合字段必须原子提交

```swift
if let layout = incoming.visualLayout, !layout.isEmpty,
   let style = incoming.styleDescription, !style.isEmpty {
    state.visualLayout = layout
    state.styleDescription = style
    // ✅ 两者共同构成可消费配置，避免半新半旧的撕裂状态
}
```

若先写入其中一个字段，视图可能在两次 action 之间观察到不满足业务约束的组合。TCA 保证 Reducer 内同步修改的原子可见性，前提是开发者把相关字段放在同一次有效性检查中提交。

### 4.4 为“清空”建立独立协议语义

non-empty-wins 会有意拒绝空集合，因此必须定义真正删除时的表达：

```swift
enum CollectionPatch<Element: Equatable>: Equatable {
    case omitted                 // ✅ 没有新信息
    case replace([Element])      // ✅ 可包含空数组，表示权威清空
}

switch incoming.sceneDraftPatch {
case .omitted:
    break
case let .replace(items):
    state.sceneDrafts = items
}
```

长期看，服务端版本号、快照序号或字段级 patch 比启发式判断更可靠；但在协议明确把空集合当“未填充”时，字段级守卫是成本最低且与真实数据兼容的修复。

### 4.5 测试矩阵

| 当前状态 | 入站快照 | 期望 |
|---|---|---|
| stage 7 | stage 5 | 保持 7 |
| stage 7 | stage 8 | 前进到 8 |
| scenes `[A,B]` | `[]` 或缺字段 | 保持 `[A,B]` |
| scenes `[A,B]` | `[A,B,C]` | 替换为新非空集合 |
| 有效输入 | nil / 核心 URL 为空 | 保持有效输入 |
| 布局与样式均有效 | 只到达新布局 | 两字段均不更新 |
| 有效集合 | 显式 `replace([])` | 权威清空 |

测试还应交换同一组快照的到达顺序，验证最终“已确认事实”一致。对于可交换字段，可进一步做性质测试：`merge(merge(s,a),b)` 与 `merge(merge(s,b),a)` 应产生相同的单调部分。

## 五、可迁移原则

1. **解码成功不等于可以整体覆盖**：流式、重连和多来源同步都应在领域边界定义 merge，而不是让 wire model 直接替换 UI state。
2. **每个字段都要显式选择冲突策略**：进度用 `max`，累计集合用 non-empty-wins，可选标量用有效值覆盖，组合字段原子提交。
3. **空值与删除必须分开编码**：若空集合既表示省略又表示清空，客户端不可能可靠合并；引入 patch 枚举、存在位或版本化操作。
4. **串行执行不保证语义新鲜度**：Reducer、actor 或串行队列只解决内存并发，不会替你判断哪个事件更权威。
5. **单调规则只保护不可逆事实**：用户意图、可撤销资源和纠错结果需要版本或显式操作，不能盲目“只增不减”。
6. **用乱序排列测试合并律**：不要只测理想顺序；重放旧快照、精简快照、空字段和重复事件才是核心回归集。

## 技术深问

**Q1：为什么不比较整份快照的时间戳，只接受最新的？**

单一时间戳要求所有来源共享可靠时钟和完整版本关系，而且较新的精简快照仍可能缺少旧快照中的字段。时间戳可过滤明确陈旧事件，但不能替代字段级完备度判断。

**Q2：non-empty-wins 会不会掩盖服务端真正清空集合的操作？**

会，所以它只适用于协议已确认“空表示未提供”的字段。需要清空时必须增加显式 `replace([])`、删除事件或版本化 patch，让“无信息”和“清空”可区分。

**Q3：为什么阶段用 `max`，而不是收到成功状态才加一？**

快照可能跨阶段到达或在重连后跳跃，逐次 `+1` 会依赖事件完整性。直接取已成功阶段编号的最大值，能从任意累计快照恢复已确认进度，同时抵抗旧快照回放。

**Q4：字段级 merge 会不会让 State 永远保留过期数据？**

可能，因此需要区分“不可逆累计事实”和“可更新配置”。前者适合单调合并；后者应使用版本、来源优先级或显式撤销。字段表应成为协议文档和测试的一部分，而非散落的临时 `if`。
