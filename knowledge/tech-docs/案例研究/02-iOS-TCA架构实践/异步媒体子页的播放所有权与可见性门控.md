# 异步媒体子页的播放所有权与可见性门控

> **技术域**：iOS TCA 架构实践  
> **难度**：⭐⭐⭐⭐⭐  
> **关键词**：UIKit 容器控制器 / UIPageViewController / AVPlayer / 生命周期转发 / 可见性单一事实源 / Task 幂等  
> **可迁移场景**：视频 Feed、轮播、分页详情、Tab 容器、预加载媒体卡片及异步创建的子控制器

---

## 一、场景与系统架构

一个分页宿主使用 UIKit 容器承载多个媒体子页，状态由单向数据流异步驱动。首屏数据可能在页面已经离场后才到达；宿主仍会据此创建子控制器并更新分页栈。每个子页持有播放器，并通过异步序列观察播放状态。

问题的关键不是播放器 API，而是谁有资格决定“现在可以出声”。子页知道自己的 appearance 回调，却不知道整个业务页面是否仍是用户正在看的页面；真正的可见性只能由宿主掌握。

```text
状态流异步到达
      │
      ▼
分页宿主（可见性 SSOT、播放权所有者）
  ├─ visible = viewDidAppear ... viewWillDisappear
  ├─ activePages[index] ───────────────┐
  ├─ 创建子页时下发 canPlay 闭包       │
  ├─ 回到前台：只恢复当前页             │
  └─ 离场：暂停全部活跃页               │
                                       ▼
                           媒体子页（播放权执行者）
                           ├─ viewWillAppear 只提出起播时机
                           ├─ canPlay() 为真才 play
                           └─ observer Task：先取消旧实例再创建
```

“播放所有权”在这里表示：宿主决定是否授予播放资格，子页只执行授权；生命周期回调只是触发信号，不是授权本身。

## 二、问题现象

可复现事件 trace 是：冷启动进入分页页，数据尚未返回时立刻切走；数据随后到达，分页容器装入第一个子页，并向它转发 `viewWillAppear`。旧实现中子页无条件调用播放，于是界面已经不可见，音频仍从屏外响起。

```text
t0  宿主出现，但数据为空
t1  用户切走，宿主收到 viewWillDisappear；此时 activePages = 0
t2  数据异步到达，状态应用仍创建并装入子页
t3  容器向新子页转发 viewWillAppear
t4  旧实现：play() → 屏外漏音
    新实现：canPlay() == false → 保持暂停
```

第二条 trace 出现在返回页面时：宿主 `viewDidAppear` 主动恢复当前页，容器又可能向子页转发 `viewWillAppear`。两条入口都会启动状态观察。旧观察任务不取消时，同一子页可同时存在 **2 个**消费循环，造成重复状态处理、重复渲染以及短暂停顿；修复后任一时刻至多保留 **1 个**观察任务。

这些数字描述可复现的调用与任务数量，不冒充帧率或耗时数据。修复的验收信号是：宿主不可见期间 `play()` 调用为 0；重复进入观察入口后，旧任务收到取消且活跃观察任务仍为 1。

## 三、根因分析

### 3.1 UIKit 转发的是容器层级变化，不是业务可见性证明

`UIViewController` 的 appearance 回调由呈现关系和容器转发共同驱动。自定义或系统分页容器在调用 `setViewControllers`、切换子控制器或完成过渡时，会为子页建立 appearance transition。这个 transition 表达的是“子页正在进入容器管理的可见位置”，并不自动证明最外层宿主仍位于前台层级。

异步状态把两个时间轴拆开了：

```text
宿主时间轴：出现 ── 离场 ───────────────────────
数据时间轴：请求 ───────────── 返回 ── 装入子页
子页时间轴：                      viewWillAppear
```

子页的 `viewWillAppear` 在自身时间轴上完全合法，却发生在宿主业务可见区间之外。把它等同于“用户能看到且允许播放”，就是根因。

### 3.2 `view.window != nil` 不是可靠替代品

分页容器重设控制器时，appearance 回调与视图挂入 window 的先后顺序并非业务授权协议。正常首播期间，回调发生时 window 也可能尚为空；反过来，视图仍在 window 层级也不保证没有被其他页面或容器覆盖。用 window 存在性门控会同时产生误拦与漏放。

宿主的 `viewDidAppear` 与 `viewWillDisappear` 更适合定义一段明确区间：前者授予、后者先撤销。这个布尔状态是播放资格的单一事实源，并通过闭包只读下发，避免子页复制一份可能过期的状态。

### 3.3 离场时只暂停当前索引不完备

分页容器为手势过渡和预加载可能同时保有当前、前一页、后一页，过渡中“当前索引”也未必覆盖所有已获得播放器的对象。只暂停 current 会留下活动集合中的其他播放器。宿主既然持有活跃子页表，离场就必须遍历整个集合统一撤销播放权。

更重要的是 t1 时集合可能为空，暂停循环什么也做不了；t2 新建的子页仍需通过同一个可见性状态被门控。因此“离场暂停全部”与“创建后禁止自决起播”缺一不可。

### 3.4 播放入口不唯一，观察任务必须幂等

子页既可能因自身 `viewWillAppear` 起播，也可能因宿主 `viewDidAppear` 被显式恢复。UIKit 生命周期和宿主编排是两个合法入口，试图靠调用顺序保证只执行一次很脆弱。

异步状态观察通常是长生命周期循环。每调用一次就新建 Task 而不取消旧实例，会让多个消费者处理同一个播放器事件。即便闭包使用弱引用，旧任务本身仍活跃；弱引用解决对象保留环，不解决重复订阅。正确不变量是：`start` 先取消现有任务，再替换为新任务；`stop` 取消并清空。

### 3.5 状态机应显式表达授权与执行

播放条件至少是三个状态的合取，而不是某个回调：

```text
mayPlay = hostVisible && pageIsCurrent && mediaIsPlayable
```

本案例的修复首先补齐 `hostVisible`。在更复杂容器中，当前页、应用前后台、音频焦点、用户手动暂停也应进入同一授权判断。这样 `play()` 是状态推导后的 effect，不再是生命周期回调的无条件副作用。

## 四、解决方案

### 4.1 旧代码：子页把回调当成播放许可证

```swift
final class MediaPageController: UIViewController {
    override func viewWillAppear(_ animated: Bool) {
        super.viewWillAppear(animated)
        player.play()                    // ❌ 子页不知道宿主是否仍可见
        beginStateObservation()          // ❌ 重复入口会叠加 Task
    }

    private func beginStateObservation() {
        observation = Task {
            for await state in player.states {
                render(state)            // ❌ 旧观察仍可能同时消费
            }
        }
    }
}
```

旧逻辑在同步、单入口的理想时序下看似成立，一旦数据到达和页面可见性脱钩，就失去正确性。

### 4.2 宿主维护可见性单一事实源

```swift
final class PagingHostController: UIViewController {
    private var isHostVisible = false
    private var activePages: [Int: MediaPageController] = [:]
    private var currentIndex = 0

    override func viewDidAppear(_ animated: Bool) {
        super.viewDidAppear(animated)
        isHostVisible = true                         // ✅ 先授予播放权
        activePages[currentIndex]?.resumeIfAllowed()
    }

    override func viewWillDisappear(_ animated: Bool) {
        super.viewWillDisappear(animated)
        isHostVisible = false                        // ✅ 先撤销，堵住异步新建窗口
        for page in activePages.values {
            page.pauseAndStopObserving()             // ✅ 不只暂停当前索引
        }
    }

    private func makePage(for item: MediaItem) -> MediaPageController {
        let page = MediaPageController(item: item)
        page.canAutoPlay = { [weak self] in
            self?.isHostVisible ?? false              // ✅ 子页只读宿主事实源
        }
        return page
    }
}
```

布尔值在 `viewWillDisappear` 一开始就置 false，保证离场后的异步状态应用即便创建子页，也无法取得播放权。返回时由 `viewDidAppear` 恢复当前页，授权路径完整闭环。

### 4.3 子页只执行授权，不自行判断宿主状态

```swift
final class MediaPageController: UIViewController {
    var canAutoPlay: (() -> Bool)?

    override func viewWillAppear(_ animated: Bool) {
        super.viewWillAppear(animated)
        guard canAutoPlay?() ?? true else { return } // ✅ 回调只是时机，闭包才是授权
        guard mediaIsPlayable else { return }        // ✅ 资源状态仍需独立门控
        player.play()
        replaceStateObservation()
    }

    func resumeIfAllowed() {
        guard canAutoPlay?() ?? false, mediaIsPlayable else { return }
        player.play()
        replaceStateObservation()
    }
}
```

如果组件需要独立复用，可以明确约定未注入闭包时的默认策略。对会发声的生产组件，更保守的默认拒绝通常安全；若为兼容已有调用方而默认放行，应通过测试确保所有容器都完成注入。

### 4.4 观察任务采用替换语义

```swift
private var stateObservation: Task<Void, Never>?

private func replaceStateObservation() {
    stateObservation?.cancel()                       // ✅ 双入口也只保留一个任务
    stateObservation = Task { [weak self] in
        guard let self else { return }
        for await state in player.states {
            guard !Task.isCancelled else { break }   // ✅ 及时停止旧消费循环
            await MainActor.run { self.render(state) }
        }
    }
}

func pauseAndStopObserving() {
    player.pause()
    stateObservation?.cancel()
    stateObservation = nil                           // ✅ 状态与资源一起归零
}

deinit {
    stateObservation?.cancel()                       // ✅ 最终兜底，不替代正常 stop
}
```

先取消再创建把 `start` 变成幂等操作。消费端仍检查取消，因为异步序列何时响应取消由其实现决定；UI 更新切回主 actor，避免播放器事件线程直接触碰 UIKit。

### 4.5 验收矩阵与事件断言

| 场景 | 断言 |
|---|---|
| 数据为空时立刻离场，随后数据返回 | 新子页可创建，但 `play()` 为 0 次 |
| 宿主可见时首批数据到达 | 当前子页获得授权并播放 |
| 离场时保有前/中/后多个子页 | 全部收到 pause，全部观察任务取消 |
| 返回时显式恢复与 `viewWillAppear` 都发生 | 播放可重复调用，但活跃观察 Task 始终为 1 |
| 正常 appearance 时 window 尚为空 | 不因 window 判定误拦，依据宿主状态起播 |
| 媒体不可播放 | 即使宿主可见也不调用 play |

测试应使用可控播放器替身记录 `play/pause/observe` 次数，并手工推进“离场—数据返回—装页”顺序。只测试最终是否有画面，无法捕获短暂漏音和重复观察。

## 五、可迁移原则

1. **子控制器生命周期不等于顶层业务可见性**：任何分页、轮播、Tab 或预加载容器都应由最近的可见性所有者下发授权。
2. **会持续消耗资源或产生外部效果的能力必须有所有者**：音频播放、相机采集、定位、动画和实时连接都不应由叶子节点仅凭局部回调自启。
3. **离场治理要覆盖整个活跃集合**：容器的当前索引只是导航状态，不等于全部资源持有者。
4. **防旧资源与防未来新建是两道门**：离场暂停现有对象只能处理过去；共享可见性门控才能阻止异步到达后新对象起播。
5. **多入口启动必须采用替换或引用计数语义**：观察 Task、通知订阅、定时器和播放器监听都不能假设生命周期只调用一次。
6. **弱引用不等于生命周期正确**：它防止强引用环，却不防重复工作、重复渲染和多个消费者并存。
7. **把副作用条件写成可测试状态表达式**：`宿主可见 && 当前页 && 资源可播 && 非用户暂停` 比分散在回调中的 if 更容易验证与扩展。

## 技术深问

**Q1：为什么不让每个子页在 `viewDidDisappear` 自己暂停？**

它能处理已创建且收到消失回调的子页，却处理不了“宿主离场时尚不存在、之后才异步创建”的子页。宿主门控解决未来对象，统一暂停解决现有对象，两者覆盖的时间窗口不同。

**Q2：闭包会不会让 UIKit 层反向依赖宿主实现？**

闭包只表达一个最小能力查询，不暴露宿主类型。也可替换为只读协议或注入的授权对象。关键是保持单一事实源，不在每个子页复制并同步 `isVisible`。

**Q3：是否应该只允许当前页播放，而不是仅检查宿主可见？**

是。完整授权通常还需当前索引或页面 token。本案例首先修复宿主离场漏音；在会预加载相邻页的容器里，应由宿主把“当前页”一起纳入授权，并在翻页完成时撤销旧页、授予新页。

**Q4：取消旧 Task 后，为什么还要在循环里检查 `Task.isCancelled`？**

取消是协作式信号。异步序列可能在下一次挂起点才结束，也可能先交付一个已排队事件。显式检查可以阻止取消后的事件继续进入 UI 更新路径。

**Q5：TCA 已有生命周期 action，为什么 UIKit 层还需要这套门控？**

状态层可以保存可见性并决定播放 effect，但 UIKit 容器仍负责子控制器创建和 appearance 转发。无论状态放在哪一层，都要保证同一个事实源覆盖“离场后异步装页”这个时序，并让播放器 effect 服从该状态，而不是服从局部回调。
