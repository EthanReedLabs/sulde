# 派生产物缓存:双失效与负缓存纪律

## 问题原型

昂贵的摘要、嵌入、编译或聚合结果需要缓存，但缓存键只含 TTL 或源版本；超时、空结果和受限环境
占位值也被当成成功产物写入，导致一次临时故障在整个缓存周期内反复命中。

## 根因与证据

根因是没有区分真源、派生产物、失败退避和生成逻辑版本，并假设“文件存在/JSON 可解析”就代表
可复用。已观察到源已变化但 TTL 未过仍读旧值、模型/prompt 升级后旧值永久命中、受限环境生成
`UNKNOWN` 后被持续复用。双失效键、写前有效性校验、独立短退避和读侧再验证能关闭这些路径。

## 适用边界

- 适用于可从权威输入重建且重建昂贵的派生产物；源数据本身应继续由真源负责。
- 对具有外部副作用的执行结果，缓存不能代替幂等账本和独立读回。
- 失败退避可以短暂限流，但必须与成功缓存分开，且恢复后能自动重新尝试。

## 路由正例

- **输入**：一次模型超时写入空摘要，之后所有请求在 TTL 内持续返回空结果。
- **预期**：apply
- **原因**：临时失败被写入成功缓存并参与正常命中判定。
- **来源**：observed

## 路由反例

- **输入**：权威数据库按主键保存用户原始记录，并通过事务更新。
- **预期**：skip
- **原因**：这是源数据持久化，不是可重建的昂贵派生产物缓存。
- **来源**：constructed

## 执行合格例

- **做法或输出**：命中同时校验 TTL、sourceVersion、generatorVersion 与内容有效性，失败只写独立短退避。
- **预期**：pass
- **原因**：源变更、逻辑升级和临时失败分别有明确失效与恢复路径。
- **来源**：observed

## 执行失败例

- **做法或输出**：只因 JSON 文件存在就复用，其中关键字段为 UNKNOWN，且返回状态仍为成功。
- **预期**：fail
- **原因**：半有效产物跨运行传播，后续正常环境也无法自行恢复。
- **来源**：observed

## 适用场景

任何存在"昂贵加工步骤"的管线:LLM 生成的摘要/prose、向量嵌入、编译产物、渲染结果、
聚合报表。共同特征是:原始数据可低成本重读或已有真源,而加工一次的成本(token、
算力、时延)显著高于一次缓存读取。

## 原则一:缓存派生产物,而非原始数据

值得缓存的资产是**已付费完成的加工结果**,不是加工的输入。

- 原始数据通常已有权威存储(数据库、文件、API 真源),再缓存一份只增加一致性负担。
- 派生产物(摘要、prose、嵌入)每次重算都要重新付费;缓存它才真正消除重复劳动。
- 判据:问"这份数据丢了,重建要花多少钱?"——重建昂贵的才进缓存。

```text
源数据(真源,不缓存副本)
   │  version / hash / mtime
   ▼
昂贵加工(LLM / 编译 / 聚合)
   │
   ▼
派生产物 ──写缓存──> {value, sourceVersion, cachedAt}
```

## 原则二:TTL 与 sourceVersion 双失效

单一失效条件各有盲区,必须同时满足两个条件才算命中:

| 只用 | 盲区 |
|---|---|
| TTL | 源在 TTL 窗口内变更,窗口期内一直读到旧产物 |
| sourceVersion | 源长期不变时,产物无限期保留;加工逻辑本身升级(prompt/模型/编译器换版)后旧产物永不刷新 |

正确的命中判定:

```text
hit = (now - cachedAt < TTL) AND (entry.sourceVersion == currentSourceVersion)
```

- `sourceVersion` 取源数据的版本号、内容哈希或 mtime——凡能表达"源变了"的单调信号皆可。
- 加工逻辑版本(prompt 版本、模型名、编译器版本)应并入 sourceVersion 或作为第三个键,
  否则升级加工逻辑后旧产物看起来仍"新鲜"。
- 任一条件不满足即 miss,重新加工并覆盖写入。

## 原则三:负缓存纪律——失败与超时不写缓存

最隐蔽的错误是把临时故障固化:

```text
❌ 加工超时 → 把空结果/错误占位写入缓存
   → 后续请求在整个 TTL 窗口内都命中这个"错误答案"
   → 一次网络抖动变成持续数小时的功能故障
```

正确做法:

- 失败、超时、空结果**一律不写缓存**,让下一次请求重新尝试加工。
- 若担心失败风暴(源持续故障时每个请求都重跑昂贵加工),用**短 TTL 的独立失败标记**
  (如 30–60 秒的 backoff 记录)限流重试,而不是把失败当产物缓存——两者的 TTL 和
  存储位置都应分开,失败标记绝不参与正常命中判定。
- 写缓存的前置条件是产物通过最低有效性校验(非空、可解析、大小合理),与"下载完成
  才改名提交"同理:缓存里只允许存在完整有效的条目。

### 补充:受限环境的降级运行与半有效产物

❌ 错误(变体):在受限环境(沙箱、权限不足、依赖工具缺失、禁网)下,加工/采集
脚本没有硬失败,而是"成功"跑完并产出关键字段为占位值(如 `UNKNOWN`)或为空的
**半有效产物**,照常写入缓存。这比显式失败更隐蔽:文件存在、格式合法,只有内容
是错的,后续每次运行都命中并复用这份污染产物。

正确做法:

- **写入侧 fail-fast**:采集/加工脚本对关键字段做断言,任一关键字段缺失或为占位值
  即非零退出且**不落盘**,绝不写空文件或占位文件充当产物。
- **读取侧防御**:复用缓存前校验条目有效性(关键字段非空、非占位值、可解析),
  无效条目按 miss 处理并重新加工。不能假设写入侧纪律在所有历史版本和所有运行
  环境下都成立——历史脚本、异常中断或受限运行都可能留下污染条目。

## 常见踩坑对照

| 症状 | 根因 |
|---|---|
| 源已更新,页面/结果长期显示旧内容 | 只有 TTL,没有 sourceVersion 校验 |
| 升级了 prompt/模型,旧产物永不刷新 | 加工逻辑版本没有纳入失效键 |
| 一次超时后,之后每次都拿到空结果 | 失败结果被写入缓存并在 TTL 内命中 |
| 缓存条目关键字段是占位值(UNKNOWN/空串)且被反复复用 | 受限环境下降级运行未 fail-fast,半有效产物入缓存;读取侧又无有效性校验 |
| 缓存了原始数据副本,与真源不一致 | 缓存对象选错——应缓存派生产物 |

## 验收清单

1. 源数据变更后,下一次读取即重新加工(sourceVersion 生效)。
2. 源不变但超过 TTL 后,重新加工(TTL 生效)。
3. 加工逻辑升级后,旧产物全部视为 miss。
4. 人为制造一次加工失败:缓存中不出现该条目,下一次请求重新加工成功。
5. 源持续故障时,重试频率受失败标记限流,但故障恢复后 60 秒内自动回到正常加工。
6. 在受限环境(禁网/降权)运行采集脚本:关键字段缺失时脚本非零退出且不落盘;
   向缓存手工注入占位值条目后,下一次读取判为 miss 并重新加工覆盖。

## ✅ 正确

成功条目使用 `{sourceVersion, generatorVersion, cachedAt, valueDigest}` 建立命中合同；写入前做
schema、非空和语义有效性检查，再原子替换。失败、超时和权限不可观测只进入独立短期 backoff，
绝不伪装成 value。读取侧每次复核元数据和关键字段，不信任历史写入器。

## 消费与防复发

- 缓存库、派生任务、读取端和发布迁移共同消费同一键与有效性 schema。
- 指标分别记录 hit、源失效、生成器失效、无效条目、负退避和重算成功，避免只看命中率。
- 回归固定源变化、逻辑升级、超时、占位注入、损坏文件和故障恢复六类 fixture。
