# 异步状态写入前必须确认平台能力

## 问题

跨平台代码常用 no-op 实现维持依赖图可编译。如果业务层先写入 `QUEUED`、`ANALYZING` 等进行中状态，再调用 no-op 调度器，数据将永久停在假执行状态，重启和轮询都无法恢复。

## 约束

- 调度接口必须暴露明确的平台能力，例如 `isAvailable`。
- Noop 必须报告不可用，不能以“调用成功但什么也不做”伪装真实实现。
- 只有能力可用且调度请求被接受后，才能持久化进行中状态。
- 不支持的平台应保持“未请求”或明确的“不可用”终态，不得制造无限等待。
- UI、数据库和恢复任务必须使用同一个能力事实，避免每层独立猜测。

## 测试

- 可用调度器被调用且状态进入队列。
- 不可用调度器不被调用，也不写入队列状态。
- 核心业务流程在附加分析不可用时仍正常完成。
- 进程恢复不会把不可执行任务重新展示为正在处理。

能力检查只能防止虚假状态，不能替代缺失的平台实现；文档必须明确功能边界，避免把安全降级描述成功能完成。
