# 端侧模型异构分层卸载验证方法

> 适用于 Android 端侧 LLM/VLM 在 CPU 与 OpenCL GPU 之间分配计算层的性能优化。目标不是追求“GPU 已启用”的标签，而是在可接受吞吐下稳定降低应用进程 CPU、内存和热负载。

## 一、先证明真实卸载

后端名称、编译宏或 UI 中出现 OpenCL，均不能证明模型已经在 GPU 上执行。Android 的 vendor 驱动、动态链接命名空间和桌面 ICD 机制不同，错误集成可能创建了 OpenCL 后端，却仍把模型和计算缓冲区分配在 CPU。

每次设备证据至少同时记录：

- 实际选中的 accelerator device；
- 正数 GPU offloaded layers 与模型总层数；
- 正数 accelerator model buffer；
- 原生日志中没有 platform unavailable、CPU-only fallback 或等价信号；
- APK 未误打包一个无法发现 vendor 驱动的桌面式 OpenCL loader。

缺少任一项时，只能说明“路径被请求”，不能作为真实 GPU 卸载证据。

## 二、全层卸载通常不是最佳点

把所有层放到 GPU 可以大幅降低 CPU 和 RSS，但移动 GPU 的带宽、调度、驱动转换和热约束可能使 token throughput 显著下降。优化目标应写成多约束问题：

1. 保留 CPU 基线至少 90% 的持续吞吐；
2. 应用进程 CPU 至少下降一个有意义的比例，例如 20%；
3. RSS 不出现不可接受增长；
4. 无崩溃、native abort 或驱动错误；
5. 热状态达到策略阈值时能触发受控 backoff。

因此应扫描离散层数，而不是只比较 `0` 和“全部”：先跑短 smoke 找出候选区间，再在设备恢复到 nominal thermal 后对相邻候选做正式 soak。典型搜索顺序可从少量层开始逐步增加，找到满足吞吐下限时 CPU 降幅最大的点。

**补充（soak 时长下限）：短 smoke 通过只说明配置能启动并短暂运行，不构成放量证据。** 热降频需要数分钟持续负载才会显现：实测示例中，某配置短 smoke 阶段吞吐正常，进入约 5 分钟持续推理 soak 后热状态升档触发降频，吞吐从约 16 tok/s 衰减到约 10 tok/s（约 35% 衰减）。因此正式 soak 的时长必须足以让设备到达热稳态（经验下限约 5 分钟，按设备散热特性上调）；生产开关的证据必须同时包含长跑 soak 结果与多设备画像矩阵（见第五节），任何仅有短跑数据的配置不得放量。

## 三、基准必须同条件可比

CPU 与 OpenCL 阶段必须使用同一模型、prompt、context、线程数和采样参数。每个阶段都记录：

| 维度 | 最低证据 |
|---|---|
| 延迟与速度 | TTFT、平均 tok/s、soak sustained tok/s |
| CPU | 应用进程平均 CPU，而非全系统 CPU |
| 内存 | 推理后 RSS、峰值内存 |
| 加速器 | device、offloaded/total layers、model buffer |
| 热 | 开始状态、最大状态、backoff 是否触发及时间 |
| 稳定性 | crash signal、native abort、driver error |

不能把热污染的串行结果直接并排比较。正式阶段前需要等待设备回到标称热状态；提前结束的 soak 只有在记录到策略允许的热 backoff 时才有效。

**补充（取证前禁用无关副作用）：真机取证 run 开始前，必须禁用与被测路径无关的模型预加载、后台预热等应用侧副作用。** cold-load 延迟与推理后 RSS 都是进程级测量：若应用启动时并行预加载其他模型、或被测模型已被提前加载，cold-load 实测的其实是热加载路径，RSS 中混入无关模型的缓冲区，两项证据都被污染且事后无法剥离。取证构建应提供开关关闭这些副作用，并在证据中记录开关状态；无法确认副作用已禁用的 run 不得作为 cold-load/RSS 证据。

## 四、产品路由按设备画像选层

最佳卸载层数依赖 SoC、GPU、Android 版本和驱动，不应把一台设备的结果推广为全局常量。产品配置使用规范化画像键，例如：

```text
soc=<family>|gpu=<family>|android=<major>
```

只有通过正式证据的画像才写入明确层数；未知画像保持关闭或实验默认值。电池省电模式、非标称热状态和证据过期应继续由运行时 gate 拦截。

画像级配置与生产总开关是两层不同控制：前者决定“这台设备若获准，应卸载多少层”，后者决定“当前版本是否允许真实用户走该后端”。不要因为单设备通过就绕过生产门禁。

## 五、多设备放量门禁

生产放量至少需要两个不同 GPU/SoC 画像分别满足同一证据契约。设备序列号不同但画像相同，只能算复测，不能增加覆盖面。历史结果若缺少进程 CPU 或真实 accelerator 证据，应保留作诊断，但不能被新规则追认成 PASS。

推荐 verdict 包含：

- rollout mode 与阈值版本；
- required/passing distinct profiles；
- 每台设备的完整指标、状态和阻断原因；
- 生成 verdict 所用原始 run 目录或不可变 artifact 标识；
- 构建门禁对 verdict 内容的二次校验，而不是只信一个 `status=PASS`。

**补充（门禁校验方式）：构建门禁读取 verdict/证据文件时必须做结构化 JSON 解析，而不是用正则匹配文本片段。** 正则只能确认某些字符串出现过，验不出字段类型与字段间约束，容易被格式相近的伪造内容骗过。同时，门禁不能只校验结果字段（如 passing distinct profiles 数量），还必须把证据文件中携带的门槛参数（如 min_profiles、阈值版本）与门禁自身持有的期望值比对一致——否则一份自带宽松门槛的证据（例如把 min_profiles 改写为 1 并自评 PASS）就能原样通过校验。原则是：判定门槛的权威来源是构建门禁本身，证据文件只提供事实，不提供判定标准。

**补充（双向收紧）：证据契约的收紧必须同时落在生成端与消费端，且两端判定形态保持一致。** 只加固消费端（构建门禁）不够：证据生成端（evaluator）若仍允许产出弱结构、低门槛的证据，手写一份形态相近的弱 PASS 证据就可能绕过生产开关；只加固生成端同样不够，因为门禁消费的是落盘文件而非生成过程，无法证明证据确实出自加固后的 evaluator。正确做法是让 evaluator 与构建门禁执行同一套结构与门槛校验——共享同一校验实现，或保持形态一致的双实现并用同一份 fixture 互测——使证据在产出时就满足契约、在消费时再被独立复核；任何一端单独通过都不足以放量。

## 六、常见失败模式

- **只看 backend label**：可能实际仍是 CPU buffer。
- **直接全层卸载**：CPU 很低但吞吐不可用。
- **线程数不同**：把减少线程造成的 CPU 下降误算成 GPU 收益。
- **连续热机跑矩阵**：后测配置被热降频污染。
- **带着无关预加载跑取证**：应用启动时预加载其他模型或被测模型已提前加载，cold-load 与 RSS 证据被副作用污染（见第三节补充）。
- **只跑短 smoke**：无法暴露持续推理的吞吐衰减和热 backoff；短跑通过就开生产开关，上线后才在真实用户设备上暴露热降频（见第二节补充的实测示例）。
- **用同画像两台手机凑数量**：不能证明跨驱动/SoC 可迁移性。
- **把画像配置当生产放量**：局部测量结果绕过了版本级风险控制。
- **用正则扫证据文本、或只信证据自带的门槛**：字符串匹配验不出结构化约束；门槛参数被改宽后，伪造的 PASS 证据可直接通过门禁（见第五节补充）。
- **只在单端收紧证据契约**：evaluator 与构建门禁校验形态不一致，弱 PASS 证据仍可从未加固的一端绕过生产开关（见第五节补充）。

## 七、落地顺序

1. 修通 vendor OpenCL 加载并补全原生日志。
2. 让解析器和判定器强制校验真实 accelerator 证据。
3. 同条件建立 CPU 基线。
4. 低层数到高层数做冷态 smoke 搜索。
5. 对边界候选做正式 thermal-aware soak。
6. 把胜出层数绑定到精确设备画像并加单测。
7. 在第二个不同画像重复完整流程。
8. 仅当 fleet verdict 通过时生成生产候选包。

这套方法的核心是把“能调用 GPU”改造成“可证明、可比较、可回退、可分设备放量”的工程系统。
