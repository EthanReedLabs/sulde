# 批次切分原则

> 协调端派发 Batch / Phase 任务时的切分依据。归纳自多轮 Batch 实操。

---

## 1. 按"页面结构类型"切分

两类任务本质不同,切法也不同:

| 类型 | 特征 | 切分策略 |
|---|---|---|
| **独立页批量** | N 页之间无流程依赖;每页独立 View/Fragment + Store | **可 3 人并行**(Android / iOS × Dev A/B/C) |
| **Wizard 工作流** | N 页链式依赖(上一步产出 = 下一步输入),共享中央 State/Feature | **单人串行**(1 人独占)+ 其他人做独立模块 |

**典型例子**:
- 独立页批量:定价 4 档、列表多状态页、引导 3 页
- Wizard 工作流:某创作流多页向导、支付结算 5 步、登录/注册 wizard

**判定法**:能否在不引用上一步数据/不扩同一中央 State 的前提下,独立写完一页?能 → 独立;不能 → Wizard。

---

## 2. Phase 切分节奏

每个 Batch 建议切分 2~3 个 Phase:

- **Phase N.1**:独立页批量(可 3 人并行,周期短、提交快、风险低)
- **Phase N.2**:Wizard 工作流(单人独占)+ 其他人接独立模块 / scaffold 补齐
- **Phase N.3**(可选):整合测试 + 遗留 known-issues 清理

**反例**:某次 Batch 的相邻 Phase 未显式区分节奏,把一个 Wizard 起点的重构混进了独立页批量 Phase,差点拖累其他并行任务。

---

## 3. Status 语义四分(强制)

页面关系图谱的 `status` 字段枚举:

| 值 | 含义 | 场景 |
|---|---|---|
| `clear` | 两端都完成 + 映射落地 | 正常 |
| `review-needed` | 单端完成或两端都未完成,需用户/协调端确认 | 新增页默认 |
| `todo` | 已登记但未开工 | 骨架阶段 |
| `deferred-v1` | **首版不做但保留代码**,v2 可能恢复 | 甲方说"后续还要,先隐藏" |
| `archived` | **完全废弃**(此字段已禁用,统一用 deferred-v1 表达"先不做") | ⚠️ 已约定不用 |

**关键区分**:
- `archived` = 永久不复活 → 可删代码
- `deferred-v1` = 首版隐藏、v2 恢复 → **必须保留代码**,只藏入口

**推进规则**:
- Android `android.status: clear` + iOS `ios.status: clear` → 才能推 page-level `status: clear`
- 任一端 `todo` → page-level 保持 `review-needed`
- 切勿单端完成就推 page-level clear(曾踩过:某页单端 clear 后被误推 page-level clear,后轮补完才对齐)

---

## 4. 并发度限制(不是人多就快)

**硬性约束**:
- Wizard 工作流的 `core-ui/tokens/**` / 中央 `Store.kt` / `Feature.swift` 等**共享文件**永远不并行改
- 同一模块(如 `feature-<某创作流>/`)两人并行改 → 合并必冲突,实际净收益为负

**可并行的 3 场景**:
1. **跨平台并行**:Android 和 iOS 始终可并行(不同代码库)
2. **跨模块并行**:Dev A 做 `feature-detail/` + Dev B 做 `feature-discover/` + Dev C 做 `core-ui/widgets/`
3. **scaffold 并行**:scaffold 任务(AppTopBar / AdaptiveStateView)与 Feature 开发并行,路径隔离

---

## 5. 任务派发前 checklist

- [ ] 列出每个子任务的预计改动文件(绝对路径)
- [ ] 两两做文件交集 — 共享文件警告
- [ ] Wizard 工作流判定 — 有则一人独占
- [ ] 矩阵标注思考模式(按任务复杂度)
- [ ] 路径表贴进任务文件头部(方便两端 parallel-dev 二次确认)
