# 健康平台数据先标准化再进入决策

## 适用场景

应用同时读取 Health Connect、HealthKit、手表、体脂秤或其他健康来源，并用这些数据生成训练、恢复或营养建议。

## 约束

1. 原始平台对象不能直接进入 prompt、规则引擎或长期趋势。
2. 每个标准化字段必须保留 `platform`、`source`、`recordId`、`timezone`、`unit`、`capturedAt` 和采集方式。
3. 入站记录使用 `source + recordId` 去重，不能只按时间和值猜测重复。
4. 裁决顺序应显式且可测试：用户指定来源、应用自有记录、设备主动测量、自动采集、手工录入、未知来源，最后才比较采集时间。
5. 相同优先级的不同来源不能静默求和或覆盖，应保留冲突并要求用户选择主来源。
6. 睡眠、HRV、疼痛等会改变训练强度的字段存在未决冲突时，决策必须降级为未知或保守状态。

## 推荐结构

- 平台适配层：读取平台对象并立刻转换为值和 provenance。
- 标准化层：单位、时区和字段语义归一。
- 裁决层：去重、来源优先级、用户偏好和冲突输出。
- 决策层：只接收裁决后的快照，不依赖 Health Connect 或 HealthKit 类型。
- UI 层：展示来源并让用户处理同级冲突，选择应持久化且可撤销。

## 全局一致性

主来源偏好不能只在设置页参与展示。应在 DI 边界用一个 resolving data source 包装平台适配器，所有 Coach、进度、聊天和历史写入都通过该对象读取。平台适配器只负责返回候选，resolver 负责读取持久化偏好并裁决。这样可以避免不同功能对同一组健康数据得出不同结果。

Android 可按 Health Connect `dataOrigin` 分组候选并用 DataStore 保存字段级主来源；iOS 可按 HealthKit source bundle 分组并用 NSUserDefaults 保存。持久化键使用原始 source id，UI 只负责映射友好名称。

## 验证

至少覆盖同源重复、不同优先级来源、同级来源冲突、显式用户偏好、跨时区采集，以及未决恢复冲突不能产生高置信训练建议。
