# 微信支付接入：能力确认、凭据隔离与旧单结算

## 问题原型

接入方已注册微信支付商户，并具备认证服务号和网页授权，希望直接启用网站收款。
但账号注册、登录授权、具体支付产品权限、服务端支付代码和真实交易验收分别属于不同状态。
另一个常见设计风险是把一个总开关放在所有支付操作共用的适配器里，停用新收款时连旧订单的结算与退款也被关闭。

期望是能力按场景启用，缺少平台权限时保持关闭；已经产生的交易仍按有效证据安全处理。

## 原则与机制

### 先建立能力矩阵

| 能力 | 需要单独核对的内容 | 不能替代的证据 |
|---|---|---|
| 公众号网页授权登录 | 账号权限、授权域名、服务端换码与会话 | 不能证明商户已开通支付产品 |
| Native 支付 | Native 权限、符合要求的 AppID 与商户绑定、扫码交互 | 不能证明已实现微信内 JSAPI 或浏览器 H5 支付 |
| JSAPI 支付 | JSAPI 权限、AppID 绑定、授权目录、对应客户端调用流程 | 不能仅凭 Native 二维码适配完成 |
| H5 支付 | 按当前官方产品要求核对场景、权限及相应实现 | 不能把“有手机网页”当成已开通 H5 支付 |

Native 和 JSAPI 的权限与绑定要求应分别核对当前官方接入准备，不能从商户注册状态推断。
参见 [Native 接入准备](https://pay.wechatpay.cn/doc/v3/merchant/4015614538) 和
[JSAPI 接入准备](https://pay.wechatpay.cn/doc/v3/merchant/4015423216)。

### 凭据按用途分开

- 公众号 AppSecret 用于相应登录/公众号能力，不能代替支付请求签名凭据。
- 商户私钥与商户证书序列号用于支付 API 请求签名身份；APIv3 密钥用于相应加密通知数据的解密。
- 微信支付公钥及其 ID，或平台证书及其序列号，用于匹配受信验签材料；两种模式须按接入方案明确选择，不能混淆标识符。
- 私钥、AppSecret、APIv3 密钥只在服务端私密存储；不进前端、Git、聊天或完整配置输出。

证书、公钥和 APIv3 密钥的角色并不相同；轮换也必须区分材料，不能把停用收款简化为删除全部密钥。
参见 [微信支付证书密钥概览](https://pay.wechatpay.cn/doc/v3/merchant/4024350132)。

### 新单准入与历史结算分开

新订单至少受业务开关、具体渠道/产品开关、有效配置和业务准入控制；默认关闭。
关闭新收款后，既有订单的有效通知、查单、退款和对账仍应可运行，保持验签、授权和幂等校验。
不能用浏览器跳转、按钮成功提示或收到任意通知来替代服务端交易证据。
这与 `ap-0153` 中“不要把商品展示查询为空当作购买门禁”不同：已开通产品权限是真实接入条件，展示查询的临时空结果则未必是。

## 根因与证据

已确认的输入条件是“商户仅完成注册，具体支付产品尚未开通”，而登录侧已有认证服务号网页授权。
代码审查和可回读的自动化测试验证了以下行为：

- 凭据存在但渠道未显式启用时，不向前端公布可用收款渠道。
- 关闭渠道开关后，新订单被拒绝；旧订单重复支付证据只入账一次，旧订单退款仍可执行。
- 构造的签名与加密通知可被验证，篡改签名、金额、商户归属等不匹配情形被拒绝。

上述证据支持开关设计和验证边界，因此本条标为 `verified`；它不表示真实商户全链路已验收。
这些测试使用替身支付适配器、生成的测试签名材料和本地数据库。
没有真实付款、真实退款、商户后台产品开通或生产数据库并发验收证据，不得将其升级为上线成功。
“总开关阻断历史结算”是由设计分析和构造测试覆盖的反例，未观察到因此产生的真实资金事故。

## 适用边界

- 适用于自有商户 APIv3 网站支付的接入准备、渠道启停和历史订单生命周期设计。
- 服务商/子商户模式、应用内购买、APP 或小程序支付须各自核对身份体系和产品协议，不直接复制本条产品矩阵。
- 单纯修复微信登录回跳、分享 SDK 或授权域名文件时，不应要求补齐支付商户参数。
- 如私钥泄露、验签信任失效或平台冻结，应进入专门事件处置；“保留旧单处理”绝不等于继续信任失效凭据或绕过平台限制。暂停自动记账并安全轮换/对账也可成为必要措施。
- 配额、费率、主体资格、控制台菜单和审核条件属于易变信息，实施时重新查官方文档。

## 判定样本

### 路由正例

- **输入**：服务号网页授权已经开通、商户也注册了，但 Native 支付产品尚未申请，代码接入应如何准备和启用？
- **预期**：apply
- **原因**：需要分离登录能力、商户权限、实现状态和真实支付验收。
- **来源**：observed

### 路由反例

- **输入**：仅处理微信网页授权回跳失败，不做收款，也没有支付订单，是否必须先配置商户 APIv3 密钥？
- **预期**：skip
- **原因**：问题只涉及 OAuth 登录，支付凭据不是解决该故障的前置条件。
- **来源**：constructed

### 执行合格例

- **做法或输出**：在替身渠道测试里关闭新单开关，新建订单被拒绝，旧单重复证据只记账一次，旧单退款成功；报告明确真实商户联调仍未完成。
- **预期**：pass
- **原因**：验证了开关作用域和幂等结算，同时没有夸大证据层级；这里只代表代码准备通过。
- **来源**：observed

### 执行失败例

- **做法或输出**：把开关判断放进公共支付适配器构造函数，停用新单时顺带拒绝旧单通知、查单和退款，并以单测成功宣布真实支付上线。
- **预期**：fail
- **原因**：既破坏历史交易处理能力，又把模拟测试当成真实渠道验收。
- **来源**：constructed

## 正确做法

1. 确认用户实际使用场景，选择对应支付产品；分别登记注册、权限、AppID 绑定、材料配置、代码验证、商户联调状态。
2. 将私密材料以限制权限的服务端文件或密钥服务提供；只输出“已设置/未设置”和有效性检查结论。公开域名校验文件与私钥不得混放为同一开放目录。
3. 精确核验支付异步通知路径能接受平台 POST，不受网站内测 Basic Auth、浏览器会话或浏览器 CSRF 规则阻断。只处理所需路径，保留平台验签、重放防护、归属和金额核对；不扩大成整个 API 匿名开放。
4. 订单与流水持久化，采用稳定幂等键和事务保证。回调重复、回调与主动查询并发、订单已终态时，都不重复发放权益。
5. 模拟回归覆盖关闭新单、旧单结算、退款、重复通知、错误签名、错误归属/金额、超时不确定结果，以及前端能力显示。结果不确定时先查单，不盲目创建第二笔交易。
6. 在获得真实交易授权及产品就绪后，执行小额真机付款、服务端通知/查单核验、权益核对、原路退款与对账；按实际资金结果验收，不能只看客户端成功页。
7. 分阶段启用对应产品。回滚或临时停用时先停止新收款；检查存量订单及凭据有效性后，再决定如何继续结算或转人工处理。

## 取舍

分开开关和交易生命周期会增加状态管理，但能减少停收款与旧单处理相互干扰。
产品未开通期间可完成代码、负向测试与部署准备；保持明确关闭状态即可，不需要伪造商户材料。
真实付款涉及外部资金动作，应取得具体授权；文档入库或测试通过不授予自动扣款/退款权限。

## 消费与防复发

本条供接入方案、支付代码审查与发布核验检索使用，不自动开启渠道、创建订单或触发退款。
来源实现已具备渠道开关、幂等、退款和签名负向自动化覆盖；跨项目使用时必须映射到自身实现。
机械检查可以验证开关作用域、密钥泄露和交易不变量，产品真实权限与实付闭环仍需独立证据。
检索消费者必须保留 apply/skip 边界；不能因为出现“微信”就把支付条件注入纯登录任务。
