# 设计稿示意图识别指南

**目的**:避免把"一图代表一类"的示意图误解为"每张图 = 一个独立实现"。曾因漏识别这个模式,把一个共享宿主 + 多状态切换的向导流错拆成 N 个独立 Activity / 独立 fullScreenCover,导致两端架构不一致,触发大额返工(约 12 人天)。

**适用**:两端 `/ui-impl` skill 阶段 0 必读;协调端处理新设计稿更新时必读;设计师新交付时做 checklist。

---

## 核心原则

**不是所有设计稿页面都对应一个独立实现**。部分页面在设计稿里是"某类视图的代表示意",真实实现应复用 1 个宿主 + 多种状态/内容切换,而不是复制 N 份。

---

## 已识别的 9 类"一图代表一类"模式

### 模式 1:生成页 Chat Tab(跨 stage 共用)

| 项 | 内容 |
|---|---|
| 设计稿位置 | 各创作流的 Chat 页(每种创作 1 张)|
| 表面数量 | 多张(每种创作 1 张)|
| 实际覆盖 | 各自创作生成页的 Chat Tab,**跨所有生成 stage 共用**(消息流全程累积)|
| PRD 依据 | "生成页共性:Chat Tab" —— Chat 用于承接用户与 agent 的对话、thinking 文本、继续按钮、费用确认、结果入口卡 |
| 正确实现 | 每种创作 1 个 Chat Tab(同 View 的一个分支),不是"每 stage 一个 Chat" |
| 反例 | ❌ 为某创作流的每个 stage 都做一个 Chat Activity |

### 模式 2:生成页 Preview Tab 的 stage 内容

| 项 | 内容 |
|---|---|
| 设计稿位置 | 某创作流的多个 stage 页(每 stage 一页)|
| 表面数量 | 每 stage 一页 |
| 实际覆盖 | 同一生成页的 Preview Tab 内部 **stage 切换内容**,不是 N 个独立页面 |
| PRD 依据 | "生成页共性:Preview Tab 结构" —— 当前阶段页固定由三部分组成:顶部阶段标题区 / 中部阶段内容区 / 底部阶段导航区;用户点按任意已生成阶段的短横条,可回看该阶段产出 |
| 正确实现 | 1 宿主 + 1 ViewPager/@State 切换 stage 内容 |
| 反例 | ❌ Android 把每 stage 拆独立 Activity;❌ iOS fullScreenCover 弹独立 wizard |

### 模式 3:Agent 操作消息卡(3 种)

| 项 | 内容 |
|---|---|
| 设计稿位置 | 可能只画 1 种示意(普通 Continue 卡)|
| 表面数量 | 1 张 |
| 实际覆盖 | 3 种类型(PRD 明确)|
| PRD 依据 | "Agent 操作消息卡分三种:1. 普通继续卡(Continue)2. 费用确认卡(Confirm And Continue + 项目/数量/单价/总额)3. 重试卡(Retry)" |
| 正确实现 | 1 个 AgentActionCard 组件 + 3 个 variant |
| 反例 | ❌ 看到 1 张画稿就只做 Continue 卡 |

### 模式 4:分享面板

| 项 | 内容 |
|---|---|
| 设计稿位置 | 在首页里示意 1 张 |
| 表面数量 | 1 张 |
| 实际覆盖 | 首页 / 详情页 / 最终结果保存 / 作品卡长按 / 通知 等多处触发 |
| PRD 依据 | 多处引用分享能力 |
| 正确实现 | 1 个 SharePanel 脚手架(BottomSheet)+ 所有触发点复用 |
| 反例 | ❌ 每个触发点都自画一套分享 UI |

### 模式 5:BottomSheet 入口模板

| 项 | 内容 |
|---|---|
| 设计稿位置 | 某下拉选择面板(从某参数页触发)|
| 表面数量 | 1 张 |
| 实际覆盖 | 多种参数页 + 未来可能扩展的其他选择入口 |
| 正确实现 | 1 个 BottomSheet 脚手架 + 多处 show() 调用 |
| 反例 | ❌ 每种创作复制一份 dropdown UI |

### 模式 6:Dialog 骨架(内容变、结构同)

| 项 | 内容 |
|---|---|
| 设计稿位置 | 多个不同内容的 Dialog 都画了(参考图 / 故事板 / 视频片段等)|
| 表面数量 | 多张 |
| 实际覆盖 | UI 骨架相同(90% 屏宽、居中、close 按钮、确认 / 取消按钮布局);内容各异 |
| 正确实现 | Dialog 基类 + 内容 slot |
| 反例 | ❌ 每个 Dialog 重复 layout 骨架代码 |

### 模式 7:Loading / Error / Empty 通用态

| 项 | 内容 |
|---|---|
| 设计稿位置 | 多处示意(通知空态 / 通知错误态 / 额度空态 / 某落地空态 等)|
| 表面数量 | 多张 |
| 实际覆盖 | 全 App 通用三态(AdaptiveStateView 脚手架)|
| 正确实现 | 1 个 AdaptiveStateView 组件 + 各页传入 state + 配图 + 文案 |
| 反例 | ❌ 每页自画 Empty/Error 状态 UI |

### 模式 8:stepFooter 进度条

| 项 | 内容 |
|---|---|
| 设计稿位置 | 画在某 stage 底部示意 |
| 表面数量 | 1 处 |
| 实际覆盖 | Preview Tab 所有 stage 共用(底部阶段导航区固定展示 Step X of Y)|
| 正确实现 | WizardFooter 共用件 |
| 反例 | ❌ 每 stage 自画底部进度条 |

### 模式 9:Wizard Footer 操作区(Continue/Previous)

| 项 | 内容 |
|---|---|
| 设计稿位置 | 部分 stage 底部画了示意 |
| 表面数量 | 不定 |
| 实际覆盖 | 所有 Wizard stage 共用 |
| 正确实现 | WizardFooter 共用件(与模式 8 合并)|
| 反例 | ❌ 每 stage 自画 Continue 按钮 |

## 识别 Checklist(两端 /ui-impl 阶段 0 必做)

拿到一个页面编号时,按以下顺序判断:

1. **查页面关系图谱的 `tab-group` 字段**:
   - 若有 `tab-group: <某生成流>`(或类似)→ 该页是某宿主的 Tab 内容,**不是独立页**,回宿主实现
   - 若无 → 继续

2. **查 `tab-role` 字段**:
   - `chat-template` → 一张图代表宿主的整个 Chat Tab,看 `covers` 字段了解覆盖范围
   - `preview-stage` → 在宿主的 Preview Tab 内部 stage 切换实现,不独立
   - `preview-host` → 本页是 Preview Tab 宿主
   - 无 → 独立 page / modal / dialog

3. **查 PRD 对应章节**:
   - 如果 PRD 提到"共性 / 通用 / 多处复用"相关描述 → 识别为脚手架或共用件
   - 如果 PRD 明确每 stage 独立 → 按独立实现

4. **查 scaffold 清单**:
   - 如果该模式已有 scaffold 条目(如 AppTopBar / AdaptiveStateView / ShareBottomSheet)→ 用脚手架不自画

5. **不确定 → 写 handoff 请协调端确认**,不要凭感觉决定

## 识别反例(真实踩坑)

### 反例 1:Android 把向导多 stage 拆成 N 个独立 Activity

- **误判**:把某创作流的多个 stage 页(框架 / 参考图 / 故事板 / ... / 最终结果)看成 N 个独立页
- **后果**:Android 拆 N 个 Activity + N 个 layout,两端架构不一致,后续重构约 7 人天
- **应该**:识别为模式 2 "Preview Tab stage 内容" → 1 Activity + ViewPager2/Fragment 切换

### 反例 2:iOS 把向导做成独立 fullScreenCover

- **误判**:把某创作流的多 stage 做成独立 Feature `@Presents` 全屏 wizard
- **后果**:脱离生成页的 Preview Tab 宿主,后续重构约 5 人天
- **应该**:并入生成页的 Preview Tab 的 stage 切换

### 反例 3(假设):新设计师加多种 Agent 操作卡设计稿

- **误判**:看到只画了 Continue 卡,实现时只做 Continue 卡
- **后果**:费用确认 / 重试场景落地失败,设计师 review 打回
- **应该**:识别为模式 3 "Agent 操作消息卡 3 种" → 3 variant 一起做

---

## 发现新模式时的处理

如果在实际开发中发现新的"一图代表一类"场景,**必须更新本指南**:

1. 在本文末尾加新模式(沿用表格格式)
2. 在页面关系图谱补 `tab-group` / `covers` 等字段
3. 必要时 scaffold 清单补脚手架条目
4. 在两端 `.ai-workspace/handoff/` 写条目通知协调端
