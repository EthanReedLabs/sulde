# 端侧应用隐私政策与商店声明对齐方法

> 适用于在设备本地处理健康、语音、相机、图片、视频、聊天和诊断信息的移动应用。目标是让真实数据流、公开隐私政策、运行时权限和商店表单使用同一套事实，同时避免把“本地访问”误填成“离设备收集”。

## 问题原型

移动应用分别维护源码实现、依赖、最终安装包权限、运行时同意、隐私政策和商店表单，
各入口都可能局部正确却彼此矛盾。典型表现是业务代码没有直接上传或调用某能力，就宣称
“未收集/未使用”，但传递 SDK、预编译字节码或最终签名包仍携带相应权限与网络能力。

## 根因与证据

根因是把业务源码当成唯一合规事实，而商店审核和真实数据流覆盖依赖锁、最终产物、SDK
配置、初始化时序及公开披露。依赖解析、解包权限、真机同意时序和商店复验分别证明不同
层面；单一健康平台检查、构建成功或“业务未调用”都不能证明整条数据面一致。

## 适用边界

适用于处理个人或敏感数据、接入第三方 SDK、声明系统权限或准备商店发布的移动应用。
不适用于不发布、不请求设备数据且无任何第三方数据能力的纯本地原型。商店定义、SDK 版本
或最终包尚未复验时只能写“实现完成/待审核”，不得写“已合规”；账户绑定的外部发布动作
仍须由项目负责人明确启动，普通“继续实施”不构成授权。

## 判定样本

### 路由正例

- **输入**：业务没有调用设备标识 API，但最终安装包因第三方 SDK 被商店扫描出相关权限
- **预期**：apply
- **原因**：命中第三方传递能力、最终产物和对外声明需要统一建模的条件
- **来源**：observed

### 路由反例

- **输入**：内部原型不发布、不联网、不读取设备数据且没有第三方依赖
- **预期**：skip
- **原因**：没有形成本文所治理的个人数据、平台权限或商店披露链路
- **来源**：constructed

### 执行合格例

- **做法或输出**：数据路径、依赖锁、签名包、SDK opt-out、同意时序、政策与表单逐项一致
- **预期**：pass
- **原因**：所有事实层有同一来源并保留独立验证证据
- **来源**：constructed

### 执行失败例

- **做法或输出**：只因业务源码未直接调用某 API，就把商店表单填为未收集且不解包验证
- **预期**：fail
- **原因**：忽略传递 SDK 和最终产物，结论没有覆盖真实审核面
- **来源**：observed

## 正确做法

先建立统一数据路径作为单一事实源，再按下文逐层验证访问、离设备收集、共享、依赖、最终
产物、SDK 配置、运行时同意和公开披露。每个结论绑定实际证据；证据尚未取得时保持待审核，
并把实现阶段与人工发布阶段分开。

## 一、先区分三个概念

1. **访问（access）**：应用读取或处理设备上的数据，例如读取 HealthKit、录音或分析图片。
2. **收集（store-form collection）**：Google Play Data Safety 和 Apple App Privacy 主要关注数据是否离开设备，并可被开发者或第三方访问。
3. **共享（sharing）**：数据是否提供给第三方，且不属于平台规则中的服务提供商或用户主动传输等例外。

纯端侧处理可能同时满足“访问敏感数据 = 是”和“商店表单收集 = 否”。这不代表可以省略隐私政策或权限披露；敏感数据访问、用途、保留、撤销和删除仍需完整说明。

## 二、用统一数据路径做单一事实源

不要分别手写 Android、iOS、隐私网页和测试清单。先建立统一路径清单，每条至少包含：

- 数据类别和具体字段；
- 来源（用户输入、健康平台、麦克风、相机、媒体库）；
- 本地处理目的；
- 是否持久化及保留时间；
- 是否离设备；
- 是否共享；
- 导出、删除和权限撤销路径；
- Google Play 与 Apple 在“未来发生上传时”对应的数据类别。

隐私政策、权限文案、Health Apps 声明、Data Safety、App Privacy 和发布测试都从这份路径清单生成或校验。

## 三、当前端侧版本的商店填写原则

在 release 网络与依赖审计证明所有个人内容均不离设备时：

- Google Play Data Safety 的“收集”和“共享”可为否；
- 因为没有离设备收集，ephemeral processing 问题不适用；
- Apple App Privacy 可为 Data Not Collected；
- Google Play Health Apps declaration、Health Connect 权限用途、HealthKit usage descriptions、麦克风/相机/媒体权限仍需填写；
- 隐私政策仍要覆盖本地访问的所有个人和敏感数据，而不只覆盖商店表单中选择的数据类别。

商店定义会变化，提交前应重新核对官方文档，而不是长期复用旧截图或旧答案。

## 四、公开隐私政策最低内容

- 应用和责任主体名称、隐私联系方式；
- 所有个人和敏感数据类型；
- 访问、使用、存储和共享目的；
- 端侧与网络边界；
- 本地缓存和长期记录的保留规则；
- 权限撤销、数据导出、更正和删除；
- 健康平台只删除本应用拥有记录的所有权规则；
- 安全措施及 rooted/jailbroken 设备边界；
- 未成年人、政策更新和健康/医疗免责声明；
- 无鉴权、无地域限制、非 PDF、最终 HTTP 200 的公开 URL。

主 URL 应直接显示可审阅的政策内容，不能只有空白页面、登录跳转或缺少正文的语言选择器。

## 五、自动防漂移门禁

建议增加机器可读 checker：

1. 协议包必须包含全部统一数据路径。
2. 中英文政策必须分别覆盖每条路径。
3. 落地页必须直接出现核心类别、删除方式和联系方式。
4. 禁止旧的“仅覆盖某一个健康 API”范围文本回归。
5. 端侧版本必须校验 `off_device_collection=false`、`sharing=false`。
6. 一旦引入上传、账号、云同步、远程推理、analytics/crash SDK 或广告 SDK，立即阻断旧商店答案并要求重开表单。
7. 发布前从沙箱外验证 URL 最终 HTTP 状态和无鉴权访问。
8. 解析依赖锁与最终签名安装包，而不是只审业务源码；第三方 SDK 的传递依赖、字节码和可选设备标识能力都进入审核面。
9. 对最终包内每项用户授权权限校验用途文案和使用场景元数据；构建成功不能代替 manifest/module 解包证据。

门禁覆盖率必须以完整数据路径清单为分母，逐条覆盖来源、处理、持久化、导出、离设备传输和第三方接收方。Health Connect 或其他单一健康平台的检查结果只能证明对应链路，不能代表用户输入、媒体、诊断日志、备份及第三方 SDK 等其余路径合规；任何未建模或未经验证的路径都应阻断发布。

### 第三方 SDK 必须按最终产物建模

“业务没有直接调用某 API”不等于“发布包没有该能力”。推送、统计、崩溃、广告、登录、支付和分享 SDK 可能通过传递依赖或预编译字节码带入设备标识、网络、存储等能力；商店审核通常扫描最终 APK/AAB/IPA/HAP 及其权限清单，而不是只看业务调用点。

每个第三方 SDK 至少建立以下闭环：

| 层 | 必查事实 |
|---|---|
| 依赖 | 直接依赖、锁文件、传递包、预编译字节码 |
| 最终包 | 实际权限、entitlement、能力声明和资源解析结果 |
| SDK 配置 | 可选数据能力是否启用；不需要时是否使用当前版本真实 opt-out |
| 运行时 | 隐私同意前是否初始化/采集；权限何时请求；拒绝后如何降级 |
| 对外披露 | 隐私政策、第三方 SDK 清单、商店表单是否逐项一致 |

对于业务不需要的设备标识或归因能力，应优先使用 SDK 官方 opt-out；但关闭运行时采集不能自动证明静态审核不再命中，仍需解包最终签名产物并运行平台分析器。opt-out 后还必须验证 SDK 的核心业务能力没有被连带关闭，例如推送类 SDK 至少验证 token、别名/标签和消息收发。若最终包或审核报告出现用户授权权限，必须按平台要求补全用途和使用场景字段，不能只声明权限名。

未经最终包分析、真机同意时序验证和商店复验，只能写“实现完成/待审核”，不能写“已合规”或“已过审”。

## 六、健康平台的真机证据

健康集成不能只验证权限弹窗。真机 probe 应分别证明：

- 至少一种授权样本可读；
- 本应用拥有的临时训练记录可写；
- 使用同一稳定 ownership identifier 可删除；
- 不会删除其他应用拥有的记录；
- 临时验证记录在 probe 结束后无残留。

写删测试应只在显式测试 flag 下运行，正常启动绝不创建测试健康数据。

## 七、何时必须重开商店表单

- 生产版本上传任何个人内容、标识符、诊断或派生结果；
- 第三方 SDK 接收设备或用户数据；
- 第三方 SDK 新增设备标识、统计、崩溃、广告或其他可选能力，即使业务代码没有直接调用；
- 新增健康数据类型或改变处理目的；
- 引入云同步、账号、远程教练或服务端推理；
- 发布产物与“无上传”审计假设不一致。

正确做法不是一次性填完表单，而是让数据路径、政策、权限、代码和发布证据形成持续可验证的闭环。

## 八、实现阶段与人工发布阶段必须分离

发布门禁既是事实约束，也是工作流约束。项目负责人明确决定“先记录、最后人工处理”后，自动化代理必须把账户绑定的外部动作保持为 deferred，而不能因为总体目标包含“完成”就提前追逐这些门禁。

实现阶段可以继续：

- 编写和校验隐私政策、数据路径矩阵与提交清单；
- 保持协议状态为草稿或外部门禁待处理；
- 记录最终需要的账号操作、证据格式和复验命令；
- 推进产品功能、模型、UX、性能和无需发布账号的设备测试。

只有项目负责人明确启动最终发布后，才可以：

- 请求登录 GitLab、Play Console 或 App Store Connect；
- 修改 Pages 可见性；
- 提交商店表单；
- 发起外部扫描、渗透测试或审核流程。

通用的“继续”“开始实施”“直到计划完成”不等于启动最终发布。实现完成与最终 `SHIPPED` 应使用两个独立状态，人工发布门禁不能挤占当前仍未完成的产品任务，也不能单独成为实现目标 blocked 的理由。

## 消费与防复发

本方法由发布 checklist、依赖与签名包分析器、权限/用途文案 checker、真机同意时序测试及
商店表单人工 review 共同消费。能机械解析的依赖、权限、URL 状态和路径覆盖率进入门禁；
平台定义、SDK 行为、用途合理性和账户外部操作继续由人核验与授权。路由正反例用于决定
是否启动完整合规链，执行正反例用于阻止“源码没调用/构建成功”等假证据通过。
