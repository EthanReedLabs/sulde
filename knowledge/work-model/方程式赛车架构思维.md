# 方程式赛车架构思维

> 一种面向 AI 时代的软件架构决策方法论
> 核心理念：**只为确定的变做灵活，其他做到极致简单**

---

## 适用场景

- 从零设计一个新产品的架构
- 现有系统需要重构/模块化
- 需要向甲方/团队解释架构选型理由
- 需要在多个技术方案之间做取舍决策

---

## 方法论总览

```
Phase 1: 识别变化轴心 ──► 什么一定会变？
Phase 2: 评估变更成本 ──► 变一次伤筋动骨还是皮外伤？
Phase 3: 分级决策      ──► 哪些做到极致灵活，哪些做到极致简单？
Phase 4: 架构分层      ──► 五层骨架 + 依赖铁律
Phase 5: 赛规定义      ──► 灵活点的契约规范
Phase 6: 基础工具盘点  ──► 从场景反推需要什么工具
Phase 7: 碎片化适配    ──► 差异在各层内部消化，不向上泄漏
Phase 8: 分阶段落地    ──► 先跑起来，再优化
```

## Phase 1：识别变化轴心

### 三问法

对产品的每一个子系统/模块，回答三个问题：

**问 1：这个东西在未来 12 个月内会变吗？**

| 判断 | 标记 | 含义 |
|------|:---:|------|
| 一定会变 | `变` | 外部驱动、技术迭代、市场切换等确定性变化 |
| 可能会变 | `疑` | 有一定概率，但不确定 |
| 几乎不变 | `定` | 一旦选定，极少更换 |

**问 2：变的频率大概是多少？**

| 频率 | 标记 |
|------|:---:|
| 1~3 个月 | `高` |
| 3~6 个月 | `中` |
| 6~12 个月 | `低` |
| 几乎不变 | `无` |

**问 3：变一次的代价有多大？**

| 代价 | 标记 | 含义 |
|------|:---:|------|
| 伤筋动骨 | `S` | 牵连多个模块，改完需要全面回归 |
| 耗时但不致命 | `M` | 改动范围可控 |
| 皮外伤 | `L` | 局部替换，不影响其他 |

### 变化轴心分析表模板

| # | 子系统 | 会变? | 频率 | 代价 | 综合 | 备注 |
|---|--------|:---:|:---:|:---:|:---:|------|
| 1 | AI/模型服务 | 变 | 高 | S | **轴心** | 技术迭代极快 |
| 2 | 业务类型增减 | 变 | 高 | S | **轴心** | 产品试错 |
| 3 | 市场差异(中外) | 变 | 低 | M | 关注 | 一次性差异 |
| 4 | 登录/分享渠道 | 疑 | 低 | M | 关注 | 按市场不同 |
| 5 | 推送服务 | 疑 | 低 | M | 关注 | 按市场不同 |
| 6 | 云存储 | 定 | 无 | M | 常规 | |
| 7 | 支付 | 定 | 低 | M | 常规 | |
| 8 | UI 主题 | 疑 | 中 | L | 常规 | 换皮需求 |
| 9 | 网络层 | 定 | 无 | S | 锁死 | |
| 10 | 播放器 | 定 | 无 | M | 锁死 | |
| 11 | 图片加载 | 定 | 无 | L | 锁死 | |

**轴心判定规则：**
- `变` + `高` + `S` → **核心轴心**，必须做到极致灵活
- `变` + 任意 + `S` → **关注轴心**，做到协议级规范
- `疑` + 任意 + 任意 → **常规模块**，做到 Port+Adapter 可替换
- `定` + 任意 + 任意 → **锁死模块**，不抽象，直接用

### 顶尖架构师的思考原则

> "让所有东西都可插拔，不是架构，是逃避架构。"

顶尖架构师不做选择题，做取舍题。核心原则：

1. **找出 2~3 个一定会变的轴心，在这些轴心上做到极致灵活**
2. **其他所有东西做到极致简单——越死越好，越确定越好**
3. **不为"可能的未来需求"做抽象——等需求真的来了再做**
4. **过早抽象比没有抽象更危险**

## Phase 2：三级灵活度决策

### A 级：极致灵活（方程式赛车的引擎）

**适用于：核心轴心**

设计要求：
- **协议级抽象**：不只是接口，是完整的协议（请求格式 + 状态机 + 错误映射 + 结果管道）
- **独立模块**：单独的 Gradle Module / SPM Package
- **声明式注册**：模块自己声明"我提供什么、我依赖什么"
- **可装卸**：通过注册/注销机制动态开关
- **远程配置驱动**：可以通过 ConfigCenter 动态启停
- **独立测试**：可以完全 Mock 依赖，独立单元测试
- **版本化**：有自己的版本号，兼容性可追踪

设计检查清单：
- [ ] 换一个实现，业务代码是否零改动？
- [ ] 关掉这个模块，其他模块是否不受影响？
- [ ] 新增一个同类模块，是否不需要修改已有代码？
- [ ] 模块挂了，系统是否能降级运行而不崩溃？

### B 级：规范约束（方程式赛车的轮胎、制动）

**适用于：关注轴心、常规模块**

设计要求：
- **Port 接口定义**：清晰的 interface/protocol
- **Adapter 实现**：按市场/场景写不同实现
- **DI 注入**：通过 DI 容器切换实现
- **可测试**：有 Mock 实现用于测试
- **不需要动态装卸**

设计检查清单：
- [ ] 是否定义了 Port（纯接口，不含实现）？
- [ ] 业务代码是否只依赖 Port，不依赖具体实现？
- [ ] 是否有两套以上的 Adapter 实现？
- [ ] 是否有 Mock Adapter 用于开发测试？

### C 级：极致简单（方程式赛车的螺丝、座椅）

**适用于：锁死模块**

设计要求：
- **不抽象**：直接使用选定的技术方案
- **不定义接口**：直接依赖具体类
- **硬编码**：配置写死在代码里
- **够用就行**

设计原则：
- 越简单越好
- 越少抽象越好
- 越确定越好
- **不定义 Port，不写 Adapter**

## Phase 3：架构分层

### 五层架构

```
┌─────────────────────────────────────────────────┐
│  Feature 层 — 业务模块                           │  ← A级可装卸 + 普通业务
├─────────────────────────────────────────────────┤
│  Port 层 — 接口契约（纯定义，零实现）             │  ← 赛规：所有零件的标准规格
├─────────────────────────────────────────────────┤
│  Adapter 层 — 接口实现（可替换零件）              │  ← 具体零件：按市场/场景不同
├─────────────────────────────────────────────────┤
│  Core 层 — 框架内核（注册/装卸/事件/配置）        │  ← 底盘：不包含业务逻辑
├─────────────────────────────────────────────────┤
│  Infra 层 — 锁死基础设施（不抽象，直接使用）      │  ← C级：选定后不换
└─────────────────────────────────────────────────┘
```

### 依赖铁律

- Feature → 只能依赖 Port，**禁止直接依赖 Adapter**
- Port → 纯接口，不依赖任何具体实现
- Adapter → 实现 Port，可依赖 Infra
- Core → 不依赖 Feature
- Infra → 不依赖任何上层

### Core 内核组件

| 组件 | 职责 |
|------|------|
| AppShell | 启动初始化顺序控制 |
| FeatureRegistry | A级 Feature 注册/卸载/查询 |
| ServiceRegistry | Port → Adapter 映射管理 |
| EventBus | 模块间类型安全事件通信 |
| ConfigCenter | 远程配置拉取与下发 |
| LifecycleManager | 模块生命周期调度 |

### 模块拆分策略

按层拆 + A级创作类型各自独立：

| 层 | 拆法 | 理由 |
|---|------|------|
| Spec（Port） | 1 个 Module | 全是接口，放一起方便查找 |
| Adapter | 1 个 Module | 内部按目录分文件夹，不需要独立编译 |
| Core | 1 个 Module | 框架层，体量小 |
| Infra | 1 个 Module | 锁死基础设施，不会独立替换 |
| Feature（普通） | 每个 1 个 Module | home / create / profile / auth |
| Feature（A级） | 每个 1 个 Module | 需要可装卸，必须物理隔离 |

### 市场装配

通过 MarketConfig 封装所有市场差异：

| 零件 | 中国 | 海外 | 开发 |
|------|------|------|------|
| 登录 | 微信+手机号 | Google+Apple | Mock |
| 上传 | OSS | S3 | Mock |
| 推送 | 厂商通道 | FCM/APNs | Mock |
| AI | 自建 | 自建 | Mock |

切换市场 = 切换 MarketConfig，业务代码零改动。

## Phase 4：赛规定义（Specification）

赛规是所有灵活点的**宪法**，在代码之前定义。

### 赛规模板

```markdown
# [模块名] Specification v[版本号]

## 1. 模块声明
- 模块ID：
- 模块名称：
- 版本号：
- 提供的能力（Port）：
- 依赖的能力（需要其他模块提供什么）：

## 2. 接口契约
### 请求格式
- 方法签名
- 入参结构（必填/选填/默认值）
- 返回结构（成功/失败）

### 状态定义
- 所有合法状态的枚举
- 状态转移规则（A → B → C）
- 非法状态的处理策略

### 错误码映射
- 错误码表
- 错误分级（可重试/不可重试）
- 错误展示策略

### 事件协议
- 发出的事件列表
- 事件数据格式
- 订阅方式

## 3. 生命周期
- onCreate：模块初始化
- onStart：模块可见
- onStop：模块不可见
- onDestroy：模块销毁
- onError：模块异常时的降级策略

## 4. 资源约束
- 内存上限：
- 启动时间上限：
- 不允许访问的模块内部：

## 5. 兼容性
- 兼容的最低框架版本：
- 依赖的其他模块最低版本：

## 6. 测试要求
- 必须通过的测试场景列表
- Mock 实现要求
```

### 赛规的精髓

赛规不是代码，是**约束和规范**。它定义了：
- 每种模块的接口契约（输入什么、输出什么、错误怎么返回）
- 模块间的通信协议（事件格式、数据序列化格式、版本号规则）
- 模块的生命周期规范（必须实现哪些回调）
- 模块的声明格式（我提供什么、我依赖什么）
- 兼容性矩阵（哪个版本的模块 A 可以和哪个版本的模块 B 组合）

没有赛规，换零件就是空谈。**赛规先于代码存在。**

## Phase 5：基础工具盘点

### 方法：从业务场景反推

不要凭想象列工具清单，而是逐一扫描每个业务场景，问"这个场景需要什么基础设施支持"：

#### 图片加载与缓存

| 场景 | 需要什么 |
|------|---------|
| 瀑布流大量图片/视频封面 | 三级缓存图片加载（内存 LRU → 磁盘 LRU → 网络） |
| 上传图片 | 图片压缩（质量 + 尺寸） |
| 视频封面展示 | 视频缩略图提取 |

三级缓存由图片加载库（Coil/Kingfisher）内建，需配置：
- 内存缓存 256MB，磁盘缓存 512MB
- 占位图 → 模糊图 → 高清图 分级加载
- 统一错误图兜底

#### 文件处理

| 场景 | 需要什么 |
|------|---------|
| 上传图片 | ImageCompressor（目标大小压缩） |
| 上传视频 | VideoCompressor + VideoInfoExtractor |
| 上传音频 | AudioInfoExtractor + AudioWaveformGenerator |
| 大文件上传 | FileChunkSplitter（动态分片大小） |
| 上传前校验 | FileValidator（MIME + 大小限制） |

#### 数据存储

| 数据性质 | 存储方式 | 典型数据 |
|----------|---------|---------|
| 加密持久 | Keychain / EncryptedSP | Token |
| KV 持久 | DataStore / UserDefaults | 用户设置、远程配置 |
| 结构化持久 | Room / CoreData | 草稿、下载记录、断点续传 |
| 进程内临时 | LruCache / NSCache | Feed 缓存、搜索结果、播放状态 |
| 磁盘缓存 | 图片库内建 | 图片/视频封面 |

#### 网络

| 工具 | 说明 |
|------|------|
| TokenInterceptor | 自动注入 Token |
| TokenRefreshAuthenticator | Token 过期自动刷新，刷新期间请求排队 |
| NetworkMonitor | 网络连通性实时监测，断网全局通知 |
| PollingScheduler | 动态间隔轮询（根据进度阶段调整间隔） |

#### 安全

| 工具 | 说明 |
|------|------|
| SensitiveWordFilter | 客户端预检（第一道防线，不拦死） |
| FileValidator | 上传前校验文件类型和大小 |

#### UI 工具

| 工具 | 说明 |
|------|------|
| DateTimeFormatter | 统一时间格式化 |
| ScreenAdapter | 屏幕宽度 → 布局参数动态计算 |
| KeyboardHelper | 键盘弹起/收起监听 |
| LoadingStateManager | 统一加载/空/错误/无网络状态页 |

#### 调试监控

| 工具 | 说明 |
|------|------|
| Logger | 分级日志，生产环境自动脱敏 |
| CrashReporter | 崩溃收集 + 堆栈上报 |
| PerformanceMonitor | 关键路径耗时监控 |
| Analytics | 用户行为埋点 |

## Phase 6：碎片化适配

### 核心原则

> **碎片化差异在各层内部消化，不向上泄漏。**

Feature 层写一套代码，不需要关心屏幕多大、网络多慢、厂商是谁。

### 适配维度清单

#### 屏幕尺寸

| 维度 | 策略 |
|------|------|
| 小屏/大屏 | 瀑布流列数由 ScreenAdapter 动态计算，不硬编码 |
| 折叠屏/平板 | 首版保证不崩溃不变形，不做专项适配 |
| 布局单位 | 全部 dp / Auto Layout，禁止 px 硬编码 |
| 卡片高度 | 内容自适应，不固定 |

#### 刘海/灵动岛/挖孔

| 平台 | 方式 |
|------|------|
| Android | WindowInsets API 获取安全区域 |
| iOS | Safe Area 自动处理 |
| 规范 | 所有全屏页面使用 Safe Area / WindowInsets |

#### 系统版本

| 平台 | 最低版本 | 关键差异点 |
|------|---------|-----------|
| Android | API 26 (8.0) | 通知渠道、前台服务限制、存储权限变更、通知运行时权限 |
| iOS | 15.0 | async/await 全量可用 |

处理原则：
- 所有新 API 调用前做版本判断
- 高版本功能不可用时不崩溃，静默降级

#### 厂商 ROM（Android）

| 问题 | 处理方式 |
|------|---------|
| 华为无 FCM | PushService Adapter 内部接入华为 Push Kit |
| 小米/OPPO 后台限制 | 引导用户开权限 + WorkManager 兜底 |
| VIVO 通知默认关 | 引导用户开通知 |

原则：厂商差异在 PushService Adapter 内部消化，Feature 层无感知。

#### 网络环境

| 环境 | 策略 |
|------|------|
| 强网 | 分片 5MB，高清图 |
| 弱网 | 分片 2MB，先缩略图后高清 |
| 断网 | 全局无网络状态页，缓存只读 |
| 恢复 | NetworkMonitor 检测后自动重试 |

#### 设备性能分级

| 级别 | 判定 | 策略 |
|------|------|------|
| 高端 | 内存 ≥6GB | 全功能：高清图、动画全开 |
| 中端 | 内存 4GB | 标准：禁用视频自动播放，简化动画 |
| 低端 | 内存 ≤3GB | 精简：压缩图、禁用动画、缓存减半 |

首次启动采集设备信息，动态调整缓存大小、动画、预加载距离。

#### 暗色模式

- 所有颜色通过 Design Token 定义，禁止硬编码
- 图片资源区分浅色/深色版本
- 首版跟随系统设置

#### 国际化

- 所有用户可见文本抽入 strings 资源文件
- 时间戳统一 UTC，展示时转本地时区
- 货币/价格由服务端下发

## Phase 7：分阶段落地

### 原则

```
第一版：骨架 + 轴心灵活 + 其他全部硬编码
         ↓ 跑起来，验证方向
第二版：根据实际痛点，逐步增加灵活点
         ↓ 市场验证，收集真实变更需求
第三版：成熟的模块化体系
         ↓ 按需迭代
```

### 分阶段检查点

| 阶段 | 目标 | 检查标准 |
|:---:|------|---------|
| V1 | 核心轴心做到 A 级灵活，其他全部 C 级 | 换一次 AI 平台 ≤ 1 天 |
| V2 | 常规模块提升到 B 级 | 换登录/推送/上传 ≤ 0.5 天 |
| V3 | 按需扩展，不超前设计 | 真实变更需求 ≤ 3 天完成 |

### 落地禁忌

| 禁忌 | 原因 |
|------|------|
| 第一版就追求所有模块可插拔 | 过早抽象比没有抽象更危险 |
| 为"可能的未来需求"做抽象 | 等需求真的来了再做 |
| 所有模块统一灵活度 | 浪费精力在不会变的地方 |
| 跳过赛规直接写代码 | 没有规范的灵活 = 混乱 |
| 模块间直接引用内部类 | 违反封装，替换时连锁爆炸 |
| 碎片化差异泄漏到 Feature 层 | 各层内部消化，业务层无感知 |

## Phase 8：架构评审检查清单

在输出任何架构方案前，用此清单自检：

### 变化轴心识别
- [ ] 是否列出了所有子系统/模块？
- [ ] 是否对每个模块回答了三问（变/频率/代价）？
- [ ] 是否识别出了 2~3 个核心轴心？
- [ ] 轴心的判断是否有具体依据（不是凭感觉）？

### 灵活度分级
- [ ] 核心轴心是否做到 A 级（协议级抽象 + 可装卸）？
- [ ] 常规模块是否做到 B 级（Port + Adapter）？
- [ ] 锁死模块是否做到 C 级（不抽象，直接用）？
- [ ] 是否有模块被过度设计（不会变但做了 A 级）？
- [ ] 是否有模块被忽视（一定会变但只做了 C 级）？

### 架构分层
- [ ] 五层是否清晰分离？
- [ ] Feature 是否只依赖 Port，不依赖 Adapter？
- [ ] A级 Feature 是否各自独立 Module？
- [ ] 是否有构建时校验防止违反依赖规则？

### 赛规完整性
- [ ] 核心轴心的 Specification 是否定义完整？
- [ ] 接口契约是否包含：请求/响应/状态/错误码/事件？
- [ ] 模块生命周期是否定义？
- [ ] 模块间依赖是否声明？
- [ ] 是否有构建时校验（防止违反规范）？

### 基础工具
- [ ] 是否从业务场景反推了工具清单（不是凭想象）？
- [ ] 图片三级缓存是否配置？

### 碎片化适配
- [ ] 屏幕尺寸适配策略是否定义？
- [ ] 系统版本差异是否覆盖？

- [ ] 网络环境分级策略是否定义？
- [ ] 设备性能分级是否定义？
- [ ] 暗色模式是否通过 Design Token 管理？

### 落地可行性
- [ ] 第一版的工作量是否可控？

- [ ] 是否有 1~2 个参考实现（不用猜，照着写）？

## 快速决策工具

### 决策树

```
这个模块会变吗？
├── 会变 → 变的代价大吗？
│   ├── 大（S） → 变的频率高吗？
│   │   ├── 高 → A 级：极致灵活（轴心）
│   │   └── 低 → A 级：极致灵活（关注）
│   └── 小（M/L） → B 级：规范约束
└── 不会变 → C 级：极致简单
```

### 替换成本速算

```
如果今天就要换掉这个模块：
  需要改几个文件？ _____
  需要改几行代码？ _____
  需要回归测试几个功能？ _____
  总工时： _____ 天

  > 5 天 → 你应该做到 A 级
  1~5 天 → B 级足够
  < 1 天 → C 级就行
```

## 使用方法

1. **接到架构任务时**：先跑 Phase 1（三问法），列出变化轴心分析表
2. **做方案选型时**：用 Phase 2（三级灵活度）给每个模块定级
3. **定义架构分层**：用 Phase 3（五层架构 + 依赖铁律）搭建骨架
4. **定义赛规**：用 Phase 4（Specification 模板）为 A/B 级模块定义契约
5. **盘点基础设施**：用 Phase 5（从场景反推）列出工具清单
6. **碎片化适配**：用 Phase 6（各层内部消化）规划适配策略
7. **输出架构文档前**：用 Phase 8 检查清单自检
8. **和团队对齐时**：用决策树和速算表量化讨论，避免"我觉得"式争论
9. **向甲方汇报时**：展示变化轴心分析表 + 三级决策 + 替换成本对比，用数据说话

## 核心信条

```
1. 只为确定的变做灵活
2. 其他一切做到极致简单
3. 赛规先于代码
4. 先跑起来，再优化
5. 真实的变更需求告诉你该抽象什么
6. 过早抽象比没有抽象更危险
7. 每多一层抽象，就多一层认知负担
8. 越死的东西越可靠
9. 碎片化差异在各层内部消化，不向上泄漏
10. 工具清单从业务场景反推，不凭想象
```
