# 托管自动化启用前的触发与成本披露契约

## 典型症状

仓库所有者没有主动购买某项 CI/CD 服务，却在账单里看到自动化用量或费用。进一步检查时，
仓库已经存在带 `push`、`pull_request`、`schedule` 等触发器的工作流；平台在允许执行
自动化的仓库中接收到事件后，自动分配托管执行器。

这不是单纯的“账单说明不清”，而是自动化启用链路没有在发生外部资源消耗前向费用承担者
完整披露。工作流配置是可执行策略，不只是仓库里的普通文档。

## 两层开关与一条费用链

判断自动化是否会运行，必须同时核对：

1. **仓库配置层**：工作流声明了哪些事件、runner、矩阵、重试、artifact 和 cache。
2. **托管平台层**：仓库或组织是否允许 Actions/CI，工作流是否处于启用状态，预算或额度
   是否允许继续执行。
3. **费用链**：事件发生频率 × job 数量 × runner 类型 × 执行时长，再叠加 artifact、cache
   或其他托管资源的保留与传输。

只删除一次运行记录不会关闭触发器；只看工作流文件也不能证明平台侧当前允许执行。
关闭与复验必须同时覆盖配置层和平台层。

## 启用前必须披露

任何新增或扩大托管自动化的改动，在获得费用承担者明确批准前，至少展示：

- **触发链路**：`push`、PR、tag、定时、手动或上游工作流中的哪些事件会启动执行；
- **执行规模**：runner 操作系统与规格、job/矩阵数量、预计频率和单次时长；
- **费用归属**：由哪个用户、组织或企业账户承担用量，仓库是公开还是私有；
- **额度边界**：哪些执行包含在当前方案内，哪些 runner、存储或超额用量可能单独计费；
- **预算保护**：预算、告警、停止阈值及达到阈值后的行为；
- **关闭方法**：如何禁用单个工作流、仓库/组织自动化，以及如何移除或收窄自动触发器；
- **复验方法**：关闭后观察哪些事件、运行列表和账单指标，证明没有继续产生新运行。

具体价格、免费分钟数和产品规则会变化，不应固化成长期有效的常量。每次启用或扩大范围前，
应重新读取服务商的官方计费与工作流管理文档。以 GitHub Actions 为例，应核对官方的
[产品计费说明](https://docs.github.com/en/billing/concepts/product-billing/github-actions)、
[计费与用量概念](https://docs.github.com/en/actions/concepts/billing-and-usage)及
[禁用/启用工作流方法](https://docs.github.com/en/enterprise-cloud@latest/actions/how-tos/manage-workflow-runs/disable-and-enable-workflows)。

## 授权边界

新增可能持续消耗付费托管资源的自动触发器，属于会改变外部状态和费用风险的动作。普通的
“继续”“完成项目”或“加上 CI”不能替代费用承担者对上述链路的知情批准。

没有批准时，安全默认值是：

- 保留本地可运行的检查命令；
- 如确需仓库工作流，只提供 `workflow_dispatch` 等明确人工启动入口；
- 不新增定时、push 或 PR 自动触发；
- 在交付说明中列出启用后可能发生的执行与费用，而不是替用户开启。

这条边界只约束新增或扩大费用风险；已获明确授权且受预算门禁保护的自动化，可以按批准的
触发范围持续运行。

## 机械审查与关闭复验

代码审查至少执行以下检查：

```text
workflow changed?
  ├─ 新增/扩大 on: push | pull_request | schedule | workflow_run ?
  ├─ runner、矩阵、重试或 artifact 保留是否扩大资源消耗？
  ├─ 是否记录费用承担者的明确批准？
  ├─ 是否给出预算/告警/停止条件？
  └─ 是否给出平台侧关闭与复验步骤？
```

关闭后的证据至少包含：

1. 工作流或仓库自动化的实际禁用状态；
2. 自动触发器已删除、收窄或被平台侧禁用；
3. 在选定观察窗口内，原本会触发的事件没有产生新运行；
4. 账单/用量页没有继续出现来自该触发链的新消耗；
5. 若仍有用量，按 workflow、runner 和仓库追踪剩余来源，而不是把“已点关闭”当作事实。

## 判定线

如果交付不能回答“什么事件会启动、运行多少、谁付费、何时停止、如何关闭并证明已关闭”，
就还没有获得对托管自动化的知情授权。
