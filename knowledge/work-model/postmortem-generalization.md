# 沉淀 / 复盘通用化规则

> 触发: 用户要求"沉淀 / 记下来 / 后续不能再踩坑",或同类问题多轮返工后需要复盘。

## 问题原型

一次修复结束后只留下“发生了什么、最后改了什么”的总结，没有记录当时的任务语境、
适用边界和正负样本。后续 Agent 即使检索到文档，也无法判断当前情况是否真的同类，
更无法区分“应该启用这条知识”和“启用后是否做对”，于是出现漏召回、误应用或假完成。

## 根因与证据

根因是把沉淀当作叙事终点，而不是供检索、执行和监督共同消费的知识契约。已有消费链
要求 Skill 路由必须有正例触发/负例不触发测试，确定性门禁必须有正反 fixture；规则边界
也要求明确“不适用情况”。这些既有约束共同证明，只保存结论不足以形成防复发闭环。

## 适用边界

适用于跨项目可复用、能够脱敏，并且需要后续 Agent 独立判断或执行的工程知识。项目进度、
私有配置、未经验证的猜测留在会话记忆；纯事实速记若没有执行分支，也仍应写适用/不适用
边界，但消费者可以明确为“仅供检索”。证据不足时标 `inconclusive` 并继续收证据，不得
把猜测固化成强制规则。

## 判定样本

### 路由正例

- **输入**：修复已经完成，但同类任务中 Agent 仍反复误解何时应用这条经验
- **预期**：apply
- **原因**：需要把事故抽象成带边界和样本的可执行知识契约
- **来源**：observed

### 路由反例

- **输入**：只需要记录当前分支做到哪一步和下一项本项目待办
- **预期**：skip
- **原因**：这是项目私有状态，应进入会话记忆而不是跨项目知识库
- **来源**：constructed

### 执行合格例

- **做法或输出**：沉淀同时包含问题语境、证据状态、适用边界、四类样本及实际消费者回归
- **预期**：pass
- **原因**：检索、应用、验收和防复发都具有可审计依据
- **来源**：constructed

### 执行失败例

- **做法或输出**：只写“错误—原因—正确”三段，没有说明何时不适用，也没有任何回归样本
- **预期**：fail
- **原因**：后续 Agent 仍无法可靠判断是否召回以及结果是否真正正确
- **来源**：observed

## 核心原则

沉淀不能只记录当前功能事故,必须抽象成后续不同页面、不同场景都能执行的流程约束。

如果只写"这次为什么错",没有写"下次怎么防止同类错误",则沉淀不合格。

## 6 步通用化流程

1. **事故层**
   - 记录本次具体问题。
   - 标明触发路径、涉及的源码文件(真值端 / 实施端)、接口、状态、用户反馈。

2. **模式层**
   - 抽象可复发的问题模式。
   - 禁止只用功能名命名规则(例如只写"某业务同步遗漏")。

3. **适用范围层**
   - 明确规则覆盖哪些页面、tab、弹窗、列表 item、完成页、报告页、全局入口。
   - 同时写清是否适用于 UI、业务逻辑、资源、dark/light、接口、事件刷新。

4. **执行清单层**
   - 写成下次能直接执行的 checklist / gate。
   - 必须包含:必读文件、必搜关键词、必验状态、失败时如何处理。

5. **落地层**
   - 至少更新反模式 ADR + shared rules 或 AGENTS 中一个强制入口。
   - 只在聊天里总结不算沉淀完成。

6. **样本层**
   - 路由正例(`apply`)与反例(`skip`)定义何时启用、何时不启用；
   - 执行合格例(`pass`)与失败例(`fail`)定义什么才算做对、什么是假完成；
   - 每例标 `observed` 或 `constructed`，并进入实际 Skill/Hook/监督器的回归入口。

## 正确做法

先建立 Layer1 原始问题卡，再脱敏为 Layer2：分别保存问题原型、根因证据、适用边界和
路由/执行四类样本；样本区分真实观测与构造边界。随后按下面的最短可追踪链落到实际
消费者，并用正反回归证明知识确实生效。

## 消费与防复发

总结文档是知识真值，不是自动生效机制。每条可复用方法论在沉淀时都要回答“后续由谁消费”，
并按规则性质进入最小充分的执行入口：

| 规则性质 | 首选消费者 | 必须留下的执行证据 |
|---|---|---|
| 何时应启用某能力 | Skill 的 description / 入口路由 | 正例触发、负例不触发测试 |
| 任务应按什么顺序执行 | Skill 或宿主工作流的增量步骤 | 中断恢复、重复执行与失败路径测试 |
| 哪些结果一律不可接受 | 确定性 checker / lint / CI gate | 正反 fixture 与非零退出码 |
| 为什么形成这条规则 | 知识库或设计文档 | 指向上述消费者与门禁的可追踪关系 |

推荐维护一条最短可追踪链：

```text
原始事故/反馈 → 通用规则真值 → Skill 路由或工作流 → 机械门禁 → 正反回归测试
```

链路缺一环时要显式说明：

- 只有知识文档，没有入口路由：Agent 很可能不会在相关任务中召回它；
- 只有 Skill 文案，没有增量流程：被纠正后仍可能整段重做并再次漂移；
- 只有自然语言要求，没有机械门禁：重复犯错只能依赖下次人工发现；
- 只有门禁，没有规则真值：检查项会失去语义来源，后续容易被误删或错误放宽。

不是所有经验都要强塞进 Skill。低频、不可操作或仍需语义判断的内容可以只保留为知识；只有
满足“会复发、可路由、能给出下一步动作”时才升级为 Skill/workflow。能被确定性判断的部分
再进入门禁，主观质量仍由人工验收，不能用“存在某个关键词”冒充语义正确。

完成落地后，应反向 sweep 当前活跃的 Skill、任务模板和门禁，检查是否仍存在同源旧流程。
登记一条规则但不更新消费者，会让“已经记住”与“实际仍会犯错”同时成立。

## Pre-final Self-check

完成沉淀前必须确认:

- 是否从单点事故抽象到了同类场景?
- 是否写了不同页面 / 不同场景的适用范围?
- 是否提供了可执行检查清单?
- 是否落到后续 session 会读到的位置?
- 是否明确了实际消费者，并用正反例证明路由或门禁真的生效?
- 是否同时覆盖了路由正反例与执行正反例，而不是用一对样本混淆“是否适用”和“是否做对”?
- 是否把用户指出的遗漏也转成规则?

## 典型例子

某业务副作用(如异步同步弹窗 + 对应 push 接口)遗漏,不能只沉淀为"补齐这块逻辑"。正确沉淀是:

- 事故层:该同步弹窗和对应 `业务/push` 接口没实现。
- 模式层:只看页面 UI,没追业务副作用链路。
- 适用范围层:所有页面、弹窗、列表、完成页、报告页、全局入口。
- 执行清单层:追入口、动作、接口、事件、状态回显、实施端反搜。
- 落地层:某反模式 ADR + 某能力对齐清单 + AGENTS。
