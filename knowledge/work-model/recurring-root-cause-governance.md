# 同根因多处复发时转统一治理

- **平台**:none

## 何时触发

不是按 bug 数量,而是按**同一根因的复发次数**。出现下列信号中的两条,就该停止逐处修补:

- 同一个错误假设在 ≥3 处独立位置被发现,且每次都是"撞上才发现"
- 修完一处后,你能说出"其他地方大概率也有,但我不知道有几处"
- 每一处的修法都一样(复制同一段代码/同一个参数)
- 每一处的失败都静默(见 [[ap-0224]]),因此发现顺序取决于运气而非严重度

一天之内同一根因暴露 6 次、另一根因暴露 8 次,都属于典型的"已经该转治理"。

## 为什么逐处修补收敛不了

- **发现成本远高于修复成本**。单点修复往往只要一行,但走到那一行要经历"静默失败 →
  长期不可见 → 偶然触发 → 三步回溯"。真正贵的是发现,而逐处修补不降低发现成本。
- **存量未知**。修第 N 处时你不知道 N 的上界,也就无法判断进度,更无法向他人交代
  "这个问题解决了没有"。
- **增量无阻拦**。没有任何机制阻止第 N+1 处被写进来;新代码会以同样的方式重犯,
  因为它照抄的是现存的错误写法。

## 怎么做

1. **先出清单再选型**。全仓库扫描该根因的所有落点,按"失败可见性 × 用户可感后果"
   分级——静默且后果严重的优先。没有清单的选型是拍脑袋。
2. **消存量:抽共享实现**。把重复的判定/解析/调用收敛成单一真值,调用方只依赖它。
   注意别把"知道细节的责任"推回给调用方,那只是把漂移换了个地方。
3. **防增量:加机械守卫**。用 AST 或等价的结构化解析写全仓库扫描测试,新的违规写法即判红。
   **守卫的白名单要显式且尽量为空**,每一条豁免都要写明理由。
4. **验证守卫真的设防**:故意植入一处违规,确认判红;还原,确认转绿。
   没做过这步的守卫可能根本不生效——它自己就是 [[ap-0224]] 的受害者。
5. **分阶段落地**。存量大时按"静默高危 → 其余生产代码 → 测试代码"分批,
   每批独立可验收;不要一轮堆完,失败归因会变得不可能。

## 判据

治理完成的标志不是"改完了 N 处",而是:

- 该根因的落点数可被一条命令查出,且当前为 0(或仅剩显式豁免)
- 存在一条会在新违规出现时失败的自动检查,且该检查经过植入验证
- 新增调用方**不需要知道**这个坑的存在也不会踩到

三条缺一,就还停在"修了很多处"的阶段。

## 治理规则升级也要处理存量与失败态

共享守卫/过滤器升级不是只改一条 if；它是一次带数据迁移的规则版本变更：

1. **按结构分类，不枚举当前实例名**。例如识别 system prompt/审查官消息，应依据消息
   envelope、provenance、角色层级和稳定字段，而不是维护 `Sulde|sediment|reviewerA` 名单。
   新组件上线不应要求先被旧过滤器“认识”才安全。
2. **上线路径与存量回溯同批设计**。先扫描新规则会命中的历史草案/污染记录，输出数量和
   dry-run 差异；备份后幂等重处理，记录 rule version。只保护新增数据会让旧污染继续被
   消费，表现成“修了但仍复发”。
3. **失败态不自动复活，但必须有显式重试通道**。修复根因后，由授权操作者创建新的
   attempt，链接原失败证据、当前规则版本和重试理由；旧失败保持不可变。没有 retry API
   的 fail-closed 状态机会永久死锁。
4. **用扩张 fixture 验证**：加入一个从未见过的新组件、若干历史污染数据和一个已失败
   任务；断言结构规则能识别新组件、存量被迁移、失败仅经授权重试恢复。

判定线：规则升级若只覆盖新写入、依赖角色枚举，或把“不自动复活”实现成“永远不能
重试”，仍未形成可持续治理。
