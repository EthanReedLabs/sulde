# 0141 凭证据不足的截图判 UI 对齐(sticky/scroll 方向、视觉差异来源)

- **平台**:协调端(判断层) + 双端实施 + HarmonyOS
- **复发次数**:2

## ❌ 错误
凭设计/截图的**单一状态截图**(尤其空态 / 无列表)判断 **sticky-vs-scroll** 类布局方向。

- 典型:某页空态截图(无列表项)里,一个底部操作面板看着"在中部"。据此判成"该面板**跟随内容滚动**",把原本 **sticky 固定底部** 的面板改成跟随滚动。
- **漏掉的场景**:**满数据态**(列表有几十项)下,跟随滚动 = 该操作入口被列表埋到下面、滚才看得到;而真需求是"sticky 钉底**始终可见**"。单张空态截图看不出这个差异。

## 为什么错
- 空态截图里"内容流位置"和"sticky 钉底"视觉接近(没有列表把它们区分开)。
- sticky / scroll 是**交互行为**差异(滚动时动不动),静态单帧体现不出。
- 漏查**历史设计决策**(早已定的 sticky / 固定底部 / 跟键盘上浮 的决策)。

## ✅ 正确
改 **sticky / scroll / 固定底部 / 悬浮** 类布局方向前:
1. **必同时核"空态 + 满数据态"两种**(或让 Dev 真机走两态截图)—— 单状态截图不足以判 sticky-vs-scroll;
2. **先查文档化的历史设计决策**(此前的 sticky / 固定底部 / safeAreaInset 决策),别凭印象推翻;
3. task 契约里写清"滚动时该元素动不动 + 两态行为",不只写静态位置。

### 差异来源分类(每个肉眼差异先归类再改)
同类根因还表现在"看到一处视觉差异就直接调坐标/加背景补效果",本质仍是**证据不足就下结论**。改前先把差异归到四类之一,分类不同处理策略完全不同:

| 差异来源 | 判断方式 | 处理策略 |
|---|---|---|
| **资源本身** | 比对 asset 文件 / hash / 透明区 / dark variant | 直接复用同源资源,不自绘补效果 |
| **布局语义** | 追父级 `Stack/Positioned/SizedBox/FittedBox/Align/Padding`(或对端等价物)| 映射布局语义,不是只对最终坐标 |
| **平台能力差异** | 源端控件能力目标端无等价物 | 写显式适配策略(如 scaleDown、lazy、physics、overlay),别机械同名替换 |
| **运行状态** | 选中态 / 排序态 / 登录态 / 保存态等 | 先造同状态再比,别把状态差异当 UI 差异 |

判前先取"同页 + 同数据 + 同主题 + 同弹窗/滚动/选中态"的两端截图;取不到就在 task/handoff 写明原因并提高源码反抽粒度,不能用"感觉像"当真值。

### 先删冗余自绘层,再叠加
看到"豁口 / 光晕 / 黑块白块 / 额外边框 / 阴影 / 背景色"这类特殊视觉,**默认先怀疑多了一层自绘承载层**(系统 popup/menu/sheet 默认背景、目标端自绘的 `Stack/Row/Column` 背景层、dark/media 自动换图的主题层、透明 PNG 被外层背景污染)。

- ✅ 正确:确认差异来自源端资源本身 → **删掉冗余自绘层,只保留同源资源**;
- ❌ 错误:未确认是否多了一层就再画一层背景/阴影/遮罩/圆角去"盖"差异 —— 越叠越偏,且掩盖真实根因。
