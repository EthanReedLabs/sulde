# 0186 — GPU 后端编进包内即污染 CPU 回退:nGpuLayers=0 不是安全回退

- **平台**:Android(llama.cpp / ggml,Vulkan 后端;机制适用于任何已注册的加速后端)

## ❌ 错误

把 GPU 后端(如 Vulkan)编译进 APK,然后依赖 `nGpuLayers=0` 作为"纯 CPU 回退"路径:假设层卸载数为零时计算自然全部落在 CPU 上。

## 为什么

`nGpuLayers` 只控制**权重层的卸载数量**,不控制后端的**注册与调度参与**。只要 GPU 后端在编译期被链接并在运行时完成 backend 注册,ggml 调度器在图切分时仍可能把部分计算(如非层权重的算子、中间缓冲)放到该后端执行。结果是:名义上的"CPU 回退"路径仍会初始化 GPU 驱动、创建设备上下文、在 GPU 上跑计算——在驱动有缺陷或设备不兼容的机器上,本应安全的回退路径照样崩溃或性能异常。这与"后端标签≠真实执行位置"是同一类错配的反方向:那边是要 GPU 实际却在 CPU,这边是要 CPU 实际却沾 GPU。

## ✅ 正确

1. 安全回退必须**在后端注册层面禁用** GPU 后端,而不是只把卸载层数调零——例如通过显式开关(如 `GGML_DISABLE_VULKAN` 类环境变量/初始化参数)阻止该后端注册,或发布不链接 GPU 后端的独立 CPU-only 变体。
2. 验证回退是否真实生效时,不看配置值,看运行时证据:原生日志中不出现 GPU 后端初始化/设备创建,进程未加载 GPU 驱动库,计算缓冲全部位于 CPU。
3. 把"编进包内的后端集合"当作发布决策:每多链接一个后端,就多一条即使配置关闭也可能被调度器触碰的代码路径,需要独立的兼容性风险评估。
