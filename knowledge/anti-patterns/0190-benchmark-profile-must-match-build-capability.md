# 0190 — 设备硬件支持某后端 ≠ 当前构建已编译该后端:有效 profile 必须按构建能力裁剪

- **平台**:Android(端侧推理多后端场景;机制适用于任何按能力探测做后端路由的系统)

## ❌ 错误

benchmark/路由逻辑按**设备硬件能力**(GPU 型号、驱动版本、指令集支持)生成候选后端 profile,默认"设备支持即可用":把硬件探测结果直接作为有效候选集去测速或选路,不检查该后端是否被编译进当前包。

## 为什么

- "某后端可用"是**两个独立条件的合取**:设备硬件/驱动支持它,**且**当前构建把它编译链接了进来。硬件探测只回答前者。
- 同一份路由/benchmark 代码往往跑在多种构建变体上(CPU-only 变体、精简包、按 ABI 拆分的包),编译进的后端集合随变体变化;按硬件生成的静态候选表在部分变体上必然含有不存在的后端。
- 误选未编译后端的表现不一且都难排查:初始化直接失败、悄悄回退到 CPU 但仍记为该后端的成绩(benchmark 数据被污染)、或选路结果与真实最优后端不符——性能问题被误诊为模型/设备问题。
- 与"后端编进包内即被调度器触碰"(见 related)互为镜像:那边是**编了但想关关不掉**,这边是**没编但当作能开**;共同根因都是把配置/探测层的标签当成了构建实际能力。

## ✅ 正确

1. 有效 profile = **硬件能力集 ∩ 构建编译后端集**:候选后端列表生成后,必须先按运行时可查询的"本构建已注册/已编译后端"枚举裁剪,再进入 benchmark 或选路。
2. 构建能力用**运行时一手证据**获取(推理框架的后端注册枚举 API、动态库存在性检查),不硬编码"这个变体编了什么"的假设——变体配置会漂移。
3. benchmark 结果记录时同时落**声称后端与实际执行后端**,两者不符即判为无效数据,防止回退路径污染测速结论。
