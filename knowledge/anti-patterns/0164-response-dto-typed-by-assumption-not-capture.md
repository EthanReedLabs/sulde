# 0164 响应 DTO 按假设强类型建模而未对照真实响应

- **平台**:跨端
- **复发次数**:2

## ❌ 错误

接口文档只标注“通用响应”，未定义 `data` 的具体类型，客户端却凭假设声明为某个强类型。真实响应类型不同时，反序列化失败；即使服务端操作已经成功，客户端仍按失败处理中断后续某付费操作。

## 为什么错

- 文档未定义字段类型，不代表客户端可以任选类型建模。
- 强类型假设把后端返回的轻微漂移放大为整条业务链路失败。
- 若 `data` 本来无人消费，强类型声明没有收益，却引入了解析风险。
- 接口字段的真实形态应以抓包或可验证的响应样例为准，而不是文档中的笼统措辞。

## ✅ 正确

- 无人消费的 ack 类 `data` 使用可吞掉任意 JSON 形态的类型，例如 Android 的 `JsonElement` 或 iOS 的空载荷解码类型。
- 有人消费的数据必须先核对真实响应，再确定 DTO 类型，并保留脱敏后的响应样例作为契约依据。
- 对可能漂移的字段增加契约测试或兼容解码，不让非关键响应体破坏已成功的服务端操作。
- 对缺少明确上界的计数类字段，wire DTO 使用能覆盖服务端范围的位宽（如 `Long`），再在 domain / UI 边界显式截断；不能先用 `Int` 解码后再补救，因为超界会先破坏当前对象乃至整包响应。
- 契约测试覆盖 `Int.MAX_VALUE` 附近与超界样例，同时验证最终 wire 形态，而非只验证内存对象默认值。

## lint 状态

- ❌ 难以纯静态检查：类型是否正确依赖真实接口契约。
- 人工 review：新增 endpoint 或修改 DTO 时，必须附真实响应样例；无人消费的 ack 不做无收益的强类型假设；计数类字段还需确认服务端上界。
- 关联：接口契约校验、宽容 ack 解码与强类型边界。
