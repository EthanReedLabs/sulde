# NNNN — 并发测试任务共写同一结果/缓存目录导致假失败

- **平台**:Android

## 问题原型

多个本身稳定的测试任务并发运行时偶发失败，单独重跑却通过；失败用例共同读写固定结果目录、
缓存目录或临时文件。若只重试失败项，竞争窗口会消失，容易把共享输出污染误判成业务抖动。

## ❌ 错误

构建配置允许多个 Gradle test 任务并发执行(`--parallel`、多模块并行或自定义并发任务),而这些任务把测试结果写入同一 test-results 输出目录,或被测逻辑读写同一共享磁盘缓存目录,彼此之间没有隔离或顺序约束。

```groovy
// 自定义多个 test 任务并行跑,却共享同一输出/缓存路径
tasks.register('cacheTestA', Test) { /* 写同一 test-results 与缓存目录 */ }
tasks.register('cacheTestB', Test) { /* 写同一 test-results 与缓存目录 */ }
// gradle cacheTestA cacheTestB --parallel
```

## 根因与证据

并发任务对同一目录的写入会互相覆盖、截断结果文件,或在测试执行中争抢同一份被测缓存状态,产生与代码变更无关的偶发失败。表现为:批量并发跑失败、单独重跑通过。这类假失败难以从失败栈定位(栈指向断言而非目录竞争),会持续消耗排查时间并侵蚀 CI 结果可信度。

已观察到的判别信号是：相同代码在并行批次中失败、串行或独立临时目录中稳定通过；把输出根
按 task/run identity 隔离后，失败不再复现。单次重跑成功只能用于定位，不能作为原并行批次
通过的替代证据。

## 适用边界

- 适用于并发测试、采集或构建任务共享可写结果根、固定缓存和固定临时文件的场景。
- 若任务输出已经唯一隔离，失败仍可在相同 seed、环境和时序下单独复现，应转向业务缺陷诊断。
- 只读共享 fixture 通常不需串行；但 fixture 若含延迟生成、懒缓存或清理动作，仍属于共享写入。

## 路由正例

- **输入**：两个测试 task 并行写同一 results/cache 目录时偶发失败，分别执行均稳定通过。
- **预期**：apply
- **原因**：并行、共享可写目录和单跑恢复三个信号共同指向输出竞争。
- **来源**：observed

## 路由反例

- **输入**：单个测试使用独立临时目录，但在固定 seed 下每次都因同一断言失败。
- **预期**：skip
- **原因**：没有共享写入和并行相关性，应按确定性业务回归处理。
- **来源**：constructed

## 执行合格例

- **做法或输出**：每个 task 使用 run-scoped 临时目录，合并结果只读消费；并行与串行矩阵均通过。
- **预期**：pass
- **原因**：消除了写入身份冲突，并用两种调度方式验证修复不是偶然重跑。
- **来源**：observed

## 执行失败例

- **做法或输出**：保留共享目录，只给失败测试增加三次 retry，最终批次偶尔变绿。
- **预期**：fail
- **原因**：重试隐藏竞争且不能证明首次产物未被覆盖，证据仍不可信。
- **来源**：constructed

## ✅ 正确

- 每个 test 任务使用独立的结果输出目录(Gradle 默认按任务隔离;自定义任务不要把输出改成共享路径)。
- 读写共享磁盘状态(缓存目录等)的测试显式声明顺序执行:`mustRunAfter` / 专用串行 task,或让每个测试用独立临时目录(如 `@TempDir`)隔离被测状态,消除共享。

```groovy
// 缓存相关目标测试顺序执行,避免并发争抢共享目录
cacheTestB.mustRunAfter(cacheTestA)
```

## 自检

- 出现"并发跑挂、单跑过"的测试,首查:失败用例是否读写共享目录(test-results、磁盘缓存、固定路径临时文件)。
- 新增自定义 Test 任务时确认其 results/reports 目录未与其他任务重叠。

## 消费与防复发

- 测试运行器按 task/run identity 创建输出根，聚合器只能读取已闭合的独立结果。
- CI 同时保留并行压力用例和串行对照用例；发现“并行挂、单跑过”时先报告共享路径清单。
- 失败重试不得覆盖首轮结果或改写原批次 verdict，避免把竞争证据从报告中抹去。
