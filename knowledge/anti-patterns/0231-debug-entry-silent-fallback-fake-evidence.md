# 0231 — 调试审查入口对未知状态静默 fallback 到其他页面

- **平台**:跨端

## ❌ 错误

为了让审查者能直达某个界面状态，提供一个调试入口(调试菜单项、深链、`--state` 启动参数、路由 query、测试钩子)。入口收到无法识别的状态标识时，不报错，而是退到一个「总能显示点什么」的页面:

```text
openDebugEntry(state)
├── state 已知 → 打开对应界面
└── state 未知/拼错/已废弃 → 打开默认页(或首页、或上一次的页面)
```

审查流程照常跑完:入口点进去了、界面渲染出来了、截图存档了、对齐结论也写了——只是截的那张图和要审查的状态毫无关系。

## 为什么

**fallback 把「目标不存在」这个失败，伪装成了「目标已呈现」这个成功。** 调试入口的唯一职责是把系统精确置于某个待审状态;它一旦有权自行改换目标，产出的证据就不再自带「这是哪个状态」的标识。

下游没有任何环节能识破这次替换:

- 截图本身不携带状态标识，肉眼看是一个合法界面，不是错误页;
- 审查者默认「入口没报错 = 到了我要的地方」，不会去核对当前实际状态;
- 状态名拼错、状态枚举改名后入口未同步、该状态构造依赖的数据缺失——这三种真实故障，全都被折叠成同一个「看起来正常」的画面。

代价具有滞后性和放大性:假证据一旦进入审查记录，就成了后续判断的既定事实。基于它得出的「已对齐」「无差异」结论会阻止真正的检查，而真实的界面缺陷继续存在;等到线上暴露，回溯时才发现整条证据链从第一张截图起就是错的。**证据的价值来自它与目标的绑定关系，fallback 恰好切断了这个绑定。**

这也是它比普通 bug 更值得单列的原因:普通 bug 让流程停下，fallback 让错误的流程走完。

## ✅ 正确

**调试与审查通道遇到未知状态一律显式失败，绝不替换目标。**

1. 入口收到无法解析或无法构造的状态时**立刻中止**，抛错或返回明确的错误页，错误信息里带上收到的状态标识原文与可用状态清单;不要静默跳转、不要用默认值兜底、不要「先展示点什么」。
2. **失败必须在证据平面上可见**:错误页要能被截图截到，退出码/日志要能被自动化流程读到。只写一行日志、界面照常渲染，等于没有失败。
3. **状态清单单一来源**:入口可达的状态从状态枚举/路由表自动派生，禁止手写副本。副本与真值漂移正是「拼对了却被判未知」的常见来源。
4. **每份证据自带目标标识**:截图文件名或叠加水印里写入实际生效的状态标识(取自渲染侧的运行时真值，不是取自请求参数)，让「截的是哪个状态」可被事后核验，而不是靠记忆。
5. **审查结论只接受带标识的证据**:标识缺失或与待审状态不符的截图，判为未取到证据，不判为通过。

### 适用边界

fallback 在面向用户的产品路径上通常是对的——用户输入错误的深链时给他一个首页，好过给他一个报错。**这条反模式约束的是证据生产通道**:调试入口、审查入口、快照与回归截图工具、E2E 用例的状态置位。判据是问一句:**这条路径的输出会不会被当成「系统处于某状态」的证明?** 会，就必须显式失败;不会(用户自己在用)，才可以兜底。

同理适用于任何「构造指定状态 → 采集证据」的工具:数据种子脚本遇到未知 fixture 名、录制回放遇到缺失的 mock、对比工具遇到取不到的基线——都必须中止，不能改用一个能跑通的替代品。
