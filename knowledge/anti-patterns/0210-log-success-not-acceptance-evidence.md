# NNNN — 用 worker 日志 SUCCESS 代替 UI 落屏与设备端 DB 验收

- **平台**:跨端

## 问题原型

任务把 worker 日志、命令退出码、点击成功或单张 UI 截图当成最终验收，却没有把同一 run、
同一记录的持久层真值、冷启结果和用户最终落屏绑定起来，导致中间信号被升级为完成证据。

## ❌ 错误

后台任务 / 同步 worker 打出成功日志，就据此判定功能已完成:

```text
[worker] task=sync-items result=SUCCESS count=42
→ 结论:同步功能已完成，验收通过
```

证据链止步于日志:既没有在真机/模拟器上截到最终界面，也没有查过设备端数据库里到底有没有那 42 条记录、字段和归属是否正确。

## ❌ 错误(变体):真机 walkthrough 用 UI 证据当持久化证据

在真机上把功能从头点到尾，每步截图、每次点击都没报错、页面也跳到了成功态，于是判定「端到端跑通」:

```text
01-表单填写.png → 02-点击提交(无报错).png → 03-列表出现新条目.png
→ 结论:创建功能真机验证通过
```

全程没有导出设备端数据库确认那条记录真的存在。**点击成功、界面刷新、截图好看，都只是 UI 层的自证**——和 worker 日志 SUCCESS 属于同一类中间信号,不能顶替持久层真值。

## 为什么错

日志里的 SUCCESS 只覆盖 worker 自身那一段执行路径——它表示任务函数跑完了、没有抛异常。用户可感知的结果还要跨过两道彼此独立的关口:数据是否真正落到设备端持久层(事务是否提交、写入的表/账号/租户作用域是否正确、是否被后续清理或覆盖),以及界面是否订阅到同一份数据源并完成刷新。

这三段可以各自独立失败:写库成功但 UI 消费的是另一个实例、另一条流或过期缓存，界面永远不更新;也可能 worker 自认成功而事务回滚、或写进了错误的作用域，界面自然无数据可显示。用中间环节的 SUCCESS 推断端到端成功,这个推断本身没有依据——它把"我这段没报错"偷换成了"用户拿到了结果"。

**UI 证据同样是中间信号,方向相反而已。** 界面显示成功,可能来自乐观更新(先渲染、后落库,写失败无回滚提示)、内存态列表(数据只在 ViewModel/Store 里,进程重启即丢)、或写进了会被清理的临时作用域。这类失败恰恰**只在 UI 上看不出来**:截图、点击回调、页面跳转全部正常,重启 App 或换设备后数据消失。所以"每步都截了图"不构成持久化证据——**验收真值在设备端 DB,不在屏幕上**。

## 适用边界

- 适用于创建、同步、编辑、删除等必须跨 worker、数据库和 UI 才闭合的端到端验收。
- 纯函数或无持久化副作用的单元测试可用返回值和断言闭合，不强制设备数据库证据。
- 无法读取设备数据库时必须标为未验证；冷启/UI 只能增加置信度，不能伪造持久层真值。

## 路由正例

- **输入**：后台打印 SUCCESS 且页面出现记录，但重启后记录消失，验收报告仍写通过。
- **预期**：apply
- **原因**：中间日志与内存态 UI 被错误提升为持久化成功证据。
- **来源**：observed

## 路由反例

- **输入**：纯解析函数单元测试校验返回对象，无数据库、设备或外部副作用。
- **预期**：skip
- **原因**：任务终态就在函数返回边界，不存在需要跨层证明的持久化事实。
- **来源**：constructed

## 执行合格例

- **做法或输出**：同一 record/run 的 worker 结果、数据库快照、最终 UI 和冷启复查全部一致。
- **预期**：pass
- **原因**：执行、持久化、消费和重启后的事实链均已闭合且身份可追溯。
- **来源**：observed

## 执行失败例

- **做法或输出**：只保存 SUCCESS 日志与提交后截图，没有查询 DB，也没有冷启复查。
- **预期**：fail
- **原因**：证据只能证明回调和当前内存态，不能证明记录已持久化或可恢复。
- **来源**：observed

## ✅ 正确

验收以**最终 UI 落屏**和**设备端持久层实际状态**双证据为准,日志只作为定位线索;两者缺一不可,任一单独成立都不算通过。

1. 在目标设备/模拟器上导航到目标页,截取最终界面作为验收证据(同一设备、主题、语言、数据状态)。
2. 导出或直连设备端数据库,核对记录条数、关键字段值、所属作用域。
3. 真机 walkthrough 类验收:**每个写操作步骤后都要有一次 DB 查询**与之配对,截图与 DB 快照成对归档;只有截图没有 DB 查询的步骤,在报告里标"未验证持久化"。
4. 怀疑乐观更新/内存态时,加一道**冷启复查**:杀进程重启 App,再次进入目标页确认数据仍在——这是最低成本的持久化判别手段。
5. 两者不一致时**先导出 DB**,用 DB 状态把故障切成两半,避免在错误的一侧排查:

| DB 状态 | 界面状态 | 判定 | 排查方向 |
|---|---|---|---|
| 有正确记录 | 未显示 / 显示旧值 | 消费/刷新侧问题 | 读写是否同一个数据源实例、订阅是否建立、刷新信号是否到达、缓存是否失效 |
| 无记录 / 记录不全或字段错 | 未显示 | 写入侧问题 | 事务是否提交、写入作用域是否正确、是否被后续清理覆盖、SUCCESS 是否只代表函数返回 |
| 无记录 / 记录不全或字段错 | **显示成功(截图好看、点击无报错)** | **假通过——最危险的一格** | 是否只做了乐观更新未回滚、数据是否只在内存态/进程内缓存、写入是否被异常静默吞掉、是否写进临时或错误作用域 |

6. 只有 UI 与 DB 同时符合预期才写"验收通过";任一环节没有取到证据,报告里如实写"未验证",不用日志或截图顶替。

## 消费与防复发

- 验收脚本和 handoff 以 run/record identity 配对日志、数据库快照、截图与冷启结果。
- 发布门禁拒绝只有 `SUCCESS`、exit 0 或图片文件存在的单信号报告。
- 失败注入至少覆盖事务回滚、错误账号作用域、乐观更新未回滚和重启后内存态丢失。
