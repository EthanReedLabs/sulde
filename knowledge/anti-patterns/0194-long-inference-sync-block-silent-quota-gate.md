# NNNN — 端侧长推理同步阻塞 + 配额阻断静默 return

- **平台**:端侧(移动/桌面客户端通用)

## ❌ 错误

用户触发端侧 CPU 上的 VLM/LLM 长推理(数十秒到分钟级),两种实现都会让界面"按钮按了没反应":

1. **同步阻塞等待**:点击处理函数直接同步(或在无任何 UI 反馈的协程里)等待推理完成,期间无进度、无 loading 态、按钮不禁用,用户以为没点上而反复点击或退出。
2. **配额/额度阻断静默 return**:入口处检查额度不足/配额耗尽时直接 `return`,不弹提示、不改按钮态,拦截逻辑对用户完全不可见。

## 为什么

- 端侧 CPU 推理的耗时量级是**数十秒到分钟**,与网络请求的秒级心智完全不同;任何按"请求-响应"心智写的同步等待,在这个量级下都等于界面假死。
- 静默 return 的阻断在开发者视角是"正确地拦截了",在用户视角与 bug 无法区分——没有任何信号说明"系统收到了点击但拒绝了"。两种根因产生同一症状,排查时容易只修其一。
- 反复点击还会叠加副作用:排队多个推理任务或多次扣额度。

## ✅ 正确

- 长推理一律**异步 + 显式任务态**:点击后立即反馈(按钮进入 loading/禁用,或转入任务列表),推理在后台执行,通过进度回调/状态流更新 UI,支持取消。
- 分钟级任务考虑"提交-通知"模式:用户可离开当前页,完成后以通知/角标告知。
- 任何前置阻断(额度、配额、权限、网络)**必须显式呈现**:toast/对话框说明原因,或按钮预先置灰并附说明;禁止无 UI 反馈的 `return`。
- 自查判据:每条用户触发路径上,凡是可能"不执行"或"执行很久"的分支,都要能回答"用户此刻在屏幕上看到了什么变化"——答案是"什么都没有"即违规。

## lint

无机械 lint;code review 时对用户手势入口函数检查:(1) 是否存在无 UI 反馈的提前 return 分支;(2) 是否在点击路径上同步等待秒级以上的计算。
