# 0226 — 把文件扩展名当作类型判据

- **平台**:none

## ❌ 错误

用后缀回答"这是什么文件",而后缀既非必需也非权威。三种典型形态:

**① 用后缀决定能否执行**

Windows 的 `CreateProcess` 按扩展名与 `PATHEXT` 决定可执行性,无后缀的脚本(哪怕
首行有 shebang、内容是合法源码)一律拒绝启动。详见 [[ap-0225]]。

**② 用后缀决定要不要处理**

批处理脚本靠后缀白名单筛选目标:

```python
for path in changed_files:
    if not path.endswith(('.py', '.md', '.json', '.sh')):   # ❌
        continue
    normalize_line_endings(path)
```

无后缀的可执行入口文件不在白名单里 → 被静默跳过 → 保留了错误的行尾 → 打包进产物 →
下游的"首行必须是 `#!/usr/bin/env python3\n`"断言判红。**筛选条件本身没报错,
只是少做了事**,所以排查方向会先指向下游断言而不是上游筛选。

**③ 用后缀决定如何解码**

媒体/文档栈按后缀推断 MIME 或容器格式,缓存层却用内容哈希命名文件(无后缀),
于是解码器识别不出格式而失败——[[ap-0093]] 是这一形态在 iOS 上的实例。

## 为什么

- **后缀是给人看的约定,不是内容的一部分**。它可以缺失、可以错、可以与内容无关;
  任何把它当权威的判定,其正确率上限就是命名纪律的执行率。
- **无后缀恰恰集中在关键位置**。CLI 入口、hook 脚本、内容寻址的缓存文件、
  Unix 传统可执行体——这些通常故意不带后缀,而它们又往往在关键路径上。
- **失败形态是"少做"而非"做错"**。后缀白名单漏掉文件时不抛异常、不打日志,
  症状出现在很远的下游,与真因之间没有可见连线。
- **同一个错误假设会在不同层反复出现**。执行层、批处理层、解码层各写一次,
  修好其中一处不影响另外两处——它们只是共享了同一个假设。

## ✅ 正确

- **按内容或显式声明判定**:读 shebang、magic bytes、显式的类型字段/清单;
  二进制与文本的区分用"前若干字节是否含 NUL",而不是后缀。
- **筛选用排除法而非白名单**:批处理时先排除已知的二进制/无关后缀,其余一律处理;
  白名单会随新文件类型的加入而静默失效,排除法不会。
- **可执行性靠显式指定解释器**,不依赖宿主按后缀派发(见 [[ap-0225]])。
- **需要后缀就补上后缀**:内容寻址的缓存文件在哈希名后附加真实扩展名,
  比在消费端到处打补丁便宜得多。
- 立守卫时同样注意这条:**用 AST/内容解析写的守卫,不要在收集待检文件时又退回后缀过滤**,
  否则守卫自身带着同一个盲区。
