# 0246 — 共享消耗型 SKU 的未完成交易阻塞跨内容购买

- **平台**：跨端
- **复发次数**：1

## 问题原型

多个独立业务内容按相同价格共用一个 `CONSUMABLE` 商品。某次交易未完成平台要求的
finish/consume 后，用户点击任一共享该 SKU 的内容都会收到 `ALREADY_OWNED`，无法开始新购买。

期望是恢复历史交易原来对应的业务权益，完成服务端验单和平台交易终结，再允许重复购买；实际
实现常把 `ALREADY_OWNED` 当作普通错误直接提示。更危险的是，平台回执只携带共享 SKU，客户端
若直接把旧回执绑定给“当前点击内容”，会把历史订单的权益发给错误对象。

## ❌ 错误

- 只在本次购买成功回调里调用 finish/consume，不处理崩溃、断网、升级或旧版本遗留的 owned receipt。
- 收到 `ALREADY_OWNED` 后直接 toast 并返回，不查询未完成交易，也不恢复服务端订单。
- 多个内容共用价格型 SKU，却把 `productId` 当成唯一业务身份。
- 查询到旧回执后，用当前页面的内容 ID 发起验单，默认旧回执就是当前用户刚点击的内容。
- 服务端验单成功后若 finish 失败只写日志，不留下可重放状态。

## 根因与证据

根因是把 IAP 当成一次页面回调，而不是可跨进程中断、版本和页面恢复的持久交易状态机；共享
SKU 又把“商店商品身份”和“业务权益身份”压成了同一个字段。

一手现场证据已经确认：两个不同业务入口使用同一消耗型 SKU 时连续返回平台的
`ALREADY_OWNED`；客户端对该结果直接走通用错误分支，而只在新购买验单成功路径调用 finish。
这足以证明历史 owned receipt 没有进入当前内容购买的恢复闭环。

以下事实仍缺少只读对账证据，因此本条标记为 `inconclusive`：遗留 receipt 最初对应哪个业务
内容、服务端是否已经验单或发放权益，以及下述恢复方案在真实端服环境中是否已经闭环。安全的
下一步是查询 owned receipts，并按平台订单号或 purchase token 与服务端订单逐笔核对；不能从
共享 SKU 或当前页面反推历史权益。

## 适用边界

- 适用于测评、练习、单篇内容、虚拟币包等允许重复购买的消耗型 IAP，尤其是多个业务权益共用
  价格型 SKU 的设计。
- iOS、Android、HarmonyOS 的 finish、consume、acknowledge API 名称和终态不同，但“商店交易
  真值 + 服务端幂等验单 + 可恢复业务身份”不变量相同。
- 订阅和非消耗型商品可以复用幂等恢复原则，但不得照搬消耗型商品“终结后再次购买”的语义。
- 若错误发生在购买前商品查询为空，或 SKU 在商店后台无效，应路由到商品配置/购买 gate 诊断，
  不是本条的 owned receipt 恢复路径。
- 无法证明历史回执的原始业务身份时，必须停止自动发放并进入服务端或人工对账，不能猜测归属。

## 判定样本

### 路由正例

- **输入**：多个内容共用一个消耗型 SKU，其中一个买过后其他内容都报 already owned；如何恢复未 finish 交易？
- **预期**：apply
- **原因**：同时命中 consumable、共享 SKU、owned receipt 和业务身份恢复四个必要条件
- **来源**：observed

### 路由反例

- **输入**：商店商品查询暂时为空，页面是否应在购买前直接提示暂无商品？
- **预期**：skip
- **原因**：这是商品查询被误作购买 gate 的问题，应由 `ap-0153` 处理，不涉及历史交易恢复
- **来源**：constructed

### 执行合格例

- **做法或输出**：用 owned receipt 的平台订单标识反查原业务订单，服务端幂等确认原权益后完成 finish；随后共享 SKU 可再次购买，旧权益没有错发给当前内容
- **预期**：pass
- **原因**：同时闭合商店交易、服务端订单、业务权益身份和重复购买四个不变量
- **来源**：constructed

### 执行失败例

- **做法或输出**：只给新购买成功路径补 finish，`ALREADY_OWNED` 仍直接提示失败并返回
- **预期**：fail
- **原因**：只能防止新遗留交易，不能迁移已经阻塞账号的历史 owned receipt
- **来源**：observed

## ✅ 正确

1. **先固定身份模型**：明确 `productId -> 商品类型 -> 可购买次数 -> 业务权益数量`。存在一对多时，
   在拉起商店前持久化 purchase intent，并让后续平台订单号或 purchase token 能反查原始业务类型
   与业务 ID；无法建立此绑定时应改用独立 SKU。
2. **新交易按顺序闭环**：服务端先幂等验单并原子发放原始权益，客户端再 finish/consume。finish
   失败进入可重放队列，不能只记录日志；服务端“已处理”必须按同一订单幂等解释。
3. **把 `ALREADY_OWNED` 当恢复信号**：查询相同商品类型的 owned receipts，由服务端按平台订单号
   或 purchase token 解析原始订单；确认权益成功或已幂等处理后，再终结平台交易。
4. **禁止当前页面认领旧交易**：历史绑定缺失、冲突或账号作用域不一致时停止自动发放，保留可
   对账摘要并进入服务端修复或人工流程。
5. **恢复完成后再重试当前购买**：只有旧 receipt 已达到服务端与商店双终态，才允许共享 SKU
   发起下一笔；恢复、重试和重复回调均需 single-flight 与订单唯一约束。
6. **覆盖中断矩阵**：测试支付成功后/验单前、验单后/finish 前、finish 失败、App 崩溃或升级、
   服务端已处理、快速双击、账号切换、两个内容共享 SKU 和不同 SKU 隔离。
7. **启动与购买前都做窄扫描**：按账号和商品类型查询 unfinished receipts，只把能由服务端订单
   反查原业务身份的记录送入恢复队列；扫描失败不得清空本地 pending，也不得直接进入新购买。

## 消费与防复发

- 支付类 task/handoff 模板必须附 SKU—业务权益映射和 fresh/pending/canceled/already-owned/
  already-processed/finish-failure 状态矩阵。
- IAP code review 可静态检查消耗型购买是否存在 `ALREADY_OWNED -> query -> verify -> finish` 链，
  以及 finish 失败是否可重放。
- shared SKU 是否具有稳定业务绑定、服务端验单与发权益是否原子幂等，必须由端服合同 review 和
  故障注入验证；低可信 grep 不能替代。
- 发布前用真实商店账号制造“验单成功但未 finish”和“旧版本遗留 receipt”场景，证明恢复后既能
  再次购买，也不会向当前点击的其他内容错发权益。
- 真实验收必须记录 receipt/order、账号、原业务 ID、服务端幂等结果和平台终结状态的脱敏配对；
  仅看到 `ALREADY_OWNED` 消失仍不足以把本条从 `inconclusive` 升级为 verified。
