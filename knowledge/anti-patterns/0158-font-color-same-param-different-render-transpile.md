# 0158 — 字号/颜色"同参数不同效果":转译只对字面参数,不解析到最终渲染值

- **平台**:HarmonyOS
- **复发次数**:1
- **lint 状态**:❌ 无法静态检查(代码层看不出)→ 同页同状态截图逐元素对位 gate

## 现象

从源端(Flutter 类)转译到目标端(HarmonyOS)时,反复"参数对了但渲染不一样":目标端写的字号数字 / 颜色 token 和源端**看起来同参**,真机却**字偏大 / 色不对**。

- **字号**:同一个数字,源端可能经**多套**缩放机制落地——设计单位 token(只 ×用户字号调节,**不**做屏宽缩放)/ `.sp`(屏宽 ×用户字号调节)/ `.h`(屏高缩放)/ 裸 `.sp`(只屏宽,**不**×字号调节)。目标端往往只有**单一** `scaled()` 公式(屏宽 × 字号调节)。Dev 一律套目标端单公式 → 只对得上源端"屏宽×字号调节"那一支;源端若用"不做屏宽缩放"或"裸 .sp 不乘字号调节"的元素,目标端**两个系数都乘 → 偏大**。
- **颜色**:名字像但值不同的两个 token 选错;硬编码字面 hex **丢暗色变体**(源端 token 暗色自动翻,目标端写死不翻);透明度施加层级不同(源端只透明颜色 `withOpacity`,目标端 `.opacity()` 把整个元素含子图标一起透明);同一半透明色**叠在不同底色**上观感不同。
- **字号调节两端各存一套**(源端一个 SP key、目标端另一个),默认值虽都 1.0,一旦用户调过就发散。

## 为什么

根因不是参数,是**两端的"缩放 / 解析 / 混合"层不一致——参数只是输入,渲染结果由这层决定**。代码层对着数字看不出差异(两边都写 `16`),所以反复复发。字号同号可对应多种落地值,颜色最终观感由 hex + alpha + 暗色变体 + 叠底四层共同决定;只比对 token 名 / 数字 = 比错了对象。

实测提示:源端「用户字号调节」常常**基本是摆设**(只作用于少数文字),主导写法是裸 `.sp`(不应用字号调节)。若目标端默认一律乘字号调节系数,反而在用户调过字号时**整体偏大**。

## ✅ 正确

- **字号**:目标端默认公式**去掉多余的字号调节系数**,对齐源端主导的"只屏宽缩放"写法;仅少数确实应用字号调节的元素,用单独 helper 逐个补,不做前置大审查。字重按数值映射(不默认降一级),行高优先用倍率(对位 `height:1.x`)而非写死固定单位。
- **颜色**:用色必须**解析到最终 hex + alpha + 暗色变体 + 叠底**,和源端同位置 1:1;**禁**只对 token 名 / 数字。优先用主题 token(暗色自动翻),禁硬编码字面量。透明度分清"只透明颜色"还是"透明整个元素"。
- **真值列写解析后最终值**:协调端写字号/颜色类 task md,§真值列必含**解析后最终值**(字号经 resolver 的实际 px、颜色最终 hex+alpha+暗色),不只 token 名 / 数字。
- **铁律**:转译解析到 FINAL 渲染值,不对字面参数。
