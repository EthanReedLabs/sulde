# 0249 — 手动全量任务复用定时 opt-in 过滤导致空跑成功

- **平台**:跨端

## 问题原型

同一后台执行器同时承载定时巡检和用户发起的“立即检查全部”。定时巡检只处理显式
opt-in 的对象，而手动全量操作应立即覆盖全部符合基础条件的对象。实现若把定时任务的
选择谓词直接复用于手动入口，就可能在所有对象都未 opt-in 时返回成功，但最终摘要中的
检查、变更和失败计数全为零。

这类结果容易被误判为“上游没有变化”，实际含义却是“一个对象都没有检查”。如果调用方
又把异步入队响应当成最终结果，或把缺失字段默认成零，空跑会进一步伪装成正常完成。

## ❌ 错误

只复用执行函数，却没有把触发模式对应的选择策略显式传入：

```text
for item in enabled_items:
    if not item.scheduled_check_opt_in:
        continue
    check(item)
```

定时调度与手动入口都走这段逻辑。手动请求虽然成功入队、被 worker 领取并进入成功终态，
但只要没有对象开启定时巡检，任务就会合法地遍历完成并产生全零摘要。

## 为什么错

“复用同一执行器”不等于“复用同一执行范围”。定时任务的 opt-in、最小间隔和自动应用等
约束用于限制无人值守副作用；手动全量操作则表达用户对本次立即检查范围的明确选择，通常
应绕过定时 opt-in 与时间间隔，同时仍保持只检测、不自动应用等人工复核边界。

一手证据显示：执行器能够领取任务并写入成功终态，排除了任务拓扑和 worker 缺失；数据库
中存在符合基础条件的对象，但它们都因定时 opt-in 为 false 被跳过。仅修正客户端轮询后，
终态摘要仍为零；把触发模式传入执行器并拆分选择策略后，同一环境的检查数变为非零并识别
出真实变更。因此根因是执行范围语义混淆，而不是异步调度或部署拓扑。

## 适用边界

- 适用于同一 worker 同时承载“定时/自动”和“手动/立即”入口，且两种入口的范围、节流或
  副作用权限不同的场景。
- 如果任务一直停留在 pending/running、没有领取记录或租约持续过期，应先排查 runner、
  队列和租约，不应套用本条。
- 如果最终检查数正确但变更数为零，应核对上游数据、比较算法和缓存；不能仅凭“预期有变化”
  反推是 opt-in 过滤问题。
- 某些系统明确规定手动操作也只覆盖 opt-in 对象时，应以产品契约为准，并在界面中展示实际
  范围和跳过原因。

## 路由正例

- **输入**：用户点击“立即检查全部”，任务成功结束但检查、变更、失败均为零；系统存在启用
  对象，且这些对象都未开启只供定时巡检使用的 opt-in 开关。
- **预期**：apply
- **原因**：手动全量语义、非空候选集和按定时开关全部跳过三个信号同时成立。
- **来源**：observed

## 路由反例

- **输入**：手动任务长期停留在 pending，没有 worker 领取记录，租约也未建立。
- **预期**：skip
- **原因**：执行器尚未进入对象选择阶段，应诊断任务消费与部署拓扑。
- **来源**：constructed

## 执行合格例

- **做法或输出**：执行器接收显式触发模式；定时模式只检查 opt-in 且到期的对象，手动全量
  模式检查全部符合基础条件的对象并禁用自动应用；模式矩阵回归测试通过，真实终态的检查数
  与候选范围一致，调用方只展示轮询得到的终态摘要。
- **预期**：pass
- **原因**：选择范围、副作用权限、异步结果契约和线上终态证据全部闭合。
- **来源**：observed

## 执行失败例

- **做法或输出**：只让客户端轮询任务终态并移除缺失字段的零值兜底；后端仍按定时 opt-in
  过滤手动任务，因此最终可靠地返回检查数为零。
- **预期**：fail
- **原因**：修复了结果观察方式，却没有修复任务实际执行范围，用户仍拿不到全量检查结果。
- **来源**：observed

## ✅ 正确

1. 为执行器定义显式触发模式或策略对象，不从入口名称、全局开关或默认值间接猜测语义。
2. 分开维护基础候选条件与模式条件：手动全量使用基础候选集；定时模式再叠加 opt-in、到期
   时间和节流规则。
3. 将“检查范围”和“自动应用权限”分开建模。手动绕过定时过滤不代表可以静默扩大写入副作用。
4. 异步接口只在入队响应返回任务标识和初始状态；调用方轮询到终态后再读取统计，不把缺失
   字段默认成业务零值。
5. 摘要至少区分候选、已检查、按策略跳过、不支持、失败和变更。手动全量候选非空但检查数
   为零时，应产生可诊断信号，而不是无解释地成功。
6. 用模式矩阵覆盖“手动 + 未 opt-in”“定时 + 未 opt-in”“定时 + 已 opt-in”，并用一次真实
   终态读回验证检查数与候选范围。

## 消费与防复发

- 后台任务设计与代码评审检查：同一执行器的不同触发入口是否显式声明选择范围和副作用权限。
- API/前端回归检查：入队响应与终态结果是否分离，统计缺失是否被错误转换成零。
- 单元测试固定覆盖手动/定时 × opt-in 开/关矩阵，并断言实际调用次数而非只断言任务成功。
- 线上验收以任务终态和已检查计数为准；“success + 全零”只能作为待解释信号，不能自动等价
  于“没有变化”。
