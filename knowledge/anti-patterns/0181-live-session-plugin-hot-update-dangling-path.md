# 0181 — 长寿命会话跨越插件热更新持有悬空路径

- **平台**:协调端方法论(CLI agent 运行环境)

## 问题原型

CLI Agent 会话在启动时固定插件 Hook 与 Skill 的版本化绝对路径，随后跨越一次插件升级继续运行。
如果升级器删除旧目录，旧会话会调用不存在的脚本；如果原样保留旧目录，控制 Hook 又会继续执行
已经修复的旧规则。结果是源码、安装结果和新会话都显示修复成功，唯独正在工作的旧会话仍持续误拦截。

## ❌ 错误

把 CLI agent 会话(claude / codex 等)长时间挂着不重启,横跨插件/marketplace
的版本更新;或假设"会话开着就一直能用",闲置数小时/隔夜后直接继续输入。

## 根因与证据

- 会话进程在**启动时一次性快照** hook/skill 的绝对路径(含版本号目录),
  之后不再重读注册表——这是常见的性能取舍
- 插件更新按版本号开新目录;部分更新器(实测:codex 插件缓存)会**清空旧版本
  目录**。更新可能由**任何一个新会话的启动**自动触发——闲置会话是被"隔壁
  会话"弄断的,自己毫无动作也中招
- 失效形态:恢复输入后**每条 prompt 报 hook 脚本 No such file or directory**,
  且报错路径里带旧版本号;新开的会话完全正常——这个对照是最快的确诊依据
- 对照:保留旧版本目录的更新器(实测:Claude Code 插件缓存)不触发此问题,
  旧会话继续跑旧代码,只是拿不到新功能
- 只“保留旧目录”仍不完整：静态 Skill 快照继续旧版本通常可接受，但安全/控制 Hook 也继续
  旧版本时，会把已经修复的错误拦截逻辑带入后续任务，形成控制面自锁

已验证的关键证据是：同一台机器上，新会话加载新缓存后六类宿主能力均可正常闭合，而旧会话的
Hook 报错或拦截理由仍来自旧版本路径；把旧路径的两个 Hook 启动入口替换为受摘要保护的稳定桥后，
旧会话下一次回调即可进入当前运行时，静态 Skill 目录仍保持原字节。故障由此被分解为两个不同生命周期：
控制 Hook 可以热重绑定，宿主已加载的 Skill catalog 仍需新会话刷新。

## 适用边界

- 适用于宿主把 Hook/Skill 路径快照到会话、插件升级使用版本化缓存目录的 CLI Agent。
- 控制 Hook 可通过最小入口桥接当前运行时，但静态 Skill 内容、命令目录或宿主自身已加载的扩展清单
  不应被宣称可热更新；这些能力仍按宿主机制重启发现。
- 若旧路径从未被宿主持有，或宿主每次调用都会重新解析插件注册表，则不需要修改旧缓存入口。
- 桥接目标必须由受保护清单和代码摘要共同校验；无法证明目标身份时应失败闭锁，不能猜测最新目录。

## 路由正例

- **输入**：插件升级与新会话都正常，但一个恢复中的旧会话仍从带旧版本号的绝对路径执行 Hook，持续给出已修复的拦截理由。
- **预期**：apply
- **原因**：同时具备长寿命会话、版本化路径和新旧会话行为分叉，命中运行时代际悬挂的必要条件。
- **来源**：observed

## 路由反例

- **输入**：所有会话都从同一个稳定路径运行当前 Hook，但某个业务工具仍因参数不合法被策略拒绝。
- **预期**：skip
- **原因**：没有版本路径或运行时代际差异，应修复工具参数或现行策略，而不是热更新桥。
- **来源**：constructed

## 执行合格例

- **做法或输出**：安装器切换前快照旧缓存整树；Codex 清理目录后恢复静态树，再只更新 Hook 启动入口；入口通过稳定 launcher 校验当前 runtime 与 Adapter 摘要后转发；失败回滚恢复整树；当前旧会话下一次 Hook 回调观察到新运行时代际。
- **预期**：pass
- **原因**：既消除旧控制规则，又保留静态快照和可回滚边界，并以真实会话证据证明切换生效。
- **来源**：observed

## 执行失败例

- **做法或输出**：删除整个旧缓存、把旧目录整体软链到新目录，或只保留旧目录并宣称当前会话已升级。
- **预期**：fail
- **原因**：前两者会破坏宿主快照与版本隔离，后一种继续执行旧控制代码；都没有建立可验证的最小热重绑定。
- **来源**：observed

## ✅ 正确

- 通用插件仍以**更新后重启会话**为保守恢复；以“报错路径含版本号 + 新会话正常”为确诊信号
- 长时间闲置(隔夜/数小时)的会话,恢复工作前**主动重启**而非续用——
  与 [ap-0180](0180-warm-subagent-session-unbounded-reuse.md) 同族:
  长寿命会话默认"环境不变"的假设不成立
- 写插件更新器时不能在“删除旧路径”和“原样保留旧控制代码”之间二选一。Sulde 的做法是：
  保留每个旧版本的静态字节，只把两个平台 Hook 启动入口改成受保护稳定桥；桥先校验当前
  runtime 与 Adapter 摘要，再转发到当前安装版本。禁止把整棵旧目录软链到新 runtime
- 安装事务必须在切换前快照每个真实旧缓存整树；完整验证新 artifact/注册/launcher 后，先
  恢复被 Codex 清理的静态树，再只覆盖 Hook 入口。任一步失败恢复安装前整树。只有持久
  artifact 完整、无符号链接且版本描述符精确匹配时，才可自动修复此前中断留下的部分目录
- 安装结果分别披露 Hook 与 Skill catalog 的重启要求
- 同一 thread 可以继续使用新 Hook 控制逻辑；新增/修改过的静态 Skill 仍需新会话发现

## 消费与防复发

- 插件安装器消费该规则：发现所有保留的旧缓存，整树快照后只替换平台 Hook 入口，并在事务
  失败时精确恢复 descriptor、runtime、Skill、文档与入口全部字节。
- 稳定 launcher 消费该规则：记录当前 runtime 和 Adapter 表面摘要，任何路径或内容漂移都拒绝转发。
- SessionStart/doctor 报告必须分别披露 `hook_restart_required` 与 `skill_catalog_restart_required`，禁止用
  一个笼统的“需要重启”掩盖两种生命周期。
- 回归必须覆盖旧缓存发现、入口字节一致性、摘要漂移失败闭锁、回滚恢复，以及真实旧会话下一次回调
  进入当前运行时；只验证新会话不算完成。
