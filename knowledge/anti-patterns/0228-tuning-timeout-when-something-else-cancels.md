# 0228 — 现象含"超时"二字就调超时参数

- **平台**:none

## ❌ 错误

日志里出现 `cancelled` / `timeout` / `deadline exceeded`,直觉反应是"给的时间不够",
于是把超时值调大;无效后再调大;仍无效就怀疑对端慢、网络差、机器卡。

真实情况可能是**另一个组件在主动取消**,与超时毫无关系。同一现象下两种成因的实测对照:

| 场景 | 取消发生时刻 | 含义 |
|---|---|---|
| 无并发刷新 | `+120.00s` | 恰好等于配置的超时值 → 确实是超时 |
| 有并发刷新 | `+3.0s`(且稳定复现) | 与任何配置值都对不上 → 有东西在主动取消 |

在第二种情况下把超时从 60 调到 120,**只是把一个从未生效的旋钮调得更没用**;
更糟的是它制造了"我已经处理过这个问题"的错觉,让排查绕开真因继续往下走。

## 为什么

- **"取消"是结果,不是原因**。同一个终态可以由超时、被取消、对端关闭、资源回收
  等多条路径到达,而日志里往往只有终态词。
- **参数是最容易改的东西,所以最先被改**。改配置零成本、立刻能重试,于是它天然成为
  第一反应;而"先测量"需要找日志、对时间戳,门槛高一档。
- **时间维度是这类问题唯一的判别式**。成因不同,取消发生的**相对时刻**分布完全不同:
  超时是常量且等于配置值;主动取消跟随触发事件,与配置无关。不量这个值就没有判别依据。
- **改错旋钮会留下误导性痕迹**。配置里那个被调大的值会长期存在,后来者会以为它经过论证。

## ✅ 正确

- **先量,再调**:从日志取"开始"与"取消"两个带时间戳的事件,算差值。
  - 差值 ≈ 某个配置项 → 是超时,可以调,并说明为什么这个时长不够。
  - 差值与任何配置项都对不上,且稳定复现 → 有东西在主动取消,去找触发源
    (通常在同一时刻附近有另一条事件日志),见 [[ap-0227]]。
- **验证旋钮真的接在这条路径上**:把值改成一个显眼的数(如 7s),看取消时刻是否跟着变。
  不变就说明它不在这条链路上,立刻停止调它。
- **把测量结论写进配置注释**,包括"为什么是这个值"和"曾经因为什么调过"。
  否则下一个人只会看到一个没有来由的大数字。
- 排查过程本身要留痕:本次先后怀疑过环境变量、依赖缺失、凭证过期、另一个组件拖累,
  **四个方向都不是根因**——把排除掉的方向记下来,比只记正确答案更能缩短下次的路径。
