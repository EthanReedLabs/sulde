# 0153 — 支付链路商店商品查询是展示/诊断,不是购买前置 gate(且平台分支必须先拆)

- **平台**:跨端
- **复发次数**:2
- **lint 状态**:⏳ pending(待 task md / handoff 模板强制"支付平台分支矩阵"校验)

## 现象

把一端(如 iOS)购买流程里的"商店商品查询"机械迁移到另一端(如 HarmonyOS),并当成购买前置强校验:商品查询暂时返回空,代码在购买前直接 toast「暂无产品」并 return,导致收银台/内购弹层根本打不开——原本可以正常付款的用户被拦死。

典型误判链:

1. 看到某端购买前有一步"商店商品查询"(iOS 商店的商品详情查询),就按接口名相似,原样翻译成另一端商店的 `queryProducts`。
2. 迁移前没有先拆平台分支:第三方支付(如 Android 走的三方支付)根本没有这一步;iOS 商店查询、另一端应用商店内购查询语义各不相同。
3. 把"商品展示/诊断查询"当成"购买能否开始"的强校验,查询空 = 阻断购买。
4. 把"业务价格表的套餐数量"和"应用商店 productId 是否有效"混成同一逻辑,导致 UI 展示被平台配置状态污染(应用商店商品未激活 → 业务套餐列表被过滤成只剩 1 个甚至 0 个)。
5. 只验证单测 / build 通过,没在真机点到支付 SDK 弹层/收银台,误判"页面能进入" = "能付款"。
6. 只追成功路径,没追 `pending/canceled/error/purchased/restored/已处理交易` 状态闭环。

## 为什么

- **平台分支里的前置条件不是跨平台通用业务规则**。一端商店的商品查询是该商店特有步骤,不能机械等同为另一端商店购买前的阻断条件。
- **业务价格表层和商店商品有效性层是两层**,方向单一:业务价格表(后端返回的套餐列表)决定展示什么;应用商店 productId 是否有效是发起内购 `createPurchase(productId)` 时的平台配置 gate。后者不能反向影响前者的展示数量。
- 商品查询空,可能只是应用商店后台配置/上架/激活/签名/白名单尚未就绪的**平台配置问题**,属于内购发起后 SDK 会返回的错误码(如 "Invalid product information"),应在 SDK 层暴露并定位,而不是在前端提前一刀切拦住。
- **静态验证测不出支付**:单测/build 通过只证明代码能跑,证明不了真机能拉起支付弹层、能走完回执校验闭环。

## ✅ 正确

改任何支付/订阅/恢复购买/虚拟商品解锁链路前:

1. **先写"支付平台分支矩阵"**,逐项标另一端真值来源与本端映射:入口按钮/页面、各平台分支(iOS 商店 / Android 三方支付 / 另一端应用商店内购)分别走什么 SDK 和接口、商品来源、前置校验、SDK 发起、回调所有状态、后端闭环、权益刷新、埋点、真机依赖。
2. **移除购买前商品查询的阻断逻辑**。商店商品查询只能用于对账/展示/诊断,**不得作为购买前置 gate**;正式支付入口直接走该端应用商店内购发起。
3. **价格列表层与商店商品有效性层分层验收**:
   - 业务价格表层:页面是否请求业务价格接口、是否完整展示后端返回的套餐、入口生命周期(如"会员详情 → 续费"是否按真值新开购买页重新拉价格,而非原地改状态)。
   - 商店购买层:点击套餐后传给内购的 `productId` 是否存在于应用商店后台,且与包名、签名/Profile、测试账号、商品状态匹配。
4. **错误按层归因**,不要因为下层报错就回滚到前端"暂无产品"阻断:
   - 套餐只显示 1 个/不显示 → 查路由参数、生命周期、业务价格接口真响应、前端是否过滤。
   - 能进入内购但返回 "Invalid product information" → 查应用商店后台商品配置,不要回滚前端阻断。
   - 返回 "Too frequent API calls" → 查重复点击/防抖,是重复调用的次级错误,别覆盖主因。
5. **真机验证到支付弹层/收银台**,不是只看到"页面能进入";并追全 SDK 回调状态(取消/错误/成功/恢复/已处理交易),已处理交易语义按真值原样记录,若因平台审核偏离必须显式标注为平台 override,不能写成通用真值。

## lint 状态

- ⏳ pending → 落地为 task md / handoff 强制段:涉及支付/订阅/内购/恢复购买/权益刷新的 task,必须先附"支付平台分支矩阵",且勾选"已移除购买前商品查询阻断 + 已真机点到支付弹层"。
- 可静态检查项:grep 购买流程里"商品查询空 → return/toast 阻断"模式,命中即预警(展示/诊断查询不得出现在购买发起路径的前置分支)。
