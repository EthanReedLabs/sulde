# 0230 — 通用故障表现被当作亲历项目事实写入事实基线

- **平台**:none(跨端/知识与记忆治理)

## ❌ 错误

在维护"本人亲历项目事实"的基线(记忆库 project 条目、经历清单、简历事实源、案例研究素材)时,
把行业通用的故障表现直接登记为亲历事实:

```markdown
## 项目事实
- 处理过花屏问题
- 解决过 double free 崩溃
- 修过内存泄漏与主线程卡顿
```

这些条目只有"现象名词",没有本人的时间线、定位过程、改了什么、如何验证。
它们既可能来自真实经历,也可能来自读过的文章、别人的复盘、模型的补全——**写下时已无法区分**。

## 为什么

1. **两类知识的证据强度根本不同**。通用故障表现是"这类问题长这样"的排查知识,
   来源是公共经验,任何人都能复述;亲历项目事实是"我在某时某地做过什么"的一手主张,
   只有当事人能提供时间线与证据。前者混入后者,等于用零证据的内容抬高了基线的可信度声明。
2. **污染不可逆且会被放大**。基线是下游一切的输入:检索会把它当真值召回,
   叙述性产出(复盘、案例、对外材料)会引用它,后续会话会基于它继续推理。
   一条来源不明的"亲历"进去后,再没有信号能把它择出来,只会越传越确定。
3. **通用现象天然高频、易复述,是最容易被误收的一类**。花屏、double free、OOM、ANR
   这些词汇的"熟悉感"很强,很容易在整理时凭印象补进去,而真正的亲历条目反而因为细节琐碎被略过。
4. **它不是没价值,只是位置错了**。通用故障表现作为排查知识是有用的——归到排查知识层,
   下次遇到同类现象时它照样能被检索到,不需要靠伪装成亲历来换取留存。

## ✅ 正确

**按来源分层存放,入基线前过一道"一手证据"闸门。**

收录判据(三问,缺任一即不进事实基线):

| 问题 | 通过的样子 |
|---|---|
| 有本人时间线吗? | 能说出发生在哪个阶段、前后发生了什么 |
| 有定位过程吗? | 能说出怎么怀疑到这里、用什么工具/手段确认的 |
| 有改动与验证吗? | 能说出改了什么、改后如何确认问题消失 |

分层去向:

- **三问全过** → 亲历项目事实。写清现象 + 定位过程 + 改动 + 验证方式。
- **只有现象、无一手过程** → 排查知识条目。显式标注为通用知识,
  写"什么现象对应什么可能根因、该怎么查",不带主语、不宣称经历。
- **一时判不准** → 标为待核,不进基线。宁可暂缺一条,不可污染一条;
  日后补上时间线与证据再转正。

```markdown
## 排查知识(通用,非亲历)
- 花屏:多为渲染缓冲区被提前释放/复用或格式不匹配;查缓冲生命周期与格式协商
- double free:同一资源被两条路径各自持有所有权;查所有权移交与析构时机

## 项目事实(亲历,含证据)
- 某次列表滚动花屏:定位到复用池回收后仍被上一帧持有 →
  改为回收前等待帧提交完成 → 连续滚动 10 分钟无复现
```

**关键动作**:两类内容用**不同容器或显式来源标记**分开,而不是靠写法差异区分。
只靠"写详细一点"来区分是无效的——详细程度可以补写,来源不能。
