# 0227 — 启动期的周期性刷新掐断已就绪的连接

- **平台**:none

## ❌ 错误

宿主在启动阶段并发做两件事:拉起本地服务连接、同步远端配置/插件清单。
同步完成后触发一次"运行时刷新",而该刷新对**已经建立好的连接**一视同仁地取消重来:

```
T+0s   远端同步完成
T+1s   本地服务 Service initialized        ← 起来了
T+3s   远端同步完成(第 2 次)
T+4s   task cancelled                      ← 刚就绪的连接被取消
T+4s   Service initialized                 ← 重连
T+6s   远端同步完成(第 3 次)
T+7s   task cancelled                      ← 又被取消
T+7s   Child exited
       → 对外:"startup interrupted, not initialized"
```

启动 6 秒内同步三次,每次都掐掉一轮。服务每次都成功初始化,但**没有一次活到启动阶段结束**。

## 为什么

- **刷新语义写成了"重建全部",而不是"补齐缺失"**。实现刷新时关注的是"配置变了要生效",
  很少考虑"已经就绪的连接是否需要动"——于是幂等的刷新变成了破坏性的重建。
- **启动窗口是刷新最密集的时刻**。冷启动要拉配置、拉清单、校验缓存,几秒内可能触发
  多轮;而这正是本地服务建立连接的同一时段,两者必然重叠。
- **对外表征丢失了"曾经成功"这一事实**。终态消息只说"未初始化",看不出它成功过 N 次
  又被取消 N 次。按字面去查"为什么起不来"会一路查向服务本身,而服务完全正常——
  这是 [[ap-0223]] 的同族:一个表征掩盖了真实过程。
- **远端依赖会放大它**。同步慢或重试多时刷新次数变多;网络被代理/劫持时更明显。
  于是"换个网络就好了"这种偶发性掩盖了设计缺陷。

## ✅ 正确

- **刷新必须区分"已建立"与"待建立"**:已就绪且配置未变的连接跳过,不做无差别取消。
- **对启动窗口内的刷新做去抖/合并**:同一来源的多次同步在窗口内合并为一次生效。
- **终态消息保留过程事实**:报"未初始化"时附带"期间初始化成功 N 次、被取消 N 次",
  否则排查者拿不到最关键的线索。
- **诊断先看生命周期日志,不看警告文案**:带时间戳的 `initialized` / `cancelled` /
  `exited` 序列能直接给出因果;警告文案只有终态。
- 排查这类问题时**先量"取消发生在初始化后多久"**——若该值恒定且等于某个配置项,
  才是超时;否则是有东西在主动取消,见 [[ap-0228]]。
